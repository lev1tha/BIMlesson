`отчёт_финал.docx`, `отчёт_финал2.docx`, `отчёт_финал_вот_этот.docx` — знакомо? Так выглядит работа
без **контроля версий**. У программистов эту боль решает **Git**: он хранит всю историю изменений и
позволяет десяткам людей работать над одним проектом, не затирая друг друга. В этой лекции вы
пройдёте полный цикл: от первого репозитория на своём ноутбуке до pull request на GitHub — и
научитесь разруливать главный кошмар командной работы, конфликт слияния.

<BusinessNote>
Git и GitHub — стандарт индустрии: на GitHub больше 100 миллионов пользователей и сотни миллионов
репозиториев. Даже если вы не пишете код, вы столкнётесь с ними: там живёт код продукта, там ставят
задачи и обсуждают правки. И деньги здесь очень конкретные. Пример из жизни бишкекской студии:
разработчик случайно затёр файл с прайсом интернет-магазина на shop.kg. Без Git — день восстановления
по памяти и переписке (8 часов × 2 000 сом/час = 16 000 сом плюс риск продать товар по старой цене).
С Git — одна команда отката и 30 секунд времени. Понимание коммитов, веток и pull request делает
аналитика полноценным участником команды, а не сторонним наблюдателем.
</BusinessNote>

## Что такое Git

**Git** — система контроля версий (англ. *version control system*): она делает «снимки» (snapshots)
проекта в моменты, которые вы сами отмечаете. Бытовая аналогия — сохранения в компьютерной игре:
прошли сложный уровень — сохранились; дальше можно рисковать, потому что всегда есть точка возврата.
В любой момент можно посмотреть историю, сравнить версии или **откатиться** к любой из них. Ничего
не теряется безвозвратно.

Важная деталь: Git — **распределённая** система. Полная копия всей истории лежит у каждого участника
на компьютере, а не только на сервере. Интернет пропал в маршрутке по пути из Оша в Бишкек — вы всё
равно можете коммитить, смотреть историю и создавать ветки; синхронизируетесь, когда появится сеть.

## Стартовый цикл: init → status → add → commit

Чтобы превратить обычную папку в репозиторий, достаточно одной команды. Дальше вы будете крутить один
и тот же цикл десятки раз в день:

```bash
git init                     # 1. создать репозиторий в текущей папке (один раз)
git status                   # 2. посмотреть, что изменилось
git add index.html           # 3. отправить файл в staging (подготовить к снимку)
git commit -m "добавляю каталог товаров"   # 4. зафиксировать снимок
git log --oneline            # 5. посмотреть историю коммитов
```

Команда `git status` — ваш лучший друг. Она никогда ничего не меняет, только показывает состояние:
какие файлы изменены, какие подготовлены к коммиту, в какой вы ветке. Запутались — первым делом
`git status`.

<Callout title="Что покажет git log">
`git log` выводит историю: у каждого коммита есть уникальный идентификатор (**хеш** — строка вида
`a3f81c2`, автоматический «серийный номер» снимка), автор, дата в вашем часовом поясе (Asia/Bishkek,
UTC+6) и сообщение. Флаг `--oneline` сжимает каждый коммит до одной строки — удобно, когда история
длинная. По хешу можно вернуться к любому снимку.
</Callout>

## Staging area: зачем двухступенчатое сохранение

Новичков сбивает с толку шаг `git add`: почему нельзя сразу закоммитить? Между рабочей папкой и
историей у Git есть промежуточная зона — **staging area** (её ещё называют «индекс»). Это черновик
будущего коммита: командой `git add` вы складываете туда только те изменения, которые хотите
зафиксировать вместе.

Бытовая аналогия — корзина в супермаркете «Глобус»: вы ходите по залу (рабочая папка), кладёте в
корзину только нужное (staging), а на кассе пробиваете всё содержимое корзины одним чеком (commit).
Никто не заставляет пробивать весь магазин.

| Зона | Что это | Команда попадания |
| --- | --- | --- |
| Рабочая папка | ваши текущие правки, ещё «сырые» | вы просто редактируете файлы |
| Staging area | отобранные изменения для следующего снимка | `git add файл` |
| История | зафиксированные коммиты, «чеки» | `git commit -m "..."` |

Зачем это нужно на практике: вы за вечер поправили и шапку сайта, и цены в каталоге. Это два разных
изменения — и правильно сделать **два** коммита: `git add header.html` → коммит «правлю шапку»,
затем `git add prices.html` → коммит «обновляю цены на март». Через месяц, когда придётся искать,
в каком коммите сломались цены, вы скажете себе спасибо.

<Callout title="Хорошее сообщение к коммиту">
Сообщение коммита — это письмо будущему себе и коллегам. `git commit -m "фикс"` через месяц ничего
не скажет. А `git commit -m "исправляю валидацию email в форме заявки"` — сразу понятно, что и
зачем. Пишите по сути и в настоящем времени: «добавляю…», «чиню…». В командах Бишкека, работающих
с зарубежными заказчиками, сообщения часто пишут по-английски: `fix email validation in order form`.
</Callout>

## Откат: машина времени в действии

Во введении мы обещали «ничего не теряется». Вот конкретные команды на три типовые беды:

```bash
# 1. Испортил файл, ещё НЕ коммитил — вернуть последнюю сохранённую версию:
git restore index.html        # в старых учебниках: git checkout -- index.html

# 2. Плохой коммит уже в истории — отменить его НОВЫМ коммитом-антиподом:
git revert a3f81c2            # история сохраняется, изменения аккуратно отменены

# 3. Посмотреть, как выглядел проект неделю назад (только посмотреть):
git checkout a3f81c2          # вернуться обратно: git checkout main
```

Разница между `restore` и `revert` принципиальная. `git restore` стирает **незакоммиченные** правки
файла — быстро, но безвозвратно. `git revert` не стирает ничего: он создаёт новый коммит, который
отменяет изменения старого. История остаётся честной — видно и ошибку, и её исправление. В командной
работе почти всегда используют `revert`: переписывать общую историю — всё равно что вырывать страницы
из бухгалтерской книги.

<BusinessNote>
Аудит изменений — не только про код. Нацстатком КР и НБКР публикуют методологии и открытые данные,
и серьёзные аналитические команды ведут свои расчёты и скрипты в Git именно ради «бухгалтерской»
истории: всегда можно доказать, какая версия модели дала прогноз в отчёте за март, кто и когда
поменял формулу. Для финансовых расчётов это вопрос доверия, а иногда и юридической защиты.
</BusinessNote>

## .gitignore: что НЕ должно попасть в историю

Не всё в папке проекта нужно версионировать. Файл с именем `.gitignore` в корне репозитория — это
список того, что Git должен игнорировать:

```text
node_modules/     # тысячи файлов зависимостей — восстанавливаются командой pnpm install
.env.local        # СЕКРЕТЫ: ключи API, пароли к базам — никогда в репозиторий!
*.log             # временные журналы
.DS_Store         # служебный мусор macOS
```

Самая важная строка здесь — `.env.local`. В таких файлах лежат **секреты**: ключи платёжных шлюзов,
пароли, токены API. Публичные репозитории GitHub круглосуточно сканируют боты злоумышленников:
случайно запушенный ключ облачного сервиса находят в среднем за считанные минуты — и к утру у
компании счёт на сотни тысяч сом за аренду чужих серверов под майнинг, а у магазина — скомпрометирован
доступ к платёжному шлюзу. Причём удалить файл следующим коммитом недостаточно: Git хранит историю,
и ключ останется в старых снимках. Единственное лечение — немедленно отозвать и перевыпустить ключ.

<Callout title="Правило одной строки">
Секрет, однажды попавший в коммит, считается украденным. Поэтому `.gitignore` с строкой `.env.local`
создают **первым коммитом** проекта, до того, как в папке появится хоть один ключ.
</Callout>

## Ветки: параллельная работа без хаоса

**Ветка** (branch) — это отдельная линия разработки. Пока в основной ветке (`main`) стабильная
версия, вы делаете новую фичу в своей ветке, никому не мешая. Готово — **сливаете** (`merge`)
изменения обратно в `main`.

```bash
git switch -c order-form     # создать ветку и переключиться (старый вариант: git checkout -b)
# ... поработали, наделали коммитов ...
git switch main              # вернуться в основную
git merge order-form         # влить свои изменения
```

Ветки называют латиницей и по смыслу: `order-form`, `fix-prices`, `march-report`. Так десять человек
параллельно пилят десять фич, а потом аккуратно соединяют результат.

## Конфликт слияния: главный страх новичка

Пока Аида правит шапку, а Бакыт — подвал сайта, Git сольёт их работу автоматически. Но если оба
изменили **одну и ту же строку** одного файла, Git честно останавливается: он не знает, чья версия
правильная. Это и есть **конфликт слияния** (merge conflict). Выглядит страшно, лечится за минуту.

Допустим, Аида в `main` поставила цену доставки 150 сом, а Бакыт в своей ветке — 200 сом. При
`git merge` Git впишет в файл обе версии с маркерами:

```html
<<<<<<< HEAD
<p>Доставка по Бишкеку — 150 сом</p>
=======
<p>Доставка по Бишкеку — 200 сом</p>
>>>>>>> delivery-price
```

Читается так: между первым маркером и линией из знаков «равно» — версия текущей ветки (`HEAD`,
то есть `main`), ниже — версия вливаемой ветки `delivery-price`. Алгоритм разрешения:

1. Открыть файл и найти маркеры (`git status` покажет список конфликтующих файлов).
2. **Решить по смыслу**, что оставить: одну версию, другую или скомбинировать. Это решение принимает
   человек, часто вместе с коллегой — Git тут бессилен, вопрос-то бизнесовый: доставка стоит 150
   или 200 сом?
3. Удалить все три маркера и лишний вариант, оставить финальный текст.
4. `git add файл` и `git commit` — конфликт закрыт, слияние завершено.

<Callout title="Конфликт — это не поломка">
Конфликт — штатная ситуация, а не авария: Git специально **не стал** молча выбирать одну из версий,
потому что цена ошибки бывает высокой. Молчаливый автовыбор «200 сом» вместо согласованных 150 — это
уже реальные жалобы клиентов. Чем меньше ветка живёт (день-два, а не месяц) и чем чаще вы забираете
свежий `main`, тем реже и мельче конфликты.
</Callout>

## GitHub: общий дом для кода

Git работает и локально, но всю силу раскрывает с **удалённым** репозиторием — на **GitHub** (или
GitLab). Это общий сервер, куда команда складывает код:

- `git clone` — скачать проект себе (вместе со всей историей);
- `git push` — отправить свои коммиты на сервер;
- `git pull` — забрать изменения коллег.

Визитная карточка репозитория — файл **README.md**: GitHub показывает его прямо на главной странице
проекта. Это инструкция для новичка: что за проект, как запустить, куда писать вопросы. Правило
хорошего тона — по README посторонний человек запускает проект за 10 минут без единого вопроса
в чат.

## Pull request: экран, где живёт командная работа

**Pull request** (PR) — предложение влить свою ветку: коллеги смотрят изменения, комментируют,
одобряют — и только потом код попадает в `main`. Это и код-ревью, и защита от случайных поломок.
Для аналитика интерфейс PR на GitHub — главный рабочий экран, поэтому разберём его по частям:

| Вкладка / элемент | Что там | Зачем аналитику |
| --- | --- | --- |
| **Conversation** | описание задачи и вся дискуссия | понять, что и зачем меняют |
| **Files changed** | **diff** — построчное сравнение версий | увидеть сами изменения |
| Зелёные строки с плюсом | добавленный код | что появилось |
| Красные строки с минусом | удалённый код | что убрали |
| Комментарий к строке | клик на строку в diff → замечание точно по месту | «а НДС 12% в этой формуле учтён?» |
| **Approve / Request changes** | вердикт ревьюера | одобрить или вернуть на доработку |

Именно в diff аналитик ловит ошибки до продакшена: разработчик меняет формулу скидки, а вы в
комментарии к строке спрашиваете, почему порог 10 000 сом, если в задаче было 15 000. Одна такая
реплика в PR дешевле недели неправильных скидок на живом магазине.

Научитесь читать diff программно — это то, что делает сам GitHub, когда пишет «+120 −34» рядом с PR:

## Fork: как внести вклад в чужой проект

В чужой репозиторий пушить нельзя — прав нет. Для этого есть **fork** (форк): кнопка на GitHub,
которая создаёт вашу личную копию чужого репозитория. Схема вклада в открытый проект:

1. **Fork** — копируете проект к себе в аккаунт.
2. Клонируете свою копию, делаете ветку, коммитите исправление.
3. Открываете **pull request из форка** в оригинальный проект.
4. Мейнтейнер (владелец проекта) ревьюит и вливает — ваше имя навсегда в истории проекта.

Так устроен весь open source: от крошечных библиотек до ядра Linux. Для студента это ещё и карьерный
актив: профиль GitHub с реальными вкладами работодатели в Бишкеке смотрят внимательнее, чем диплом, —
это портфолио, которое нельзя подделать.

## Практика: три упражнения руками

**Упражнение 1 — первый репозиторий (10 минут).** Откройте терминал (в Windows — Git Bash, ставится
вместе с Git с сайта git-scm.com):

1. `mkdir my-shop` → `cd my-shop` → `git init`. Ожидаемо: сообщение `Initialized empty Git repository`.
2. Создайте файл `README.md` с одной строкой описания. `git status` — файл показан красным как
   *untracked* (неотслеживаемый).
3. `git add README.md` → `git status` — файл стал зелёным, он в staging.
4. `git commit -m "первый коммит: добавляю README"` → `git log --oneline` — вы должны увидеть ровно
   одну строку с хешем и вашим сообщением. Это ваш первый снимок.

**Упражнение 2 — конфликт своими руками (15 минут).** Продолжайте в той же папке:

1. В `README.md` впишите строку `Доставка: 150 сом`, закоммитьте в `main`.
2. `git switch -c price-change`, замените строку на `Доставка: 200 сом`, закоммитьте.
3. `git switch main`, замените ту же строку на `Доставка: 100 сом`, закоммитьте.
4. `git merge price-change`. Ожидаемо: `CONFLICT (content): Merge conflict in README.md`.
5. Откройте файл — вы должны увидеть маркеры конфликта и обе версии строки. Оставьте одну цену,
   удалите маркеры, затем `git add README.md` и `git commit`. `git log --oneline` покажет коммит
   слияния. Поздравляем: вы разрешили конфликт раньше, чем впервые испугались его на работе.

**Упражнение 3 — GitHub в браузере (15 минут).** Зарегистрируйтесь на github.com (это бесплатно),
создайте репозиторий `hello-bishkek` с галочкой «Add a README». Нажмите на карандаш в README,
внесите правку и сохраните через «Commit changes» — вы только что сделали коммит без терминала.
Откройте вкладку с историей коммитов (ссылка «commits» над списком файлов) и кликните на свой
коммит: вы должны увидеть diff — свою правку зелёным, старую строку красным. Это тот самый экран,
на котором вам предстоит ревьюить чужую работу.
