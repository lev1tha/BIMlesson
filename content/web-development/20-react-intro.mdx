## Введение

Положите в корзину интернет-магазина электроники в Бишкеке мышь за 890 сом, клавиатуру за 3 200 и
наушники за 2 500. На экране сразу три места показывают одно и то же: в шапке «Корзина (3)», в
списке три строки, внизу «Итого: 6 590 сом». Теперь уберите клавиатуру. Чтобы страница осталась
честной, программист обязан обновить все три места: в шапке станет 2, из списка пропадёт строка,
итог превратится в 3 390 сом. Забыли одно — и покупатель видит «Корзина (2)» рядом с суммой 6 590.
Он не понимает, сколько платить, и закрывает вкладку.

В лекции «DOM и события» вы управляли страницей именно так: находили элемент и руками меняли ему
текст. На кнопке со счётчиком это приятно, на корзине уже утомительно, а в настоящем магазине с
сотнями таких связей превращается в ремонт, где комнату красят по одному мазку и надеются ничего не
пропустить. React предлагает другой путь: вы описываете, как интерфейс выглядит при текущих данных,
а страницу подстраивает сам React. Эта лекция — первое знакомство: без установки и сборки, на
понятных примерах. После неё вы сможете читать код React-компонентов и понимать, зачем он устроен
именно так.

**Что вы узнаете:**

- почему ручное обновление DOM рано или поздно рассинхронизируется и сколько мест приходится помнить человеку
- в чём идея React: интерфейс как функция от данных, а не набор команд «найди и поменяй»
- что такое компонент и JSX и как пропсы превращают одну карточку в сотню товаров
- как работает useState: пара «значение и сеттер» и почему переменную нельзя менять напрямую
- как выводить списки через map и key, показывать пустую корзину и поднимать состояние к родителю
- когда React избыточен (лендинг кофейни) и почему первые две недели он кажется странным

Пригодится из прошлых лекций: «DOM и события», «Массивы, строки и первые алгоритмы», «Объекты и JSON»,
«Figma и прототипирование», «Tailwind», «TypeScript».

## Боль ручного DOM: три места — и забыть одно

Посчитаем честно, сколько работы прячется в «простой» корзине, если собирать её так, как в лекции
«DOM и события». Данных мало: один массив товаров. А вот мест на экране, которые от него зависят,
три: счётчик в шапке, список позиций и итоговая сумма. Каждое действие покупателя — добавил, убрал,
очистил, ввёл промокод — обязано найти все три места и обновить их.

```js
// Ручной DOM: обработчик «Убрать из корзины». Все три места помнит только программист
function removeItem(id) {
  // Шаг 0: поменяли данные
  cart = cart.filter(function (item) { return item.id !== id; });

  // Место 1: счётчик в шапке
  document.querySelector('#cart-count').textContent = cart.length;
  // Место 2: строка в списке
  document.querySelector('#row-' + id).remove();
  // Место 3: итоговая сумма
  document.querySelector('#cart-total').textContent = calcTotal(cart) + ' сом';

  // Забыли любую из трёх строк — ошибки нет, консоль молчит, но страница показывает неправду
}
```

Арифметика простая. Четыре действия на три места — это двенадцать строк обновления, которые нельзя
забыть. Добавили «мини-корзину» в подвал сайта — мест уже четыре, а строк шестнадцать. Каждая новая
возможность умножает число мест, где легко ошибиться, а проверить «обновлено ли всё» можно только
руками, нажимая кнопки. Хуже всего, что ошибка тихая: ничего не падает, поэтому находят её не
тесты, а покупатели.

Почувствуйте это на себе. В песочнице ниже — корзина с одной мышью за 890 сом: одно число `count` и
три места, которые его показывают: шапка, подпись на кнопке и итог. Понажимайте все три кнопки, а
потом загляните в код: в каждом обработчике стоят одни и те же три строки.

<Callout title="Проблема не в количестве кода, а в том, кто за всё отвечает">
Три строки обновления написать несложно. Сложно помнить, что они нужны при каждом изменении данных,
в каждом обработчике, годами и вместе с коллегами, которые правят тот же файл. В ручном DOM за
согласованность «данные и экран» отвечает человек, а люди ошибаются тем чаще, чем больше проект.
</Callout>

<BusinessNote>

сом. В ручном коде где-то потерялась строка обновления итога после применения промокода, и у 3% таких
покупателей (45 человек) сумма внизу не совпадает с суммой в шапке. Две трети из них — 30 человек —
не доверяют странным цифрам и уходят без заказа: 30 × 3 200 = 96 000 сом упущенной выручки в месяц,
больше миллиона в год. Сама правка занимает пять минут, вот только найти нужное место и заметить баг
до жалоб покупателей непросто: ни ошибки в консоли, ни красного экрана нет. Подход, при котором итог
вычисляется из данных и просто не может разойтись с ними, избавляет бизнес не от лишних строк кода, а
от целого класса дорогих багов.
</BusinessNote>

## Идея React: описать, как выглядит, а не как менять

Представьте, что нужно освежить комнату. Первый способ — **императивный** («делай вот эти шаги»):
вы стоите с кистью и командуете себе — снять картину, закрасить пятно слева, перекрасить стену над
диваном, не забыть про плинтус. За каждый мазок отвечаете вы, и пропустить что-то очень легко.
Второй способ — **декларативный** («хочу вот такой результат»): вы отдаёте мастеру дизайн-проект с
пометкой «сделайте как здесь», а он сам решает, что перекрасить, а что оставить как есть.

То же самое в такси: «поверните налево, потом направо, у светофора прямо» — набор шагов, а «в
аэропорт Манас» — результат. Ручной DOM из лекции «DOM и события» — это шаги: найди, поменяй,
убери. React — это результат: вы пишете, как интерфейс выглядит при таких-то данных.

Короткая формула: **UI = функция(данные)**. На входе данные (какие товары в корзине), на выходе
готовый вид интерфейса. Одни и те же данные всегда дают один и тот же экран — как у калькулятора:
одни и те же числа, один и тот же результат. Каждый вызов вашей функции React называет
**рендером**: он спрашивает «как должен выглядеть интерфейс сейчас?» и получает «дизайн-проект».
Когда данные меняются, React вызывает функцию ещё раз, сравнивает новый проект с прошлым и вносит в
настоящий DOM только отличия. Вы стали архитектором, а мастера с кистью нанимает React.

Вся жизнь React-приложения — вот такой круг:

<Mermaid
  title="Цикл React: данные → рендер → DOM; событие → setState → новый рендер"
  chart={`flowchart LR
    A["Данные<br/>(состояние)"] --> B["Рендер:<br/>функция компонента<br/>вернула разметку"]
    B --> C["DOM: React сам<br/>обновил только<br/>нужные места"]
    C --> D["Событие:<br/>клик, ввод"]
    D --> E["setState:<br/>новое значение"]
    E -->|"новый рендер"| A`}
/>

Пройдите по кругу по часовой стрелке. Данные (состояние) попадают в функцию компонента, она
возвращает разметку, React правит DOM. Покупатель что-то нажимает — событие вызывает **setState**
(общее имя для функции, которая меняет данные; в наших примерах это `setCount` и `setCart`), и круг
начинается заново. Обратите внимание, чего на схеме нет: нигде не написано «найди элемент» и
«поменяй текст». Эту работу забрал React.

<Callout title="А если после каждого изменения просто перестраивать всё через innerHTML?">
Идея здравая — и React по смыслу делает именно это: «каждый раз строим экран заново из данных». Но
буквально заменить всё содержимое страницы нельзя: пропадёт текст, который человек уже ввёл в поле,
сбросятся фокус и прокрутка, сломаются анимации, а на большой странице это ещё и медленно. React
решает задачу умнее: мысленно строит новый экран целиком, сравнивает со старым и правит в живом DOM
только то, что действительно отличается.
</Callout>

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Что пишет программист | шаги: найди элемент, поменяй текст, убери строку | результат: как выглядит интерфейс при этих данных |
| Число нужно показать в трёх местах | три раза найти элемент и три раза обновить текст | указать число в трёх местах разметки — обновит React |
| Кто следит, что экран совпадает с данными | человек: внимательность, ревью, тесты | сам принцип: экран строится из данных |
| Кто правит DOM | вы | React |

<Callout title="React не быстрее ручного DOM — он надёжнее">
Частый миф: React быстрее, потому что «умеет не трогать лишнее». Аккуратно написанный ручной код, как
правило, обгонит любой фреймворк, ведь фреймворк делает ту же работу плюс сравнение. Но на проекте
из сотни связей «аккуратно» держится недолго. React продаёт не скорость, а гарантию: экран не может
разойтись с данными, потому что из них и строится.
</Callout>

## Компонент и JSX: функция, которая возвращает разметку

Дальше React-код показан обычными блоками: запускать его вы будете в практике на `react.dev/learn`, а
песочница выше нужна была для контраста — «то же самое руками».

**Компонент** в React — это обычная JavaScript-функция, которая возвращает кусок интерфейса. Кнопка,
карточка товара, шапка сайта, вся корзина целиком — всё это компоненты, и они вкладываются друг в
друга, как матрёшки: страница собрана из блоков, блоки — из блоков поменьше. Если вы работали в Figma
(лекция «Figma и прототипирование»), вы уже мыслите так: компонент кнопки там один, а копий на
макете — десятки.

То, что функция возвращает, пишется на **JSX** — HTML-подобной записи прямо внутри JavaScript.
Выглядит как разметка, но это не HTML и не текстовая строка: JSX — удобная запись вызовов функций,
которую перед запуском превращает в обычный JavaScript сборщик.

```jsx
// Компонент — обычная функция. Имя пишем с ЗАГЛАВНОЙ буквы: так React отличает его от тегов
function Greeting() {
  // return отдаёт «дизайн-проект»: что должно быть на экране
  return <h1>Добро пожаловать в магазин электроники</h1>;
}

function App() {
  return (
    <div>
      {/* Свой компонент вставляется как обычный тег — по имени функции */}
      <Greeting />
      {/* Хоть два раза подряд: функция вызовется дважды, на экране будет два заголовка */}
      <Greeting />
    </div>
  );
}
```

За кулисами никакой магии нет — JSX превращается в вызовы функций:

```js
// То, что вы пишете:
return <h1>Привет</h1>;

// То, во что JSX превращается перед запуском (упрощённо): обычный вызов функции
return jsx('h1', { children: 'Привет' });
// Раньше то же самое писали как React.createElement('h1', null, 'Привет')
```

У JSX три привычки, которые отличают его от HTML. На них новички спотыкаются в первый день, поэтому
выучим их сразу:

```jsx
function PromoBanner() {
  // Обычная переменная JavaScript: данные для баннера
  const discount = 10;

  return (
    // Правило 1: корень один. Два соседних блока нужно обернуть в общий div
    <div className="rounded-lg bg-blue-600 p-4 text-white">
      {/* Правило 2: вместо class пишем className — слово class в JavaScript занято */}
      <img src="/promo.jpg" alt="Акция" />
      {/* Правило 3: каждый тег закрыт, даже одиночный — слэш в конце у img */}
      <p>Скидка {discount}% до пятницы</p>
      {/* Фигурные скобки — окошко обратно в JavaScript: внутри можно вычислять */}
    </div>
  );
}
```

Про фигурные скобки стоит запомнить отдельно: всё, что находится внутри них в разметке, React
вычисляет как обычный JavaScript — переменную, арифметику, вызов функции. Это и есть то самое
«окошко», через которое данные попадают на экран.

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Показать заголовок со значением | createElement, textContent, appendChild | функция возвращает разметку, значение подставляется в фигурных скобках |
| Использовать блок повторно | копировать код или писать функцию, которая шаг за шагом собирает узлы | написать компонент и вставлять его как собственный тег |
| Оформление | атрибут class в HTML и classList в JavaScript | атрибут className, а в нём утилиты Tailwind |

<Callout title="Помните боль из «Tailwind»: один className на десяти карточках?">
В лекции «Tailwind» длинная строка классов, скопированная на десять карточек, была проблемой:
поменять радиус скругления у всех сразу нельзя, одну карточку обязательно забудешь. Совет там был
такой: как только набор повторяется больше двух-трёх раз, выносите его в компонент. Теперь вы знаете,
что это такое: один компонент с одной строкой классов внутри.
</Callout>

## Пропсы: один компонент — сто товаров

Компонент, который всегда рисует одно и то же, мало полезен. Магазину нужна карточка, которую можно
показать сто раз с разными названиями и ценами. Для этого компоненту передают **пропсы** (от слова
properties, «свойства») — данные, которые родитель отдаёт ребёнку, так же как вы передаёте аргументы
в функцию.

Аналогия — бланк накладной: графы одни и те же, а в каждой накладной вписаны свои название и цена.
Компонент — это бланк, пропсы — то, что в него вписали. В Figma то же самое: компонент создаётся
один раз, копии получают свои тексты, а переключатели вариантов (размер, состояние) в лекции
«Figma и прототипирование» названы прямо: «в коде это будут пропсы».

```jsx
// Сразу достаём нужные поля (деструктуризация из лекции «Объекты и JSON»): name и price
function ProductCard({ name, price }) {
  return (
    <article className="rounded-lg border p-4">
      {/* Фигурные скобки — окошко в JS: сюда подставится значение пропса */}
      <h3 className="font-bold">{name}</h3>
      <p>{price} сом</p>
    </article>
  );
}

function Catalog() {
  return (
    <div className="grid gap-4">
      {/* Строка передаётся в кавычках, число — в фигурных скобках, чтобы осталось числом */}
      <ProductCard name="Мышь беспроводная" price={890} />
      <ProductCard name="Клавиатура механическая" price={3200} />
      <ProductCard name="Наушники беспроводные" price={2500} />
    </div>
  );
}
```

Почему число передают в фигурных скобках? Всё, что в кавычках, — строка. Цена «890» в кавычках
пришла бы как текст, и арифметика с ней сломалась бы точно так же, как с `value` у поля ввода в
лекции «DOM и события»: плюс склеил бы строки вместо сложения чисел.

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Показать 100 товаров с разными данными | функция, которая шаг за шагом собирает узлы и подставляет название и цену | один компонент, у каждого использования свои name и price |
| Поменять оформление всех карточек | искать и править каждое место, где собирается карточка | изменить компонент один раз — поменяются все |
| Проверить, что цена — число | никак: ошибка всплывёт у покупателя | TypeScript: interface для пропсов, ошибку подчеркнёт редактор |

Последняя строка таблицы — не фантазия. В лекции «TypeScript» вы описывали форму объекта через
interface; пропсы описываются ровно так же:

```tsx
// Из лекции «TypeScript»: описываем форму пропсов — ошибку покажет редактор, а не покупатель
interface ProductCardProps {
  name: string;   // название — строка
  price: number;  // цена в сомах — число
}

function ProductCard({ name, price }: ProductCardProps) {
  return (
    <article>
      <h3>{name}</h3>
      <p>{price} сом</p>
    </article>
  );
}

// Эту строку редактор подчеркнёт красным: price ждёт число, а пришла строка
// <ProductCard name="Мышь" price="890" />
```

<Callout title="Пропсы можно только читать">
Компонент получает пропсы так же, как функция аргументы: пользоваться можно, переписывать нельзя.
Если карточке нужно самой что-то запоминать и менять, например сколько штук добавили, для этого есть
другой механизм. Он называется состоянием, и сейчас мы разберём его не торопясь.
</Callout>

## Состояние: useState — память компонента

Пропсы приходят снаружи и сами не меняются. А что делать, если нажатие кнопки должно изменить то,
что нарисовано? Нужна **память компонента**, которая переживает перерисовки, а при изменении сама
запускает новую. В React она называется **состоянием** (state) и работает через специальную функцию
`useState`. Разберём по шагам, без спешки.

### Шаг 1. Почему обычная переменная не подходит

Первая мысль — завести переменную и увеличивать её по клику. Так делать нельзя, причём по двум
причинам.

- Первая: React не узнаёт об изменении. Он перерисует компонент только тогда, когда ему сообщат, что
  данные поменялись. Изменить переменную напрямую — всё равно что исправить цифру в своём блокноте
  и не позвонить мастеру: стена осталась прежней.
- Вторая: даже если перерисовка случится, функция компонента выполнится заново с первой строки, и
  обычная переменная снова станет нулём. Локальные переменные не переживают новый вызов функции.

Состояние решает обе проблемы: значение лежит не в функции, а у React, и менять его можно только
через специальную функцию — тот самый звонок мастеру.

### Шаг 2. Как читать строку с useState

```jsx
// Одна строка = ячейка памяти + единственный правильный способ её менять
const [count, setCount] = useState(0);
```

| Кусок строки | Что это |
| --- | --- |
| `useState(0)` | **хук** — специальная функция React (имя всегда начинается с use): «заведи этому компоненту ячейку памяти, начальное значение 0» |
| `count` | текущее значение из ячейки — то, что лежит в ней в момент этой перерисовки |
| `setCount` | **сеттер** — кнопка вызова мастера: записывает новое значение и просит React перерисовать компонент |
| квадратные скобки слева | знакомая деструктуризация массива из лекции «Объекты и JSON»: useState возвращает пару, а мы сразу раскладываем её по двум именам |

Имена `count` и `setCount` придумываете вы. Принято называть пару одним словом: имя значения и то же
имя с приставкой set — `cart` и `setCart`, `isOpen` и `setIsOpen`. И правило хуков: вызывайте
`useState` только на верхнем уровне компонента, не внутри `if`, циклов и вложенных функций. React
различает ячейки памяти по порядку вызовов, как ячейки камеры хранения по номерам: собьёте
порядок — получите чужие вещи.

### Шаг 3. Что происходит по клику

| Шаг | Что происходит |
| --- | --- |
| 1 | Покупатель нажимает кнопку, срабатывает onClick |
| 2 | Вызывается `setCount(count + 1)`: React запоминает новое значение |
| 3 | React заново вызывает функцию компонента — это новый рендер |
| 4 | `useState` теперь возвращает уже новое значение, и функция строит новую разметку |
| 5 | React сравнивает её с прошлой и правит в DOM только отличия: здесь один текстовый узел |

Теперь то же самое в коде — минимальный счётчик корзины:

```jsx
import { useState } from 'react';              // берём хук из библиотеки React

function Counter() {
  // count — сколько штук в корзине, setCount — единственный способ это число поменять
  const [count, setCount] = useState(0);

  return (
    <div>
      {/* Показываем текущее значение: после каждой перерисовки здесь свежее число */}
      <p>В корзине: {count} шт.</p>
      {/* onClick — это addEventListener('click') из лекции про DOM, но прямо на кнопке */}
      <button onClick={() => setCount(count + 1)}>Добавить</button>
    </div>
  );
}
```

<Callout title="count — фотография, а не табло">
Внутри одной перерисовки `count` не меняется никогда, даже сразу после вызова `setCount`: это
фотография значения на момент съёмки. Новое число появится только на следующей фотографии — в
следующей перерисовке. Запомните это: на нём держится граничный случай про тройной `setCount` ниже.
</Callout>

### Шаг 4. Три места из песочницы — одной строкой

Вернёмся к корзине из песочницы, где одно число приходилось обновлять руками в трёх местах. Вот она
на React:

```jsx
import { useState } from 'react';

function Cart() {
  // ОДНА строка состояния вместо переменной и девяти строк обновления (3 обработчика × 3 места)
  const [count, setCount] = useState(0);
  // Итог не храним отдельно, а вычисляем из count при каждой перерисовке
  const total = count * 890;

  return (
    <div>
      {/* Место 1 из трёх: шапка */}
      <header>Корзина ({count})</header>

      {/* Клик делает одно: вызывает сеттер. Ни querySelector, ни textContent */}
      <button onClick={() => setCount(count + 1)}>
        {/* Место 2: подпись кнопки */}
        В корзину ({count})
      </button>

      {/* Сброс — тоже одна строка, про экран кнопка ничего не знает */}
      <button onClick={() => setCount(0)}>Очистить</button>

      {/* Место 3: итого */}
      <p>Итого: {total} сом</p>
    </div>
  );
}
```

Четвёртое место показа (мини-корзина в подвале) здесь стоило бы одной строки разметки. Ни в каких
обработчиках дописывать ничего не пришлось бы: все места читают одно и то же `count`.

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Хранить число | переменная, которую вручную держат в согласии с экраном | useState: React знает, что число поменялось |
| Реагировать на клик | найти кнопку и повесить addEventListener | атрибут onClick прямо на кнопке |
| Обновить три места | три строки textContent в каждом обработчике | ничего: все три места читают count |

<Callout title="Не храните то, что можно вычислить">
Итог `total` здесь — не отдельное состояние, а вычисление из `count`. Если завести для итога вторую
ячейку памяти, получатся две вещи, которые снова надо держать в согласии, — та самая боль ручного DOM,
только внутри React. Правило: в состоянии лежит минимум («что выбрал покупатель»), а всё остальное —
итог, число позиций, «пусто ли» — вычисляется из него по ходу перерисовки.
</Callout>

Для массивов и объектов в состоянии действует правило гигиены из лекции «Массивы, строки и первые
алгоритмы»: исходное не мутируем, а отдаём сеттеру новую копию.

| Что нужно сделать с корзиной | Как получить новый массив, не трогая старый |
| --- | --- |
| добавить товар | `[...cart, product]` |
| убрать товар | `cart.filter(...)` оставит всех, кроме одного |
| заменить товар | `cart.map(...)` вернёт новый массив с подменённым элементом |

## Списки: map и key

В лекции «DOM и события» список из массива строился так: очистить контейнер, перебрать массив через
`forEach`, на каждый элемент создать узел и пристроить его через `appendChild`. В React список — это
просто массив, превращённый в разметку методом `map` (он знаком вам по лекции «Массивы, строки и
первые алгоритмы»): на каждый товар одна карточка.

```jsx
const products = [
  { id: 1, name: 'Мышь беспроводная', price: 890 },
  { id: 2, name: 'Клавиатура механическая', price: 3200 },
  { id: 3, name: 'Наушники беспроводные', price: 2500 },
];

function ProductList() {
  return (
    <div className="grid gap-4">
      {/* map превращает массив данных в массив карточек: на каждый товар — одна */}
      {products.map((p) => (
        // key — «номерок в гардеробе»: уникальный id из данных, по нему React узнаёт карточку
        <ProductCard key={p.id} name={p.name} price={p.price} />
      ))}
    </div>
  );
}
```

Заметили атрибут `key`? Это обязательный «номерок» каждого элемента списка. Аналогия — гардероб:
пальто висят на крючках, и гардеробщик находит ваше по номерку. Без номерков он ориентируется на
«пятое по счёту» — и если человек из середины очереди заберёт свою куртку, остальные получат чужие
вещи. React без `key` ведёт себя так же: сопоставляет карточки по позиции, и после удаления из
середины может перепутать, какая карточка какая.

Правила для `key`: уникальный среди соседей, постоянный (у товара он один и тот же при каждой
перерисовке) и берётся из данных — идентификатор товара из базы или API. Индекс в массиве годится,
только если список никогда не переставляют и не удаляют из него. Хуже всего `Math.random()`: ключ
меняется при каждой перерисовке, и React пересоздаёт все карточки заново.

Поле поиска из лекции «DOM и события» в React — это `filter` плюс `map`: поменялся запрос,
поменялся отфильтрованный массив, поменялась разметка. Ни `innerHTML = ''`, ни `appendChild`.

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Показать массив | forEach, createElement, appendChild | map возвращает карточки прямо внутри разметки |
| Перерисовать после фильтра | сначала очистить контейнер (innerHTML = ''), потом строить заново | ничего не чистить: новый массив даёт новую разметку |
| Узнавать элементы | вы держите ссылку на каждый узел сами | атрибут key — уникальный «номерок» каждого элемента |

## Условный рендер: корзина пуста — так и скажем

В ручном DOM «пустое состояние» — отдельная забота: при удалении последней строки нужно найти
заглушку и показать её, при добавлении первой — спрятать, а заодно скрыть кнопку «Оформить». Одна
забытая строка — и пустая корзина с кнопкой оплаты. В React это не действие, а просто условие в
описании интерфейса: товаров нет — рисуем заглушку, иначе список. Помните четыре состояния из лекции
«Figma и прототипирование» (пусто, загрузка, ошибка, много данных)? Вот так «пусто» превращается в
обычный `if`.

```jsx
function CartList({ items }) {
  // Граничный случай — пустой ввод: в корзине ничего нет
  if (items.length === 0) {
    // Ранний выход: показываем заглушку, остальной код функции не выполняется
    return <p>Пока пусто. Добавьте что-нибудь из каталога</p>;
  }

  // Сюда доходим, только если товары есть
  return (
    <ul>
      {items.map((item) => (
        // Цена в сомах, key из данных
        <li key={item.id}>{item.name} — {item.price} сом</li>
      ))}
    </ul>
  );
}
```

Есть и короткая запись «слева проверка, справа — что показать», но в ней сидит классическая ловушка:

```jsx
// Ловушка: в пустой корзине слева от && стоит число 0 — и React напечатает 0 прямо на экране
{items.length && <button>Оформить заказ</button>}

// Правильно: слева настоящая проверка, которая даёт true или false
{items.length > 0 && <button>Оформить заказ</button>}
```

<Callout title="Ноль — тоже значение">
React не рисует `false`, `null` и `undefined`, но число 0 рисует. Поэтому слева от `&&` ставьте
настоящее сравнение «больше нуля», а не само число.
</Callout>

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Показать «Пока пусто» | при удалении последней строки найти заглушку и показать, при добавлении — спрятать | в разметке условие: если пусто — заглушка, иначе список |
| Спрятать кнопку «Оформить» | classList.add('hidden') и не забыть вернуть класс обратно | кнопка рисуется, только если в корзине что-то есть |

## Подъём состояния: у кого должна жить память

Теперь магазин посложнее. Есть две карточки товаров с кнопкой «В корзину» и шапка со счётчиком
корзины. Нажали кнопку в карточке — число в шапке должно вырасти. Вопрос: где хранить это число?

Первая мысль — в каждой карточке своё состояние. Но тогда шапка узнать о нём не может: данные
между соседями «вбок» не передаются. Аналогия — две кассы магазина, у каждой свой блокнот выручки.
Вечером директор спрашивает «сколько всего?», и приходится складывать блокноты, надеясь, что никто
ничего не пропустил. Нормальный магазин ведёт одну общую учётную систему, а кассы лишь отправляют в
неё продажи.

В React это называется **подъёмом состояния** (lifting state up): память поднимают к ближайшему
общему родителю. Данные текут вниз — через пропсы, а события — вверх: ребёнок получает от родителя
функцию и вызывает её, когда что-то произошло. Запомните как «пропсы вниз, колбэки вверх».

<Mermaid
  title="Дерево компонентов магазина: состояние живёт в App, вниз — пропсами"
  chart={`flowchart TD
    A["App<br/>состояние корзины живёт здесь"] -->|"count"| B["Шапка<br/>(счётчик корзины)"]
    A -->|"products, onAdd"| C["СписокТоваров"]
    C -->|"name, price, onAdd"| D["КарточкаТовара<br/>Мышь беспроводная"]
    C -->|"name, price, onAdd"| E["КарточкаТовара<br/>Клавиатура механическая"]
    C -->|"name, price, onAdd"| F["КарточкаТовара ×N<br/>по одной на каждый товар"]`}
/>

Читайте дерево сверху вниз: у корня App вся память корзины, ниже шапка и список, ещё ниже —
карточки. Стрелки подписаны тем, что именно передаётся вниз. А вверх едет только одно: клик по
кнопке в карточке вызывает функцию `onAdd`, которую когда-то передал App, — и корзина меняется в
том единственном месте, где она хранится. На схеме русские названия, в коде английские: Шапка —
это `Header`, СписокТоваров — `ProductList`, КарточкаТовара — `ProductCard`.

```jsx
import { useState } from 'react';

const PRODUCTS = [
  { id: 1, name: 'Мышь беспроводная', price: 890 },
  { id: 2, name: 'Клавиатура механическая', price: 3200 },
];

// Шапка ничего не хранит и не ищет: получает готовое число пропсом
function Header({ count }) {
  return <header className="p-4 font-bold">Корзина ({count})</header>;
}

// Карточка не знает про шапку. Она умеет одно: сказать «меня нажали» через onAdd
function ProductCard({ name, price, onAdd }) {
  return (
    <div className="rounded-lg border p-4">
      <h3>{name}</h3>
      <p>{price} сом</p>
      {/* Вызываем функцию родителя. Что он с этим сделает, карточке неважно */}
      <button onClick={onAdd}>В корзину</button>
    </div>
  );
}

// Список только передаёт данные и функцию дальше вниз
function ProductList({ products, onAdd }) {
  return (
    <div>
      {products.map((p) => (
        // Для каждой карточки оборачиваем onAdd, чтобы он знал, КАКОЙ товар нажали
        <ProductCard key={p.id} name={p.name} price={p.price} onAdd={() => onAdd(p)} />
      ))}
    </div>
  );
}

// App — общий родитель: память корзины живёт ЗДЕСЬ, в одном месте
function App() {
  // Сначала корзина пуста
  const [cart, setCart] = useState([]);
  // Итог вычисляем из корзины, а не храним
  const total = cart.reduce((sum, item) => sum + item.price, 0);

  function addToCart(product) {
    // Новый массив: старые товары плюс новый. Старый массив на месте не меняем
    setCart([...cart, product]);
  }

  return (
    <div>
      {/* Вниз: сколько товаров в корзине */}
      <Header count={cart.length} />
      {/* Вниз: данные для списка и функция, которую позовёт карточка */}
      <ProductList products={PRODUCTS} onAdd={addToCart} />
      {/* Итог: 0 сом, пока корзина пуста */}
      <p>Итого: {total} сом</p>
    </div>
  );
}
```

Проверьте логику на цифрах. Нажали «В корзину» на обеих карточках: массив `cart` стал из двух
товаров, React перерисовал App — и сразу везде правда: в шапке «Корзина (2)», внизу «Итого: 4090
сом» (890 плюс 3 200).

| Задача | Руками на DOM | На React |
| --- | --- | --- |
| Карточка должна поменять счётчик в шапке | карточка сама находит шапку через querySelector и пишет туда число | карточка вызывает onAdd и ничего не знает про шапку |
| Где хранится корзина | нигде: «правда» размазана по узлам страницы | в App: одно место, один массив cart |
| Откуда шапка знает число | никто ей не сообщит, пока программист не напишет строку | получает count пропсом при каждой перерисовке |

В коде нет ни одного `querySelector`. Карточка не знает, что где-то есть шапка; шапка не знает, откуда
берётся число. Каждый компонент отвечает за свой кусочек, а согласованность гарантирует то, что вся
память лежит в одном месте.

## Экосистема: с чего начать и где это ценят

React сам по себе — библиотека для интерфейсов: сборку, адреса страниц и сервер он не даёт. Поэтому
вокруг него выросла «обвязка». Для начала вам хватит знать три имени.

| Инструмент | Что это | Где встретите |
| --- | --- | --- |
| Vite | быстрый стартовый набор: создаёт проект и запускает локальный сервер | учебные и небольшие проекты, первые шаги |
| Next.js | React плюс страницы, маршруты и сервер | реальные сайты и продукты; на нём построен и этот портал |
| TypeScript | типы поверх JavaScript (лекция «TypeScript») | большинство профессиональных React-проектов |

Начать можно за пару минут (нужен Node.js — см. лекцию «Модули и npm»):

```bash

npm create vite@latest my-shop -- --template react
cd my-shop          # зайти в папку проекта
npm install         # скачать зависимости
npm run dev         # запустить локальный сервер: откроется адрес вроде http://localhost:5173
```

Этот портал сам написан на React и Next.js. Все тренажёры, которые вы щёлкали, — подсети, OSI-пазл,

Рынок труда подтверждает: в вакансиях фронтенд-разработчиков в Бишкеке React стоит в требованиях
очень часто. Проверьте сами: откройте hh.kg, введите «frontend» и прочитайте требования в пяти

быстро разберётесь и в них.

## Когда React избыточен — и честно про кривую входа

Вспомните лендинг кофейни «Зерно» из лекции «Лендинг, который продаёт»: первый экран с офером, три
шага, блок доверия, кнопка заявки. После загрузки такая страница почти не меняется: нет корзины, нет
личного кабинета, нет данных, которые должны совпадать в нескольких местах. React здесь решает
проблему, которой нет: добавляет сборку, папку `node_modules` и десятки килобайт JavaScript, которые
телефону на медленной сети нужно скачать, прежде чем показать первый экран.

| Что строим | Что взять | Почему |
| --- | --- | --- |
| Лендинг кофейни, сайт-визитка | HTML и CSS (при желании Tailwind) | страница почти статична, «памяти» нет, грузится быстрее |
| Личный кабинет клиента с заказами и оплатой | React | много экранов, данные должны совпадать везде |
| Админка, CRM, дашборд с фильтрами | React | фильтры, таблицы, формы: состояние на каждом шагу |
| Один калькулятор на статичной странице | чистый JavaScript | тащить весь React ради одного виджета — перебор |

<BusinessNote>
Студия в Бишкеке берёт за лендинг кофейни «Зерно» 25 000 сом. Заведи она под него React-проект,
добавились бы настройка сборки, деплой и разбор зависимостей — минимум рабочий день, то есть около
3 200 сом при ставке 400 сом в час, — а продаж у кофейни от этого не прибавится ни на чашку. Совсем
другая арифметика у личного кабинета интернет-магазина на двенадцать экранов (заказы, адреса, оплата,
бонусы): там сотни связей «данные и экран», и каждая забытая — потерянный заказ, как в примере выше.
Профессионал отличается не тем, что везде ставит модный инструмент, а тем, что умеет прикинуть:
окупится ли он в этой задаче.
</BusinessNote>

Теперь честно про кривую входа. React — не самое простое, что вы учили. Чтобы читать его код, нужно
уверенно знать функции, массивы с `map` и `filter`, деструктуризацию и spread (лекции «Массивы,
строки и первые алгоритмы» и «Объекты и JSON»), модули и npm — плюс несколько новых идей: состояние,
рендер, key. Типичный путь такой: сначала «зачем так сложно, ведь querySelector проще», через неделю
«почему экран не обновился?» (почти всегда — переменную изменили напрямую), через две «как я раньше
жил без компонентов?». Если на втором этапе хочется всё бросить, это нормальный этап, а не признак
того, что вы «не программист».

<Callout title="Не учите всё сразу">
На старте вам нужны ровно три приёма: компоненты с пропсами, `useState` и `map` с `key`. Всё остальное —
`useEffect` для загрузки данных, маршруты, формы, глобальные хранилища — добавляйте по одному и тогда,
когда без него уже больно. Тот же принцип, что в бизнесе: не арендуйте склад на тысячу квадратов, пока
торгуете с балкона.
</Callout>

## Граничные случаи: где всё ломается

Каждый случай разобран по схеме: ситуация → что происходит → почему → как правильно.

**1. Изменил переменную состояния напрямую — интерфейс не обновился**

- **Ситуация:** счётчик заведён обычной переменной `let count = 0`, а в обработчике кнопки написано
  `count = count + 1`. Или корзина лежит в состоянии, а в обработчике вызван `cart.push(product)`.
- **Что происходит:** клик «ничего не делает»: число на экране прежнее. Иногда экран «догоняет» после
  совсем другого клика, и это ещё хуже: баг кажется плавающим.
- **Почему:** React узнаёт об изменениях только через сеттер. Пока не вызван `setCart` или `setCount`,
  он не знает, что данные поменялись, и не перерисовывает компонент. Если отдать сеттеру тот же
  самый массив, который вы изменили на месте, React сравнит ссылки, увидит тот же объект и тоже
  решит, что менять нечего.
- **Как правильно:** всегда отдавать сеттеру новое значение, а для массива — новую копию.

```jsx
function addToCart(product) {
  // Плохо 1: обычная переменная (let count = 0) вместо состояния — React ничего не узнал
  count = count + 1;

  // Плохо 2: меняем массив на месте. Ссылка прежняя — React решит, что ничего не изменилось
  cart.push(product);
  setCart(cart);

  // Правильно: отдаём сеттеру НОВЫЙ массив (копия из лекции про массивы)
  setCart([...cart, product]);
}
```

**2. Забыл key в map — React путает элементы при удалении из середины**

- **Ситуация:** в списке из трёх товаров у каждой карточки есть поле «комментарий к заказу». В поле
  второй карточки вы ввели «в подарок», а потом удалили первую. Ключом служит индекс элемента в
  массиве (или key нет вовсе).
- **Что происходит:** комментарий «в подарок» остался на втором месте списка, но теперь там карточка
  третьего товара: текст «переехал» к чужому товару. Без key React ещё и ругается в консоли:
  предупреждение про уникальный key у элементов списка.
- **Почему:** React узнаёт элементы по ключу, а при его отсутствии — по позиции. После удаления
  первой карточки позиции сдвинулись: ключ 0 теперь у бывшей второй карточки, ключ 1 — у бывшей
  третьей. А внутреннюю память (введённый текст) React привязывает к ключу, а не к товару, вот она
  и остаётся на месте.
- **Как правильно:** ключ из данных, то есть идентификатор товара. Тогда у клавиатуры при любых
  удалениях ключ прежний, и комментарий едет вместе с ней.

```jsx
// Плохо: ключ-индекс. Удалили первый товар — у всех остальных ключ сдвинулся
{products.map((p, i) => <ProductCard key={i} name={p.name} price={p.price} />)}

// Правильно: ключ из данных — у товара он свой навсегда
{products.map((p) => <ProductCard key={p.id} name={p.name} price={p.price} />)}
```

**3. Состояние в двух компонентах-близнецах разъехалось — поднять к родителю**

- **Ситуация:** у каждой из двух карточек свой `useState` для «сколько штук в корзине», а шапка
  должна показывать общую сумму.
- **Что происходит:** шапка показывает 0 или вообще не знает, что показывать, хотя в карточках уже по
  две штуки; две копии одного и того же числа живут отдельно и расходятся.
- **Почему:** у каждого компонента своя память. Состояние одной карточки не видно ни шапке, ни
  соседней карточке: данные «вбок» не передаются.
- **Как правильно:** поднять состояние к ближайшему общему родителю (в нашем магазине — App),
  вниз отдавать пропсами, а изменения принимать колбэками, как в разделе про подъём состояния.

```jsx
// Плохо: у каждой карточки своя память, а шапка не видит ни одной из этих ячеек
function ProductCard({ name }) {
  const [added, setAdded] = useState(0);   // «сколько штук этого товара» спрятано внутри
  return <button onClick={() => setAdded(added + 1)}>{name}: {added}</button>;
}
```

**4. Три раза подряд setCount(count + 1) — счётчик вырос на 1**

- **Ситуация:** кнопка «+3 штуки» вызывает `setCount(count + 1)` три раза подряд в одном обработчике.
- **Что происходит:** счётчик вырос на 1, а не на 3.
- **Почему:** в рамках одной перерисовки `count` — фотография, допустим 0. Все три вызова говорят
  «поставь 0 плюс 1», то есть три раза просят поставить 1. К тому же React объединяет несколько
  вызовов сеттера из одного обработчика в одну перерисовку — это называется **батчингом**
  (batching), он экономит работу.
- **Как правильно:** передать сеттеру не число, а функцию, которая получает предыдущее значение.
  Тогда каждый вызов берёт самое свежее число, а не фотографию.

```jsx
// Плохо: во всех трёх вызовах count — одно и то же число из текущего рендера
function addThree() {
  setCount(count + 1);   // count равен 0 → просим поставить 1
  setCount(count + 1);   // count всё ещё 0 → снова просим поставить 1
  setCount(count + 1);   // и снова 1. Итог на экране: 1, а не 3
}

// Правильно: передаём функцию — «возьми самое свежее значение и прибавь единицу»
function addThreeRight() {
  setCount((prev) => prev + 1);   // 0 → 1
  setCount((prev) => prev + 1);   // 1 → 2
  setCount((prev) => prev + 1);   // 2 → 3
}
```

**5. Тяжёлый расчёт прямо в компоненте — тормозит каждый рендер**

- **Ситуация:** компонент таблицы заказов при каждой перерисовке сортирует и суммирует 50 000 строк.
- **Что происходит:** ввод в поле поиска «залипает»: каждая нажатая клавиша ждёт, пока пересчитается
  вся таблица.
- **Почему:** функция компонента вызывается заново при каждом изменении состояния или пропсов, и всё,
  что написано в её теле, выполняется каждый раз — даже когда вы лишь нажали клавишу, не менявшую
  заказы. Сортировка 50 000 строк на слабом телефоне занимает десятки миллисекунд, а бюджет одного
  кадра при 60 кадрах в секунду — около 16.
- **Как правильно:** сначала измерить (вкладка Profiler в React DevTools), а потом: вынести расчёт за
  пределы компонента, если он не зависит от интерфейса; запомнить результат хуком `useMemo`, чтобы
  пересчитывать только при изменении заказов; совсем тяжёлое — считать на сервере.

```jsx
import { useMemo } from 'react';

function OrdersTable({ orders }) {
  // Плохо: эта сортировка выполняется при КАЖДОЙ перерисовке, даже если orders не менялся
  // const sorted = [...orders].sort((a, b) => b.sum - a.sum);

  // Лучше: useMemo запоминает результат и пересчитывает только когда поменялся orders
  const sorted = useMemo(() => [...orders].sort((a, b) => b.sum - a.sum), [orders]);

  return (
    <ul>
      {sorted.map((o) => (
        <li key={o.id}>Заказ {o.id}: {o.sum} сом</li>
      ))}
    </ul>
  );
}
```
