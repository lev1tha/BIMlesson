## Введение

Полтора года без единой чистки — и файл `styles.css` в проекте вырастает до нескольких тысяч строк.
Где-то там лежат `.card`, `.card-2`, `.card-new`, `.card-final`, `.card-final-v2` — и никто в команде
уже не помнит, какой из них реально используется на проде, а какой не трогали с прошлого лета. Нужно
перекрасить одну кнопку — но похожих кнопок в файле пять, имена почти не отличаются, и неизвестно,
что ещё зацепится где-то на другом конце проекта. Самое страшное слово в такой команде — не «баг»,
а «удалить»: удалить старый класс страшно, вдруг он ещё где-то используется, и мёртвый CSS просто
копится годами, потому что чистить его дороже, чем жить с ним дальше.

Так выглядит классический CSS без дисциплины — не потому что CSS плохой, а потому что у него нет
встроенного ограничения на то, как далеко может дотянуться одно правило и сколько имён можно
придумать. Утилитарный CSS, а вместе с ним и Tailwind — это другой набор правил игры: маленькие
классы одного действия вместо больших сочинённых имён. Разберёмся, как он читается и когда правда
экономит деньги, а когда это просто мода.

**Что вы узнаете:**

- почему обычный файл стилей за полтора года разрастается и «удалить класс» становится страшно
- что такое утилитарный CSS и чем маленькие классы одного действия лучше больших сочинённых имён
- как читать утилиты Tailwind, сопоставляя их с обычным CSS
- как шкала отступов в Tailwind связана с сеткой 8pt из Figma
- как состояния и адаптивность включаются через префиксы `hover:`, `focus:` и `md:`
- почему дизайн-токены не оставляют места для «случайного hex» и когда Tailwind лучше не ставить

Пригодится из прошлых лекций: «HTML и CSS», «Flexbox», «Адаптивность», «Figma и прототипирование», «CSS-анимации».

## Проблема классического CSS: как файл стилей выходит из-под контроля

В лекции 01 класс выглядел безобидно: одно имя `.btn`, десяток кнопок, всё просто и переиспользуемо.
Проблема начинается не на первой странице, а через полгода активной работы, когда у продукта уже
пятнадцать разных кнопок в разном контексте, а придумывать новое уникальное имя нужно каждый раз,
когда старое уже занято чем-то немного другим.

Получается примерно так. Понадобилась красная надпись в шапке карточки — родилось имя
`.card-header-title-red`. Через неделю такая же нужна в подвале — не факт, что кто-то вспомнит про
уже существующий класс, скорее появится `.card-footer-title-red`, а то и вовсе
`.card-header-title-red-2`, потому что первый «наверное, используется где-то ещё, лучше не трогать».
Дело не в лени конкретного разработчика: у CSS-классов нет встроенного способа сказать «я больше не
нужен» — они просто накапливаются.

```css
/* Реальный фрагмент выросшего styles.css: три очень похожих правила,
   и без истории git не понять, какое из них ещё используется на проде */
.card-header-title-red { color: #dc2626; font-weight: 700; }
.card-footer-title-red { color: #dc2626; font-weight: 700; margin-top: 4px; }
.card-header-title-red-2 { color: #ef4444; font-weight: 700; padding-left: 2px; }
```

<Callout title="Самое дорогое слово в старом проекте — «удалить»">
Удалить существующий класс страшно: он может использоваться на странице, которую давно не открывали
в браузере, — старой акции, забытой версии формы, скрытом блоке. Поэтому мёртвый CSS не выбрасывают,
а копят «на всякий случай», и файл стилей растёт только в одну сторону — вверх.
</Callout>

<BusinessNote>
Веб-студия в Бишкеке два года ведёт сайт сети кофеен: `styles.css` дорос до 3 700 строк, и внятной
системы имён в нём давно нет — вперемешку `.btn`, `.btn-primary`, `.btn-cta`, `.header-btn-v2`.
Приходит новый вёрстальщик со ставкой около 300 сом/час, и задача «сделать кнопку брони столика чуть
крупнее» превращается в детектив: 35–40 минут уходит на то, чтобы найти нужный из семи похожих
классов и убедиться, что правка не «зацепит» точно такую же кнопку в другом разделе сайта.
Пятиминутная по сути правка обходится студии почти в 200 сом и полчаса чужого рабочего времени — а
таких мелких правок за месяц набирается пара десятков. С утилитарным CSS та же задача решается прямо
в разметке — `p-3` на `p-4` — без похода в отдельный файл и без риска зацепить чужой код: класс
`p-4` в этом месте касается только этого элемента. Именно поэтому junior-специалист на первой неделе
в команде может сразу править интерфейс уверенно — сломать что-то далеко от места правки утилитой
почти невозможно.
</BusinessNote>

именованные классы отлично работают, пока проект маленький и его ведёт один человек, — и ломаются
именно там, где мы только что были: в команде, которая пишет CSS два года подряд. Утилитарный CSS —
третья точка на этом пути, и у неё принципиально другая идея внутри.

## Утилитарный CSS: кирпичики LEGO вместо лепки из глины

Представьте два способа собрать одну и ту же фигурку. Первый — лепка из глины: каждая деталь
создаётся с нуля под конкретную задачу, у неё уникальная форма, и если через месяц понадобится
похожая, но чуть другая деталь, проще вылепить новую, чем аккуратно доработать старую (а старую
трогать страшно — вдруг развалится). Второй способ — LEGO: есть конечный набор стандартных
кирпичиков фиксированных размеров, и из них собирается что угодно, комбинируя уже готовые детали.
Один и тот же кирпичик 2×4 используется в сотне разных моделей — и это не убожество, а сила системы.

Классический CSS с именованными классами по сути ближе к лепке: `.card-header-title-red` — деталь,
вылепленная один раз под одно конкретное место. Утилитарный CSS — набор кирпичиков LEGO: `p-4`,
`flex`, `gap-2`, `text-xl`, `rounded-lg` — фиксированный набор маленьких классов одного действия, из
которых собирается любой интерфейс прямо в разметке, без лепки нового куска глины под каждую
карточку.

Практически это выглядит так — та же кнопка, тот же результат, разный способ его получить:

```html
<!-- Именованный класс: имя придумано, стили — в отдельном файле -->
<button class="card-header-title-red">Скидка</button>
```

```html
<!-- Утилиты: имя не нужно, стили — тут же, в разметке -->
<button class="p-4 flex gap-2 text-xl rounded-lg bg-red-600 text-white">Скидка</button>
```

<Callout title="«Утилита» — это просто одно CSS-свойство под коротким именем">
`p-4` не философия, а буквально `padding: 16px`. Ничего магического — просто кто-то заранее сделал
словарь коротких имён на самые частые CSS-свойства и значения, чтобы не изобретать их каждый раз
заново.
</Callout>

## Как читать утилиты: таблица соответствий Tailwind и обычного CSS

Учить Tailwind — это в первую очередь учиться **читать** короткие имена, а не программировать заново.
Вот словарь, который закрывает большую часть повседневной вёрстки:

| Утилита | Что делает | Эквивалент в обычном CSS |
| --- | --- | --- |
| `p-4` | паддинг со всех сторон | `padding: 16px;` |
| `px-6` | паддинг слева и справа (x = horizontal) | `padding-left: 24px; padding-right: 24px;` |
| `mt-2` | внешний отступ сверху | `margin-top: 8px;` |
| `flex` | включает flex-контейнер | `display: flex;` |
| `items-center` | выравнивание по поперечной оси | `align-items: center;` |
| `justify-between` | распределение по главной оси | `justify-content: space-between;` |
| `text-sm` | размер шрифта помельче | `font-size: 14px;` |
| `font-bold` | жирное начертание | `font-weight: 700;` |
| `bg-blue-600` | цвет фона из палитры | `background-color: #2563eb;` |
| `text-white` | цвет текста | `color: #ffffff;` |
| `rounded-lg` | скругление углов | `border-radius: 8px;` |
| `border` | рамка в 1px | `border-width: 1px;` |

<Callout title="Узнали flex, items-center, justify-between?">
Это не новый язык — это ровно та же модель Flexbox из лекции 02: `display: flex` включает контейнер,
`align-items` двигает по поперечной оси, `justify-content` — по главной. Tailwind не придумывает
новую вёрстку, он сокращает запись той, что вы уже знаете.
</Callout>

Хвостик `-600`, `-lg`, `-sm` у некоторых утилит — не случайные слова, а шаг по заранее заданной
шкале: цвета идут от `50` (почти белый) до `900` (почти чёрный) с шагом в сто, размеры — от `xs` до
`2xl`. Не нужно помнить весь список наизусть — достаточно понимать принцип «чем больше число, тем
сильнее эффект», а точное значение легко найти в документации за десять секунд.

Проверьте эквивалентность вживую: слева — карточка на именованных классах, справа — та же карточка на
утилитах. В реальном проекте класс `.p-4` писать самому не нужно — его генерирует сборка Tailwind по
конфигу; здесь, в учебной песочнице, мы прописали такие классы вручную, чтобы увидеть, из чего
складывается результат:

## Шкала отступов: та же сетка 8pt, только с шагом вдвое мельче

В лекции 12 разбирали сетку 8pt: дизайнеры в Figma берут отступы кратными 8 — 8, 16, 24, 32 — чтобы
интерфейс выглядел ритмично и не приходилось выбирать между 13 и 15 пикселями. У шкалы отступов
Tailwind ровно та же идея, только шаг мельче — числа кратны 4 пикселям, то есть та самая сетка 8pt,
поделенная пополам ради более гибких промежуточных значений:

| Класс | В пикселях | В rem |
| --- | --- | --- |
| `p-1` | 4px | 0.25rem |
| `p-2` | 8px | 0.5rem |
| `p-3` | 12px | 0.75rem |
| `p-4` | 16px | 1rem |
| `p-6` | 24px | 1.5rem |
| `p-8` | 32px | 2rem |

Число в имени класса — это позиция на шкале, а не пиксели напрямую: `p-4` не потому что «4 пикселя»,
а потому что это четвёртый шаг шкалы, который равен 16px. Та же логика работает у `m-*` (margin),
`gap-*`, `w-*` (ширина) и `h-*` (высота) — единая шкала отступов используется буквально везде, где
нужно расстояние.

<Callout title="Почему это не «магические числа»">
Как и в Figma из лекции 12, конечный набор шагов — это фича, а не ограничение: дизайнер и
разработчик физически не могут выбрать «на глаз» 13px вместо 12px, потому что такого шага в шкале
попросту нет. Меньше решений — быстрее работа и ровнее интерфейс.
</Callout>

## Состояния и адаптивность через префиксы: hover:, focus:, md:

Все утилиты выше — это только базовое, «всегда включённое» состояние. Реальный интерфейс так не
живёт: кнопка должна темнеть под курсором, получать видимую рамку при переходе табом (вспомните
`:focus-visible` из лекции 14), а раскладка — перестраиваться на широком экране. Такие утилиты можно
**включать по условию** через префикс перед именем класса, через двоеточие:

```html
<button class="bg-blue-600 hover:bg-blue-700 focus:ring text-white p-4 flex flex-col md:flex-row">
  Оформить заказ
</button>
```

| Запись | Когда действует |
| --- | --- |
| `bg-blue-600` | всегда — это база |
| `hover:bg-blue-700` | только пока курсор мыши наведён на элемент |
| `focus:ring` | только когда элемент получил фокус — клавиатурой (Tab) или кликом |
| `md:flex-row` | только на экранах шириной от 768px и шире |

Префикс — это ровно то же условие, которое вы уже писали руками: `hover:` заворачивает правило в
псевдокласс `:hover`, `focus:` — в `:focus`, а `md:` — в медиазапрос `@media (min-width: 768px)`,
слово в слово тот брейкпоинт, что был отправной точкой в лекции 04. И база в этой записи, как и там,
пишется **без префикса** и рассчитана на телефон — Tailwind тоже mobile-first, префиксы только
**добавляют** правила для более широких экранов, а не отрезают лишнее от десктопа.

<Callout title="focus: — не необязательная деталь">
70% трафика портала — с телефонов, но оставшиеся пользователи нередко работают с клавиатуры.
Пропущенный `focus:` на кнопке — тот же провал доступности, что и забытый `:focus-visible` в чистом
CSS: элемент теряется для человека, который не пользуется мышью.
</Callout>

## Дизайн-токены: почему тут невозможен «случайный hex»

Утилита `bg-blue-600` печатает не любой синий, а один конкретный `#2563eb` — потому что палитра
цветов, шкала отступов, шрифтов и радиусов заданы один раз в конфиге сборки, а не придумываются на
лету при вёрстке каждого элемента. Это тот же принцип токенов, что разбирали в лекции 12 про Figma:
не «синий #2563eb», а именованный шаг палитры, который переиспользуется одинаково в тысяче мест.

```js
// Примерно так выглядит часть конфига — источник правды для всех классов bg-*, text-*, border-*
colors: {
  blue: { 600: '#2563eb', 700: '#1d4ed8' },
  slate: { 900: '#0f172a' },
}
```

Раз палитра конечна, у разработчика физически нет способа между делом вписать «на глаз» случайный
оттенок синего вместо `bg-blue-600` — разве что сознательно обойти систему (это тоже возможно, и это
один из граничных случаев ниже). Интерфейс получается консистентным не потому, что все в команде
запомнили правильный hex, а потому что неправильный hex вообще не встречается в словаре утилит.

<Callout title="Кстати, именно так свёрстан этот портал">
Правила проекта прямо запрещают произвольные hex-значения в Tailwind-классах — только токены из
`globals.css`. Это не абстрактный пример из учебника, а рабочее правило репозитория, в котором
хранится сама эта лекция.
</Callout>

## За и против: честно

Утилитарный CSS — не бесплатный обед, у него есть настоящая цена, и разумно знать её заранее.

| За утилиты | Против утилит |
| --- | --- |
| Все стили элемента видны в одном месте — не нужно прыгать между HTML и отдельным CSS-файлом | Строка `class` может растянуться на несколько десятков символов — читать плотную разметку сложнее |
| Правка не «ломает» чужой код: `p-4` используется в тысяче мест с одним и тем же смыслом, случайно испортить чей-то компонент почти нельзя | Нет привычных содержательных имён — по одной разметке не всегда понятно, что это «карточка заказа», а не произвольный набор классов |
| Не нужно выдумывать имена — самая недооценённая экономия часов за месяц работы | Систему обозначений нужно один раз выучить: первые дни разработчик буквально сверяется со шпаргалкой |
| Мёртвый CSS не копится: не используете класс в разметке — он не попадёт в сборку | Разметка дублируется: если пять карточек выглядят одинаково, у каждой своя копия длинной строки классов |

Часто это формулируют так: длинный `className` — реальная плата, но взамен вы получаете гарантию,
что правка стиля в одном месте страницы не аукнется в другом, потому что стили физически не
покидают этот `class`. Для маленькой команды на длинной дистанции это почти всегда выгодный обмен;
для разового проекта — не факт, смотрите следующий раздел.

## Когда Tailwind — лишний инструмент

Всё, что написано выше, — не повод тащить Tailwind в любой проект по умолчанию. Инструмент решает
конкретную проблему — рост стилей в команде на длинной дистанции, — и там, где этой проблемы нет, он
добавляет работы, а не убирает её.

Представьте страницу-визитку небольшого кафе: один файл `index.html`, от силы 50 строк разметки,
десяток CSS-правил, делает её один человек за вечер и, скорее всего, больше никогда не вернётся её
редактировать. Чтобы завести Tailwind, нужно подключить сборку (даже минимальную), настроить конфиг,
разобраться в именах утилит — и всё это ради файла, который проще и быстрее написать пятью обычными
классами из лекции 01. Здесь «цена входа» выше, чем экономия, а экономия утилит проявляется только
на масштабе.

<Callout title="Простое правило">
Чем больше людей одновременно правят одни и те же стили и чем дольше живёт проект — тем сильнее
выигрыш от утилит. Разовый лендинг на один вечер эту экономию попросту не успевает окупить.
</Callout>

## Граничные случаи: где всё ломается

**Динамическая сборка имени класса в JS.** Компонент карточки красит бейдж по категории: имя класса
собирают на лету строкой вроде «bg-» плюс название цвета из базы данных плюс «-600». На экране
разработчика, где Tailwind ещё не пересобрал стили заново, всё как будто работает. После деплоя
бейдж внезапно белый, будто стиль вообще не подключили. Причина — сборщик Tailwind не выполняет
JavaScript и не знает, чему равна переменная в рантайме: он сканирует исходный код в поисках
буквальных, целиком написанных строк классов, и то, что не встретилось текстом, в итоговый CSS не
попадает. Правильно — держать заранее прописанный полный список всех возможных классов (объект-словарь
«категория → готовый класс») либо явно вносить нужные классы в safelist конфигурации, чтобы сборщик
увидел их текстом.

**Конфликт утилит в одном className.** На одном элементе одновременно стоят `p-2` и `p-4`:
разработчик увеличивал отступ, дописал новый класс, не убрав старый, — и в разных местах интерфейса
у одинаковой на вид карточки то паддинг 8px, то 16px. Причина — у обоих классов одинаковая
специфичность (один класс — 10 очков по каскаду из лекции 01), поэтому выигрывает не тот класс, что
написан правее в строке `class`, а тот, чьё правило стоит **ниже** в самом собранном CSS-файле, — а
этот порядок определяет сборщик, а не порядок символов в атрибуте. Правильно — не копить одноимённые
утилиты одного и того же свойства на одном элементе: убирать старый класс перед добавлением нового,
а не дописывать поверх.

**Длиннющий повторяющийся className на десяти карточках.** Один и тот же километровый набор классов
скопирован на десять карточек товара. Через месяц понадобилось у всех сразу увеличить радиус
скругления — и правку вносят в десяти местах руками, а одну карточку неизбежно забывают. Причина —
утилитарный CSS избавляет от имён классов, но не от дублирования разметки: длинная строка классов,
скопированная как текст, нигде не хранит память о том, что все десять карточек — «одно и то же».
Правильно — как только один и тот же набор утилит повторяется больше двух-трёх раз, выносить его в
компонент (`ProductCard`) с одним общим набором классов внутри, а не копипастить строку по всей
разметке.

**Произвольный hex вне палитры.** Дизайнер прислал точный hex для баннера акции, разработчик тут же
вписал его прямо в разметку через `bg-[#3c8dbc]` — синтаксис произвольного значения в квадратных
скобках — и получил нужный оттенок за одну правку. Через полгода на сайте три похожих, но чуть
разных оттенка синего: тот самый акционный hex, обычный `bg-blue-600` и ещё один hex с другой
страницы. Причина — произвольное значение обходит палитру конфигурации, ради которой утилитарный CSS
вообще существует: оно не связано ни с одним токеном и не подтянется, если бренд поменяет основной
цвет. Правильно — заводить новый оттенок в конфиге как именованный токен дизайн-системы (как в
лекции 12), а не вписывать hex-код точечно, даже если «это только один баннер».

**Забытый мобильный вариант.** Разработчик открыл макет сразу на десктопе, написал `md:flex-row`,
`md:gap-6`, и на широком экране всё выглядит отлично. На телефоне блоки наползают друг на друга,
потому что базовых, непрефиксованных классов раскладки на элементе попросту нет. Причина —
mobile-first, как и в лекции 04, означает, что база без префикса обязана сама быть рабочей мобильной
раскладкой; `md:` только **добавляет** правила поверх, а не создаёт раскладку с нуля. Если базовых
классов нет вообще, на узком экране элемент остаётся с тем, что дал браузер по умолчанию. Правильно —
всегда сначала писать непрефиксованные классы для телефона (`flex flex-col gap-4`), и только потом
добавлять `md:`-варианты для более широких экранов.
