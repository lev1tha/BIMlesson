## Введение

В лекции про свой HTTP-сервер на Node вы уже написали настоящий, рабочий API для магазина «Тянь-Шань
Электроникс»: сервер слушал порт, отвечал на GET и POST, возвращал JSON. Всё работало — и этого было
достаточно, пока с сервером разговаривал только один человек: вы сами, из консоли браузера. Но настоящий
интерфейс сервера почти никогда не остаётся личным экспериментом одного разработчика.

Представьте более реалистичную ситуацию. В компании есть мобильное приложение — его пишет команда из
трёх человек в отдельном офисе, а то и в другом городе. Есть сайт — его собирает фронтенд-команда. И
есть сервер — его код видит только бэкенд-команда. Все три команды физически не сидят рядом и не могут
созваниваться по каждому вопросу вроде «а что вернёт сервер, если товара нет на складе?». Единственное,
что у них есть общего, — сам API: набор адресов, методов и форматов ответов. Если этот набор
спроектирован небрежно, три команды тратят часы на переписку просто чтобы понять друг друга. Если
спроектирован по понятным правилам — новый разработчик открывает список эндпоинтов и, не задав ни
одного вопроса, понимает, как получить список товаров и как оформить заказ.

**API** (Application Programming Interface, «программный интерфейс приложения» — уже встречался в лекции
про асинхронность и fetch) — это и есть тот самый договор. Сегодня мы смотрим на него со стороны того,
кто этот договор пишет: не как потребитель чужого API дёргает fetch, а как автор своего API формулирует
правила так, чтобы ими было приятно пользоваться, не читая многостраничную инструкцию и не звоня автору
каждый час.

<BusinessNote title="Сколько стоит неряшливый API">
Мобильное приложение и сайт интернет-магазина в Бишкеке разрабатывают две разные подрядные команды.
Бэкенд-разработчик называет эндпоинты как придётся: где-то `/getProduct`, где-то `/order/new`, где-то
статус 200 приходит даже при ошибке, а текст «нет на складе» лежит просто в теле без отдельного кода.
Каждая новая фича превращается в переписку: разработчик мобильного приложения раз в один-два дня пишет
в чат «а как понять, что заказ не прошёл?» и ждёт ответа несколько часов, прежде чем продолжить работу.
При ставке фронтенд-разработчика около 400 сом/час и трёх таких простоях в неделю по 40 минут — это
лишние 2 000 сом в неделю, около 8 000 сом в месяц, и это без учёта сорванных сроков и раздражения
обеих команд. Чёткий контракт API стоит нескольких часов проектирования один раз — и экономит эти
созвоны на всё время жизни проекта.
</BusinessNote>

**Что вы узнаете:**

- как называть адреса ресурсов существительными и подбирать метод запроса: GET, POST, PUT, PATCH, DELETE
- как статус-коды и единый формат ошибки делают ответ понятным ещё до чтения тела
- как просить у сервера не всё, а нужное, через query-параметры
- как менять формат API через версии и не сломать чужое мобильное приложение
- почему кнопка «повторить платёж» страшна и при чём тут идемпотентность
- как API узнаёт, кто стучится, и почему документация — часть продукта

Пригодится из прошлых лекций: «Свой HTTP-сервер на Node», «Асинхронность и API», «Как открывается сайт: DNS, HTTP и HTTPS», «Публикация сайта».

## Ресурсы: адрес — это существительное, а не команда

REST (Representational State Transfer — расшифровку можно не запоминать, важнее сама идея) держится на
одном простом соглашении: адрес называет **ресурс** — вещь, сущность, с которой работаем: товары,
заказы, пользователей. Не действие над ней. Действие — это отдельно, и у него есть свой способ появиться
в запросе, о нём в следующем разделе.

<Callout title="Аналогия: меню ресторана, а не рецепт для кухни">
API — это меню, а не разрешение зайти на кухню. В меню написано «Плов» и «Лагман» — блюда, то есть
ресурсы. Вы не пишете официанту инструкцию «сходиНаКухнюИПожарь» — вы называете блюдо, а официант, то
есть метод запроса, сам решает, что с ним сделать: принести, заменить, убрать со стола. Официант — это
глагол, блюдо — существительное. REST требует того же от адреса: `/products` — это ресурс «товары», и
разбираться, что с ним делать, должен метод запроса, а не сам адрес.
</Callout>

Отсюда — три практических правила, по которым сразу видно чужой хороший (или не очень) API:

1. **Ресурсы называют существительными во множественном числе.** `/products`, `/orders`, `/users` — а
   не `/getProducts` или `/product`. Множественное число — потому что по этому адресу лежит коллекция, а
   не один-единственный экземпляр.
2. **Конкретный элемент коллекции получает свой адрес через идентификатор в пути.** Товар с номером 8 —
   это `/products/8`, а не `/products?id=8`. Идентификатор в пути читается как «конкретная вещь из этой
   полки», а не как случайный фильтр среди многих.
3. **Вложенность в адресе повторяет вложенность в жизни.** Позиции внутри конкретного заказа — это
   `/orders/42/items`: сначала заказ 42, внутри него — список позиций. Адрес читается сверху вниз ровно
   так же, как вы бы объяснили эту структуру человеку на словах.

```text
/products                  — коллекция всех товаров
/products/8                — товар номер 8
/orders                    — коллекция всех заказов
/orders/42                 — заказ номер 42
/orders/42/items           — позиции внутри заказа 42
/orders/42/items/3         — конкретная позиция номер 3 внутри заказа 42
```

Плохой пример почти всегда легко узнать по глаголу в адресе: `/getUserOrders`, `/createNewOrder`,
`/deleteProductById`. Каждый такой адрес пытается сделать работу, которая по правилам REST принадлежит
методу запроса, — и мы как раз подошли к тому, что это за методы.

## Методы: глаголы, которые прилагаются к существительным

Если адрес — существительное, то метод запроса (тот самый «глагол» из лекции про DNS и HTTP) — это то,
что с этим существительным нужно сделать. У REST есть негласный контракт на пять основных глаголов:

| Метод | Что делает | Свойства | Пример для магазина |
| --- | --- | --- | --- |
| **GET** | читает данные, ничего не меняя | безопасный (safe) — без побочных эффектов; можно кэшировать | `GET /v1/products/8` — карточка товара |
| **POST** | создаёт новую сущность | каждый вызов создаёт новую запись | `POST /v1/orders` — оформить новый заказ |
| **PUT** | заменяет ресурс целиком | нужно прислать все поля, даже не изменившиеся | `PUT /v1/products/8` — переписать карточку товара полностью |
| **PATCH** | меняет часть ресурса | присылаете только то, что реально меняется | `PATCH /v1/products/8` — поменять только цену |
| **DELETE** | удаляет ресурс | результат — ресурса больше нет | `DELETE /v1/cart/items/8` — убрать товар из корзины |

**Безопасный** для GET значит не «защищённый от взлома», а «не имеющий побочных эффектов»: сколько раз
ни открой карточку товара, на складе и в базе ничего не изменится. Именно поэтому GET можно спокойно
**кэшировать** (запомнить ответ и не спрашивать сервер заново) — открыли то же самое, получили тот же
самый ответ. POST закэшировать так нельзя в принципе: два одинаковых POST должны, по умолчанию, породить
два разных результата — важная деталь, к которой мы вернёмся в разделе про идемпотентность.

<Callout title="PUT против PATCH: целиком или по кусочку">
Путаница между PUT и PATCH — частая ошибка на собеседованиях и в реальном коде. PUT — это «вот вам
полностью новая версия объекта, замените старую этой»: если в запросе не прислать поле складОстаток,
многие серверы честно обнулят его, ведь вы прислали объект без этого поля. PATCH — это «поменяйте
только то, что я прислал, остальное не трогайте»: тело запроса с одним полем ценаСом обновит только
цену, остальные поля карточки товара останутся как были. Если сомневаетесь, что выбрать для формы
«редактировать одно поле в интерфейсе», — почти всегда правильный ответ PATCH.
</Callout>

Разберём пример запроса и ответа для оформления заказа — того самого действия, которое в лекции про
Node вы уже писали руками через `req.on('data', ...)`:

```json
// Запрос: POST /v1/orders
{
  "товар": "Наушники беспроводные",
  "количество": 1,
  "ценаСом": 2500,
  "адресДоставки": "Бишкек, ул. Киевская, 95"
}
```

```json
// Ответ: 201 Created
{
  "id": 4521,
  "статус": "принят",
  "итогоСом": 2500
}
```

Обратите внимание: тело запроса не содержит `id` — его придумывает сервер, а не клиент. Это ещё одно
негласное правило REST: **сервер — единственный источник истины для идентификаторов**. Клиент никогда не
диктует серверу, под каким номером сохранить новую запись.

## Статус-коды: ответ говорит сам за себя, ещё до чтения тела

В лекции «Как открывается сайт: DNS, HTTP и HTTPS» вы уже встречали группы кодов 2xx, 3xx, 4xx и 5xx в
общем виде. Для собственного API эти группы — не абстракция, а конкретное решение, которое вы
принимаете в каждом обработчике: что записать в `res.statusCode`, прежде чем вызвать `res.end()`.

| Код | Название | Когда использовать в своём API |
| --- | --- | --- |
| **200** | OK | GET или PATCH прошли успешно, в ответе есть тело с данными |
| **201** | Created | POST успешно создал новую запись — товар, заказ, пользователя |
| **204** | No Content | Успех, но возвращать нечего: DELETE прошёл, тело ответа пустое |
| **400** | Bad Request | Запрос кривой: не хватает поля, неверный формат, отрицательное количество товара |
| **401** | Unauthorized | Клиент вообще не представился: нет токена или ключа доступа |
| **403** | Forbidden | Клиент представился, но именно ему сюда нельзя |
| **404** | Not Found | Такого товара, заказа или маршрута не существует |
| **409** | Conflict | Запрос логически противоречит текущему состоянию: товар уже лежит в корзине |
| **500** | Internal Server Error | Сервер сам упал — вина не клиента, а бэкенда |

Три пары легко перепутать, если не проговорить разницу вслух отдельно.

<Callout title="401 против 403: не представился или представился, но нельзя">
Разница ровно та же, что на проходной бизнес-центра. **401** — это «покажите пропуск»: человек вообще
не предъявил документ или предъявил просроченный, сервер не знает, кто перед ним. **403** — это «пропуск
у вас на руках, вижу, кто вы, но в эту комнату вам нельзя»: сервер прекрасно опознал клиента и вежливо
отказал по правам доступа. Спутать их — значит вместо честного «войдите в аккаунт» показать пользователю
запутывающее «доступ запрещён», хотя проблема ровно в том, что он не залогинен.
</Callout>

204 намеренно не несёт тело ответа, а не по забывчивости: если возвращать после DELETE нечего, незачем
тратить байты трафика на пустой объект. 409 стоит отдельно от 400 — запрос сам по себе абсолютно
корректен по формату (все поля на месте, типы верные), но противоречит текущему состоянию данных:
`POST /v1/cart/items` с товаром, который уже лежит в корзине этого покупателя, — это не «кривой» запрос,
а именно конфликт с тем, что сервер уже знает.

Отдельное правило — для 400: мало написать «400, отказ». Тело ответа обязано объяснять, что именно не
так, иначе разработчик на другом конце будет гадать, какое из пятнадцати полей запроса сервер счёл
неверным. Как выбрать нужный код на практике, если в обработчике произошла ошибка, удобно свести в одну
схему:

## Формат ошибки: одно сообщение для человека, один код для программы

Хорошая ошибка отвечает сразу двум читателям. Разработчику, который сейчас смотрит в консоль и должен за
десять секунд понять, что пошло не так. И коду, который эту ошибку должен молча распознать и показать
пользователю правильный текст на нужном языке, не разбирая руками произвольную фразу.

```json
// Ответ: 400 Bad Request
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "На складе осталось 2 шт., в заказе запрошено 5"
  }
}
```

`message` — то самое человекочитаемое объяснение из правила про 400: не «Bad Request», а именно то, что
разработчик увидит и сразу поймёт. `code` — короткая машинная метка, которая не меняется от языка
интерфейса и не зависит от формулировки: фронтенд проверяет именно `code`, а не сравнивает строки
текста, которые сегодня по-русски, а завтра могут стать по-кыргызски или по-английски.

<Callout title="Почему нельзя проверять ошибку по тексту сообщения">
Если фронтенд сравнивает поле `message` с конкретной фразой, любая правка формулировки (опечатка,
локализация, более вежливый тон) тихо ломает всю логику обработки ошибки на клиенте. `code` специально
придуман так, чтобы никогда не меняться без предупреждения, — это машинный контракт, а `message` можно
менять сколько угодно, ничего не сломав.
</Callout>

## Query-параметры: как просить не всё, а нужное

Адрес ресурса называет «что», а всё, что после знака вопроса, — это «какое именно» и «сколько». Три
типовые задачи query-параметров в любом API со списками:

**Фильтрация** — сузить выборку по условию: `GET /v1/orders?city=Бишкек` вернёт только заказы с
доставкой по Бишкеку, а не по всей стране. **Сортировка** — задать порядок: `GET /v1/orders?sort=-created_at`
означает «по дате создания, в обратном порядке» — минус перед именем поля почти везде читается как
«убывание». **Пагинация** — отдать не всё сразу, а порцию: `GET /v1/orders?page=2&limit=20` — вторая
страница по 20 записей.

<Callout title="Зачем пагинация нужна не только в байтах, но и в деньгах">
Представьте эндпоинт `GET /v1/orders` без пагинации на магазине, который работает три года и накопил
100 000 заказов. Мобильное приложение на слабом телефоне пытается получить и разобрать весь этот список
одним ответом: сервер тратит секунды на сборку такого JSON, сеть — секунды на передачу нескольких
мегабайт, а телефон покупателя на устаревшем Android рискует просто зависнуть или упасть по нехватке
памяти при разборе такого ответа. Результат — не «медленно», а полностью нерабочий экран заказов для
части аудитории. Пагинация — не оптимизация про запас, а разница между работающим и неработающим
приложением при реальном объёме данных.
</Callout>

Есть два способа считать страницы. **Страничная пагинация** (`page` и `limit`, как в примере выше) —
самая простая для понимания и для интерфейса с номерами страниц, но плохо себя ведёт, если между
запросами в список добавляются новые записи: то, что было на странице 2, может незаметно съехать на
страницу 3. **Курсорная пагинация** — вместо номера страницы отдаёт «курсор», метку последней увиденной
записи, и следующий запрос просит «всё, что после этой метки»: список не съезжает, даже если данные
постоянно меняются, но зато нельзя одним кликом перепрыгнуть сразу на пятнадцатую страницу. Для ленты
заказов, которая меняется каждую минуту, курсор надёжнее; для каталога товаров, который меняется редко,
простого `page` вполне достаточно.

## Версии API: как поменять формат и не сломать чужой телефон

Что-то в API рано или поздно приходится менять: добавить обязательное поле, переименовать поле,
изменить структуру ответа. Проблема в том, что на телефонах пользователей уже стоит мобильное
приложение, написанное под старый формат, — и это приложение не обновляется само в момент, когда вы
задеплоили новый бэкенд.

<Callout title="Месяцы, а не секунды">
Сайт обновляется в момент деплоя — все посетители через минуту видят новую версию, вы уже разбирали
это в лекции про автодеплой. Мобильное приложение так не работает: новую версию нужно сначала выпустить
в App Store и Google Play, дождаться модерации, а затем ждать, пока пользователи сами захотят
обновиться. Часть аудитории месяцами живёт на старых версиях приложения просто потому, что
автообновления выключены или телефон редко подключается к Wi-Fi. Если бэкенд-команда в одностороннем
порядке поменяет формат ответа, эти пользователи не увидят ошибку — экран заказов у них просто молча
перестанет работать, а разбираться, почему, техподдержка будет по одному обращению за раз.
</Callout>

Решение — **версионирование**: адрес API включает номер версии, например `/v1/orders`. Пока часть
аудитории сидит на старом приложении, сервер продолжает поддерживать `/v1/...` в прежнем виде, а новый,
несовместимый формат ответа выходит по отдельному адресу `/v2/orders`. Старые телефоны продолжают ходить
на `/v1` и ничего не замечают, новые версии приложения переходят на `/v2` в своём темпе. Только когда
статистика показывает, что на `/v1` почти никто не заходит, эту версию можно официально закрыть —
заранее предупредив и обычно оставив несколько месяцев переходного периода.

## Идемпотентность на пальцах: почему «повторить платёж» — страшная кнопка

**Идемпотентность** (звучит страшно, суть простая) — свойство запроса давать один и тот же результат,
сколько раз его ни повтори. `PUT /v1/products/8` с одним и тем же телом можно смело слать хоть пять раз
подряд — товар просто пять раз перезапишется одними и теми же данными, ничего плохого не случится.
`DELETE /v1/orders/42` тоже идемпотентен: после первого вызова заказа уже нет, и повторный вызов просто
ничего не находит — результат «заказа 42 не существует» от повтора не меняется.

С POST всё наоборот: `POST /v1/orders` **не идемпотентен по своей природе** — каждый вызов создаёт новую
запись. Позвать его дважды с одинаковым телом — получить два заказа вместо одного. Именно поэтому кнопка
«Повторить платёж» так пугает: если первый запрос на самом деле прошёл на сервере, а ответ до телефона
покупателя просто не долетел из-за плохой сети, повторное нажатие может списать деньги во второй раз за
один и тот же товар.

<Mermaid
  title="Идемпотентный повтор: тот же заказ, а не дубль"
  chart={`sequenceDiagram
    participant П as Приложение
    participant A as API
    П->>A: POST /orders (ключ идемпотентности a1b2c3)
    A-->>П: 201 Created, id 4521
    П->>A: Ответ не дошёл — повтор POST /orders (тот же ключ a1b2c3)
    A-->>П: 201 Created, id 4521 — тот же заказ, не дубль`}
/>

Спасает **ключ идемпотентности** (idempotency key): клиент сам придумывает уникальную строку для каждой
логической попытки оплаты (например, случайный набор символов, сгенерированный один раз при нажатии
кнопки) и передаёт её в заголовке запроса. Сервер запоминает пары «ключ — результат»: увидев тот же ключ
второй раз, он не создаёт новый заказ, а просто возвращает результат первой попытки. Мобильное приложение
может смело повторять запрос при любом сомнении в сети — сервер сам отфильтрует дубли по ключу.

<BusinessNote title="Цена одного забытого ключа идемпотентности">
Интернет-магазин электроники в Бишкеке принимает оплату картой через платёжный шлюз. При кратковременном
сбое мобильной сети у части покупателей приложение не получает ответ вовремя и повторяет запрос оплаты
без ключа идемпотентности. За месяц таких повторов набирается около 15 двойных списаний на средний чек
3 000 сом — 45 000 сом, которые нужно вручную находить, объяснять в поддержке и возвращать покупателям;
каждый такой возврат занимает у оператора около 20 минут разбирательства. Один ключ идемпотентности в
заголовке запроса убирает эту статью расходов полностью, а не частично.
</BusinessNote>

## Аутентификация обзорно: как API узнаёт, кто стучится

Прежде чем сервер решит, разрешён запрос или нет (вспомните разницу 401 и 403 из раздела про
статус-коды), ему нужно каким-то образом узнать, кто стучится. Для API это почти никогда не логин с
паролем при каждом запросе — вместо этого используют одно из двух:

- **API-ключ в заголовке** — простая строка, которую сервис выдаёт один раз при регистрации приложения:
  заголовок вида `X-API-Key: a1b2c3d4e5`. Подходит для серверных интеграций, где ключ хранится в
  переменных окружения (как в лекции про деплой), а не в коде, который увидит браузер.
- **Bearer-токен** — более гибкий вариант для входа обычного пользователя: после успешного логина сервер
  выдаёт токен, а дальше каждый запрос несёт заголовок `Authorization: Bearer` и сам токен следом.
  «Bearer» дословно значит «предъявитель» — как проездной без фото: у кого токен, тот и прошёл.

<Callout title="Токен — только в заголовке, никогда в адресе">
Соблазн передать токен прямо в адресе — `GET /v1/orders?token=a1b2c3` — понятен: короче писать, легче
проверить вручную прямо в браузере. Но весь адрес запроса целиком оседает в логах сервера, в истории
браузера и в логах промежуточных прокси-серверов, а исправить это задним числом невозможно — ровно как
и с ключом, случайно попавшим в git-историю из лекции про деплой. Это тот же принцип, что и в лекции про
безопасность фронтенда: секрет обязан жить там, где его не увидит никто лишний, а адресная строка — одно
из самых людных мест в интернете. Правильное место токена — только заголовок `Authorization`, никогда
query-параметр адреса.
</Callout>

## Документация — часть продукта, а не сноска на потом

Даже идеально спроектированный API бесполезен, если единственный способ узнать, как им пользоваться, —
писать автору лично. Хорошее описание эндпоинта отвечает на все вопросы заранее, до первого запроса:

```text
GET /v1/orders/4521
Возвращает заказ по идентификатору.

Параметры пути:
  id (число, обязателен) — идентификатор заказа

Заголовки:
  Authorization: Bearer <токен>  — обязателен

Успех — 200 OK:
  { "id": 4521, "статус": "в пути", "итогоСом": 2500 }

Ошибки:
  401 — токен не передан или недействителен
  404 — заказа с таким id не существует, либо он принадлежит другому покупателю
```

Разберите этот пример по частям: метод и путь указаны одной строкой, объяснено, что означает
идентификатор в пути, названы обязательные заголовки, показан пример успешного ответа и — что чаще
всего забывают — перечислены коды ошибок с объяснением каждого, а не просто общее «могут быть ошибки».
Разработчик другой команды, увидев такое описание один раз, обращается к автору API только в
действительно нестандартных случаях, а не за расшифровкой каждого поля.

### Задание 1: спроектируй 5 эндпоинтов на бумаге

Сервис доставки цветов «Флора.kg» нанял вас спроектировать API. Пользователи должны уметь: посмотреть
каталог букетов, посмотреть конкретный букет, оформить заказ на доставку, проверить статус своего заказа
и отменить заказ, если курьер ещё не выехал. Прежде чем смотреть образец ниже — возьмите лист бумаги
(или текстовый файл) и запишите свои пять адресов с методами и ожидаемыми кодами ответа. Вопросы, которые
стоит задать себе для каждого: существительное или глагол в адресе? Где идентификатор — в пути или в
query? Какой код при успехе, какой при ошибке?

Образцовый ответ:

| Метод | Путь | Что делает | Успех | Возможная ошибка |
| --- | --- | --- | --- | --- |
| GET | `/v1/bouquets` | список всех букетов в каталоге | 200 | — |
| GET | `/v1/bouquets/12` | карточка одного букета | 200 | 404 — такого букета нет |

Сверьте со своим вариантом: если вместо `/v1/orders/930` у вас получилось что-то вроде

### Задание 2: пощупайте настоящее публичное API

Откройте в браузере адрес `https://jsonplaceholder.typicode.com/posts?userId=1` — это открытый учебный
API, не требующий ни ключа, ни регистрации. *Ожидаемый результат:* страница покажет сырой JSON-массив —
несколько объектов с полями `userId`, `id`, `title`, `body`. Обратите внимание на форму адреса: `posts` —
существительное во множественном числе, а `userId=1` — query-параметр фильтрации, ровно то, что
разбиралось в разделе про query-параметры.

Теперь откройте консоль разработчика (F12 → Console) на любой странице и выполните тот же запрос через
`fetch` — тем самым методом из лекции про асинхронность и API:

```js
fetch('https://jsonplaceholder.typicode.com/posts?userId=1')
  .then(ответ => ответ.json())
  .then(посты => console.log('Постов у пользователя 1:', посты.length));
```

*Ожидаемый результат:* в консоли появится число — сколько записей вернул сервер именно для пользователя
с id 1, а не общий счётчик всех постов на сервере. Замените `1` на `2` и запустите снова: число должно
измениться — наглядное доказательство, что фильтрация через query-параметр реально работает, а не просто
существует в теории.

### Задание 3: найдите ошибку в трёх «плохих» эндпоинтах

Ниже — три примера, которые встречаются в учебных и даже в боевых проектах. Для каждого — в чём проблема
и как переписать правильно.

- **`GET /getUser?id=5`.** Проблема: в адресе спрятан глагол `get`, хотя это уже целиком обязанность
  метода GET, — а идентификатор пользователя вынесен в query, хотя это главный, обязательный признак
  конкретной сущности, а не необязательный фильтр. Правильно: `GET /v1/users/5`.
- **`DELETE /products/all`.** Проблема: `all` — это не идентификатор конкретного товара, а
  замаскированная под путь опасная команда «удали вообще всё». Один случайно скопированный адрес, один
  автоматический скрипт мониторинга, один робот — и весь каталог обнулён без возможности отличить это
  действие от обычного удаления одной позиции. Правильно: массовое удаление либо не поддерживать вовсе,
  либо оформить отдельным явным маршрутом с телом запроса и обязательным подтверждением, а не адресом,
  который можно случайно открыть в браузере.
- **`GET /orders/create`.** Проблема: GET обязан быть безопасным методом без побочных эффектов (это
  разбиралось в разделе про методы), а `create` в адресе намекает, что запрос всё-таки что-то создаёт.
  Если такую ссылку случайно откроет предзагрузчик браузера, антивирус или поисковый робот, у магазина
  начнут появляться пустые заказы из ниоткуда. Правильно: `POST /v1/orders` — создание есть только там,
  где для этого специально предназначен метод.

## Граничные случаи: где всё ломается

- **GET, который на самом деле удаляет данные.** Ситуация: в админ-панели ссылка «Удалить» реализована
  как обычный `GET /admin/products/8/delete`, потому что так проще всего повесить её на HTML-ссылку без
  формы. Что происходит: поисковый робот или автоматический предзагрузчик ссылок в браузере проходит по
  всем ссылкам страницы подряд, включая эту, — и через одну ночь половина каталога оказывается удалённой,
  без единого человека за клавиатурой. Почему: GET по контракту обязан быть безопасным — ничего не
  меняющим, и весь интернет, включая роботов, рассчитывает именно на это без исключений. Как правильно:
  любое действие с побочным эффектом — только через POST, PUT, PATCH или DELETE, а на кнопку в
  интерфейсе вешать реальный запрос нужным методом, а не ссылку-переход.
- **POST оплаты повторился по таймауту — двойное списание.** Ситуация: покупатель на медленном мобильном
  интернете нажимает «Оплатить», ответ сервера не успевает прийти за отведённое время, приложение
  решает, что запрос не дошёл, и отправляет `POST /v1/payments` ещё раз. Что происходит: первый запрос
  на самом деле уже списал деньги и создал платёж, второй запрос без дополнительной защиты создаёт
  второй, отдельный платёж на ту же сумму. Почему: POST не идемпотентен по своей природе — сервер не
  может сам понять, что это «тот же самый» платёж, а не два разных. Как правильно: генерировать ключ
  идемпотентности один раз на попытку оплаты и передавать его при каждом повторе — сервер возвращает
  результат первой попытки вместо создания дубля.
- **Список без пагинации падает на реальном объёме данных.** Ситуация: `GET /v1/orders` в учебном
  проекте на пяти тестовых заказах работал прекрасно, а через год работы магазина, когда заказов
  накопилось 50 000, тот же эндпоинт на реальных данных либо отвечает по 20–30 секунд, либо роняет
  приложение покупателя при попытке разобрать многомегабайтный JSON. Почему: тестовые данные никогда не
  отражают реальный масштаб, а объём ответа растёт линейно вместе с бизнесом — то, что не болело на
  старте, обязано заболеть при росте. Как правильно: пагинацию закладывать в дизайн эндпоинта с первого
  дня, а не добавлять по факту первой жалобы на медленную загрузку.
- **Токен в query-параметре засветился в логах и истории браузера.** Ситуация: разработчик для простоты
  тестирования передаёт токен доступа прямо в адресе — `GET /v1/orders?token=a1b2c3` — и решение
  случайно доезжает до боевой версии приложения. Что происходит: полный адрес запроса оседает в логах
  сервера, в логах промежуточных прокси и в истории браузера на устройстве пользователя — в отличие от
  тела запроса и части заголовков, которые в стандартных логах доступа обычно не сохраняются. Почему:
  URL по всему пути от браузера до сервера проходит через системы, которые исторически не считались
  местом хранения секретов, и никто не проектировал их с расчётом на такую нагрузку ответственности. Как
  правильно: токен — только в заголовке `Authorization`, никогда в адресе запроса.
- **Поле в ответе переименовали без новой версии — старые приложения падают молча.** Ситуация:
  бэкенд-команда решает, что поле `ценаСом` звучит неточно, и переименовывает его прямо в `/v1/products`,
  без выпуска `/v2`. Что происходит: старые версии мобильного приложения, ещё не обновлённые у части
  пользователей, продолжают искать прежнее поле в ответе, не находят его и либо показывают пустую цену,
  либо падают целиком — без единого сообщения об ошибке на сервере, ведь с точки зрения HTTP запрос
  прошёл идеально успешно. Почему: смена формата ответа — это разрыв контракта, который сервер не имеет
  права объявлять в одностороннем порядке для уже выпущенных клиентов. Как правильно: несовместимые
  изменения формата — только через новую версию адреса, старую поддерживать, пока ей реально кто-то
  пользуется.
- **200 OK с текстом «ошибка» внутри тела ответа.** Ситуация: платёжный шлюз отвечает статусом 200 на
  любой запрос независимо от результата, а сам результат — успех это или отказ банка — записан отдельным
  полем внутри JSON-тела ответа. Клиентский код проверяет только `response.ok` (мы разбирали эту
  привычку в лекции про fetch) и, увидев успешный HTTP-статус, показывает покупателю «Оплата прошла»,
  хотя банк реально отклонил платёж. Почему: код ответа описывает только то, что случилось на уровне
  транспорта («сервер сумел ответить»), а не то, что случилось в бизнес-логике внутри — мы уже видели
  ровно эту ловушку в лекции про DNS и HTTP на примере мониторинга, здесь она же встречается на уровне
  кода фронтенда. Как правильно: даже при успешном HTTP-статусе разбирать содержимое тела ответа и
  ориентироваться на бизнес-поле результата, а не только на код состояния.
