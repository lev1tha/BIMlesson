В Кыргызстане до 70% визитов на сайты — с телефонов, причём чаще всего это бюджетные
Android-смартфоны с экраном шириной 360 CSS-пикселей. А верстают сайты обычно на большом мониторе
шириной 1920. Если об этой разнице не подумать, на смартфоне сайт превращается в «крошечные буквы,
которые надо растягивать пальцами». **Адаптивная вёрстка** (англ. *responsive design*) — это набор
приёмов, благодаря которым одна и та же страница сама подстраивается под ширину любого экрана.

<BusinessNote>
Интернет-магазин на домене shop.kg делает 2 000 000 сом выручки в месяц, и 70% заказов приходит
с телефонов — это 1 400 000 сом. Если мобильная версия неудобна (мелкий текст, кнопка «Купить»
не попадает под палец) и конверсия на телефонах падает хотя бы вдвое — бизнес недосчитывается
до 700 000 сом ежемесячно. Плюс Google с 2019 года ранжирует сайты по принципу mobile-first
indexing: робот смотрит в первую очередь на мобильную версию. Плохой адаптив — это одновременно
потерянные заказы сегодня и потерянные позиции в поиске завтра.
</BusinessNote>

## Первый шаг: тег viewport

Небольшая тонкость, которую стоит понять один раз: ширина в CSS считается не в физических
пикселях матрицы, а в **CSS-пикселях**. У телефона с экраном 1080 физических пикселей ширина
для вёрстки — всё равно около 360 CSS-пикселей (браузер укрупняет картинку втрое, иначе текст
был бы нечитаемо мелким). Когда мы говорим «экран 360px» — речь именно о CSS-пикселях.

Без одной строки в `<head>` телефон покажет сайт «уменьшенной десктопной копией»: отрисует его
как будто на экране шириной 980px и ужмёт. Эта строка говорит браузеру: «рисуй по реальной ширине
устройства»:

```html
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

Она уже стоит почти в каждом шаблоне — но знать, зачем она, обязательно: без неё не работает
ни один приём из этой лекции.

## Относительные единицы вместо жёстких пикселей

Жёсткие `px` не тянутся под экран. Гибкие единицы подстраиваются:

| Единица | Относительно чего | Когда удобно |
| --- | --- | --- |
| `%` | размера родителя | ширина блоков, картинок |
| `rem` | размера шрифта **корня страницы** (по умолчанию 16px) | шрифты, отступы — масштабируются все сразу |
| `em` | размера шрифта **текущего элемента/родителя** | отступы внутри кнопки, привязанные к её шрифту |
| `vw` / `vh` | 1% ширины/высоты окна | секции «на весь экран», плавные заголовки |

### em vs rem: в чём разница и почему rem безопаснее

Обе единицы «относительные», но точка отсчёта разная — и это меняет всё:

- `1rem` — всегда от корневого размера шрифта страницы. По умолчанию `1rem = 16px`,
  `1.5rem = 24px`, `2rem = 32px`. Предсказуемо в любом месте документа.
- `1em` — от размера шрифта родителя (а для отступов — от шрифта самого элемента). Значения
  **накапливаются** при вложенности.

Числовой пример накопления. Пусть у вложенных списков стоит `li { font-size: 1.2em; }`:

```text
корень:            16px
список 1 уровня:   16 × 1.2 = 19.2px
список 2 уровня:   19.2 × 1.2 ≈ 23px
список 3 уровня:   23 × 1.2 ≈ 27.6px  ← шрифт «разъехался» сам собой
```

С `rem` такого не бывает: `1.2rem` на любом уровне — это ровно `19.2px`. Поэтому практическое
правило простое: **шрифты и общие отступы — в rem**, `em` — только когда нужно, чтобы отступ
масштабировался вместе со шрифтом конкретного элемента (например, паддинги кнопки).

Бонус rem: если пользователь со слабым зрением увеличил базовый шрифт в настройках браузера
с 16 до 20px, весь сайт на rem аккуратно вырастет на 25%. Сайт на px — нет.

<Callout title="Правило для картинок">
Одна строка спасает вёрстку на мобильных: `img { max-width: 100%; height: auto; }`. Картинка больше
никогда не «вылезет» за пределы экрана и не сломает раскладку — она ужмётся до ширины контейнера.
</Callout>

## Контейнер контента: приём, без которого лендинг расползается

Обратная проблема адаптивности: на мониторе 2560px строка текста без ограничения растянется
на 200+ символов — читать невозможно (комфортная длина строки — 60–80 символов, подробнее об
этом будет в лекции про типографику). Лечится стандартным паттерном **центрирующего контейнера**:

```css
.container {
  max-width: 1200px;  /* шире этого не растянется */
  margin: 0 auto;     /* оставшееся место делится поровну слева и справа */
  padding: 0 16px;    /* «воздух» у краёв на телефоне */
}
```

Как это работает на разных экранах:

| Ширина окна | Что происходит |
| --- | --- |
| 360px (телефон) | контейнер занимает всю ширину, по 16px отступа у краёв |
| 1200px (ноутбук) | контейнер впритык, поля почти нулевые |
| 1920px (монитор) | контейнер 1200px по центру, по 360px пустых полей с боков |

Этот блок-обёртка есть практически на каждом коммерческом сайте — присмотритесь к любому
лендингу на широком мониторе: контент всегда собран в центральную колонку.

## Брейкпоинты: на каких ширинах «переключать» макет

**Брейкпоинт** (англ. *breakpoint*, точка перелома) — ширина экрана, на которой макет меняется:
колонки складываются, меню сворачивается в «бургер». Отправная точка — типовые диапазоны:

| Брейкпоинт | Какие экраны | Типичные устройства |
| --- | --- | --- |
| 360–479px | базовые телефоны | бюджетные Android (Redmi, Galaxy A) — самые массовые в КР |
| 480–767px | крупные телефоны, телефон «лёжа» | iPhone Pro Max, фаблеты |
| 768–1023px | планшеты | iPad, Android-планшеты |
| 1024–1279px | ноутбуки | типичный рабочий ноутбук |
| 1280px и шире | десктопы | офисные мониторы, Full HD и больше |

<Callout title="Брейкпоинты выбирают по контенту, а не по списку устройств">
Моделей телефонов тысячи, и подгонять вёрстку под каждую бессмысленно. Правильный метод: тяните
окно и смотрите, где макет реально ломается (карточки стали слишком узкими, меню не влезает) —
там и ставьте брейкпоинт. Таблица выше — ориентир для старта, а не закон. На практике большинство сайтов
живёт всего с двумя-тремя брейкпоинтами: примерно 768px и 1024px.
</Callout>

## Медиазапросы: разные стили для разной ширины

**Медиазапрос** (`@media`) применяет стили только при выполнении условия — чаще всего условия
о ширине экрана. Так на телефоне можно сложить колонки в одну, увеличить шрифт, спрятать лишнее:

```css
/* базовые стили — для мобильных */
.cols { display: grid; grid-template-columns: 1fr; }

/* на экранах шире 768px — два столбца */
@media (min-width: 768px) {
  .cols { grid-template-columns: 1fr 1fr; }
}
```

### min-width против max-width: два способа записать одно и то же

Одну и ту же адаптивную шапку можно описать «с двух концов». Сравните:

```css
/* Вариант 1 — mobile-first: база для телефона, min-width ДОБАВЛЯЕТ */
.menu { flex-direction: column; }
@media (min-width: 768px) {
  .menu { flex-direction: row; }
}

/* Вариант 2 — desktop-first: база для десктопа, max-width ОТРЕЗАЕТ */
.menu { flex-direction: row; }
@media (max-width: 767px) {
  .menu { flex-direction: column; }
}
```

Оба варианта дают одинаковый результат. `min-width: 768px` читается как «от 768px и шире»,
`max-width: 767px` — «до 767px включительно». Обратите внимание на несостыковку в единичку:
границы не должны пересекаться, иначе на ровно 768px сработают оба правила. В чужом коде вы
встретите оба стиля, поэтому уметь читать нужно оба.

<Callout title="Mobile-first: почему сегодня пишут от мобильного">
Подход **mobile-first** — сначала стили для узкого экрана, потом через `min-width` добавляют
«улучшения» для широких. Так проще: мобильная версия — самая ограниченная, от неё легче
наращивать, чем «отрезать» лишнее от десктопа. Для аудитории Кыргызстана это ещё и вопрос
приоритета: раз 70% пользователей приходят с телефона, логично, чтобы именно их версия была
базовой, а не «урезанной вдогонку».
</Callout>

Открой предпросмотр и **потяни его край** — на узкой ширине блоки встанут в столбик, на широкой — в
ряд, а фон подписи сменится:

<html lang="ru">

    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <style>
      body { font-family: sans-serif; margin: 0; padding: 16px; }

## clamp(): плавный размер вместо ступенек

Медиазапросы меняют размер «ступенькой» на брейкпоинте. Функция `clamp(мин, желаемое, макс)`
делает то же самое **плавно** — это называют текучей типографикой (*fluid typography*):

```css
h1 { font-size: clamp(24px, 5vw, 40px); }
```

Читается так: «возьми 5% ширины окна, но не меньше 24px и не больше 40px». По числам:

```text
экран 360px:  5vw = 18px  → ниже минимума → берём 24px
экран 640px:  5vw = 32px  → в границах    → берём 32px
экран 1000px: 5vw = 50px  → выше максимума → берём 40px
```

Один заголовок — и ни одного медиазапроса. Для основного текста clamp применяют реже (16px
читается везде), а для крупных заголовков лендинга это приём номер один.

## Спрятать на мобильном: как правильно и как не надо

Частая задача: на десктопе показывать широкий баннер, на телефоне — прятать. Механика простая:

```css
.desktop-only { display: none; }          /* по умолчанию скрыто */
@media (min-width: 1024px) {
  .desktop-only { display: block; }        /* на широких — показать */
}
```

<Callout title="Ловушка: display: none не отменяет загрузку">
Если спрятать через `display: none` тег `img`, браузер **всё равно скачает файл** — он просто
не покажет его. Три «скрытых» баннера по 800 КБ — это 2,4 МБ лишнего трафика на каждый мобильный
визит. При 30 000 мобильных визитов в месяц магазин впустую прогоняет 72 ГБ чужого трафика, а
пользователь на медленном 3G где-нибудь по дороге в Каракол ждёт лишние секунды. Правильные
решения: отдавать разные размеры картинок через `srcset` и тег `picture` (подробно — в лекции
про картинки и скорость) или использовать фоновое изображение внутри медиазапроса — фон из
несработавшего медиазапроса браузер не загружает.
</Callout>

## Как проверять адаптивность: DevTools вместо десяти телефонов

Проверять вёрстку на настоящем телефоне полезно, но неудобно делать это постоянно. В любом
десктопном браузере есть **режим эмуляции устройств** прямо в инструментах разработчика:

1. Откройте страницу и нажмите `F12` (или правый клик → «Просмотреть код»).
2. Нажмите `Ctrl + Shift + M` (на macOS — `Cmd + Shift + M`) — включится **device toolbar**,
   панель эмуляции устройства.
3. Сверху появится выпадающий список устройств и поля ширины/высоты. Выберите «Responsive»
   и вручную выставьте ширину **360** — это наш обязательный минимум.
4. Потяните за край рамки — увидите, как срабатывают брейкпоинты; иконка поворота проверит
   «телефон лёжа».

Там же в DevTools можно включить **троттлинг сети** (вкладка Network → выпадающий список
«No throttling» → «Slow 3G») и почувствовать сайт так, как его чувствует пользователь со слабым
мобильным интернетом за пределами Бишкека.

## Практика: сделай руками и проверь себя

### Упражнение 1. Аудит настоящего сайта на 360px

Откройте любой знакомый сайт (сайт вашего университета — отличный кандидат) и пройдите чек-лист:

1. `F12` → `Ctrl + Shift + M` → режим «Responsive» → ширина `360`.
2. Проверьте: **нет горизонтальной прокрутки** (страницу не нужно двигать вбок).
3. Основной текст читается без увеличения (на глаз — не мельче 16px).
4. Кнопки и пункты меню можно уверенно нажать пальцем (область нажатия примерно 44×44px —
   рекомендация Apple и Google).

**Ожидаемый результат:** вы либо убедитесь, что сайт адаптивен, либо найдёте конкретные поломки —
вылезающую вбок таблицу, микроскопическое меню. Запишите находки: это готовый язык разговора
с подрядчиком-разработчиком.

### Упражнение 2. Передвинь брейкпоинт

Вернитесь к песочнице выше и поменяйте в медиазапросе `600px` на `900px`. Потяните край
предпросмотра. **Ожидаемый результат:** колонки теперь складываются в столбик заметно раньше
(на всех ширинах до 900px), а подпись дольше остаётся зелёной. Верните значение назад и
добавьте промежуточный шаг: на ширине от 600px — две колонки (`1fr 1fr`), от 900px — три.

### Упражнение 3. Почини неадаптивную страницу

В песочнице ниже — типичная «десктопная» вёрстка, которая разваливается на телефоне. Сузьте
предпросмотр до ширины телефона и убедитесь: появляется горизонтальный скролл, заголовок
гигантский. Почините её по списку в комментариях:

<Sandbox template="static" code={`<!doctype html>
<html lang="ru">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <style>
      /* ЗАДАНИЕ — три починки:
         1) .container: замени width на max-width и добавь padding: 0 16px
         2) .cards: сделай mobile-first — базово 1fr,
            а три колонки перенеси в @media (min-width: 700px)
         3) h1: замени 48px на clamp(24px, 6vw, 48px) */
      body { font-family: sans-serif; margin: 0; }
      .container { width: 900px; margin: 0 auto; }
      h1 { font-size: 48px; }
      .cards { display: grid; grid-template-columns: 1fr 1fr 1fr; gap: 12px; }
      .card { background: #eef; padding: 20px; border-radius: 8px; }
    </style>
  </head>
  <body>
    <div class="container">
      <h1>Доставка по Бишкеку и Ошу</h1>
      <div class="cards">
        <div class="card">Заказ онлайн — оплата картой или наличными курьеру.</div>
        <div class="card">По Бишкеку привезём за 2 часа, по Ошу — на следующий день.</div>
        <div class="card">От 3000 сом — доставка бесплатно.</div>
      </div>
    </div>
  </body>
</html>`} />

**Самопроверка:** после починки на ширине 360px не должно быть горизонтального скролла, карточки
стоят в один столбик, заголовок ужался примерно до 24px. На широком предпросмотре — три колонки,
контент не шире 900px и стоит по центру. Если всё так — вы только что своими руками прошли путь
от «сайт сломан на телефоне» до «сайт адаптивен».

<BusinessNote>
Зачем это упражнение экономисту, который не будет верстать сам? Затем, что «адаптивность» — частый
пункт в договоре на разработку сайта (порядка 30 000–150 000 сом за лендинг у фрилансеров и студий
в Бишкеке). Теперь вы умеете за две минуты проверить сдачу работы: DevTools, 360px, чек-лист из
упражнения 1. Это разница между «на глаз вроде нормально» и аргументированной приёмкой.
</BusinessNote>
