Заявка, регистрация, оформление заказа, обратная связь, поиск по каталогу — всё это **формы**.
Форма — единственное место, где сайт не показывает что-то посетителю, а наоборот — получает данные
от него. Собрать форму несложно, но у неё неожиданно много тонкостей: куда уходят данные, как их
проверить, как не растерять людей по дороге к кнопке «Отправить». Разберём всё по порядку.

<BusinessNote>
Форма — это точка, где посетитель превращается в лид (**лид** — контакт потенциального клиента,
который оставил заявку). Посчитаем на примере бишкекского магазина электроники: реклама в Instagram
стоит 60 000 сом в месяц, клик обходится в 20 сом — это 3 000 посетителей. Из них 300 начинают
заполнять форму заказа, но до кнопки «Отправить» доходят только 40% — 120 заявок, по 500 сом за
каждую. Если упростить форму так, чтобы доходили 55% — будет 165 заявок по 364 сома, **плюс 45
заявок в месяц без единого дополнительного сома на рекламу**. Каждое лишнее поле и каждая
непонятная ошибка — это выброшенный рекламный бюджет.
</BusinessNote>

## Из чего состоит форма

Форма — это контейнер `<form>` с полями ввода `<input>` и кнопкой отправки. Бытовая аналогия:
бумажная анкета — лист (форма), графы для заполнения (поля) и окошко «сдать анкету» (кнопка):

```html
<form>
  <input type="text" name="name" />
  <button type="submit">Отправить</button>
</form>
```

Ключевой атрибут поля — **`type`**: он задаёт вид поля и встроенную проверку:

| type | Что это | Бонус |
| --- | --- | --- |
| `text` | обычный текст | — |
| `email` | почта | браузер проверит формат `@` |
| `tel` | телефон | на смартфоне откроет цифровую клавиатуру |
| `number` | число | стрелочки, только цифры |
| `password` | пароль | скрывает символы точками |
| `date` | дата | календарь |
| `checkbox` / `radio` | галочка / выбор одного | — |
| `file` | прикрепить файл | окно выбора файла |

<Callout title="Кнопка внутри формы — всегда submit">
У кнопки `<button>` внутри формы тип по умолчанию — `submit`: любое нажатие (и клавиша Enter в
текстовом поле!) отправляет форму. Если нужна кнопка, которая ничего не отправляет (например,
«показать пароль»), ей явно пишут `type="button"`.
</Callout>

## Куда уходят данные: action и method

Сама по себе форма ничего никуда не сохраняет. У неё есть два атрибута-«маршрутизатора»:
**`action`** — адрес, куда отправить данные (как адрес офиса, куда несут анкету), и **`method`** —
способ отправки. Способов два: `get` и `post`.

```html
<form action="https://shop.kg/search" method="get">
  <input type="text" name="q" />
  <input type="text" name="city" />
  <button type="submit">Найти</button>
</form>
```

Ввели «наушники» и «Бишкек», нажали «Найти» — браузер сам соберёт вот такой адрес и перейдёт по нему:

```text
https://shop.kg/search?q=наушники&city=Бишкек
```

Всё, что после знака вопроса, называется **строкой запроса** (англ. *query string*): пары
`имя=значение`, склеенные через `&`. Обратите внимание: имя в паре — это атрибут **`name`** поля!
Именно поэтому `name` стоит у каждого поля во всех примерах: это «подпись графы анкеты», под которой
сервер получит введённое значение. **Поле без `name` при отправке просто пропускается.**

<Callout title="Классическая ошибка: «форма приходит пустая»">
Менеджер жалуется: заявки с сайта приходят, а телефона клиента в них нет. Причина почти всегда одна:
верстальщик забыл атрибут `name` у поля телефона. Браузер поле показывает, человек его заполняет,
но в отправку оно не попадает — данные молча теряются.
</Callout>

Разница между `get` и `post` — как между открыткой и письмом в конверте:

| | `method="get"` | `method="post"` |
| --- | --- | --- |
| Где данные | в адресной строке, после `?` | внутри запроса, «в конверте» |
| Видны в истории браузера и логах | да | нет |
| Можно сохранить в закладки и переслать ссылкой | да | нет |
| Подходит для | поиск, фильтры каталога | пароли, заказы, персональные данные |

Отсюда железное правило: **пароли и личные данные — только `post`**. Пароль, отправленный через
`get`, попадёт в адресную строку, историю браузера, журналы сервера — то есть останется лежать
открытым текстом сразу в нескольких местах.

<BusinessNote>
Аналитик сталкивается со строкой запроса каждый день, даже не трогая HTML. Рекламные метки
`utm_source=instagram&utm_campaign=march` в отчётах веб-аналитики — это те же пары имя=значение.
А ссылка на каталог с выбранными фильтрами (`shop.kg/phones?brand=samsung&price_max=30000`) — это
«замороженная» GET-форма: её можно вставить в рекламу, и посетитель попадёт сразу на готовую
подборку. Понимание query string — рабочий инструмент маркетолога, а не только программиста.
</BusinessNote>

## Метка label — не для красоты, а обязательна

Каждое поле должно иметь **метку** `<label>`, связанную с ним. Это не просто подпись:

```html
<label for="email">Email</label>
<input type="email" id="email" name="email" />
```

<Callout title="Зачем label связывают с полем">
Связанная метка (`for` = `id`) даёт три вещи: **клик по подписи** ставит курсор в поле (на телефоне
попасть пальцем по подписи проще, чем по узкому полю), **скринридер** зачитывает незрячему
пользователю, что это за поле, и поле проще тестировать автоматикой. Есть и второй способ связать:
обернуть поле в метку — `<label>Имя <input /></label>` — тогда `for` и `id` не нужны.
</Callout>

## Не только текст: textarea, select и radio

Однострочного `input` мало, когда нужен длинный комментарий, выбор из списка или «одно из двух».

**Многострочный текст — `<textarea>`.** В отличие от `input`, это парный тег, а высота задаётся
атрибутом `rows`:

```html
<label for="comment">Комментарий к заказу</label>
<textarea id="comment" name="comment" rows="4"></textarea>
```

**Выпадающий список — `<select>` с вариантами `<option>`.** Пользователь видит текст варианта,
а на сервер уходит его `value`:

```html
<label for="city">Город доставки</label>
<select id="city" name="city">
  <option value="bishkek">Бишкек</option>
  <option value="osh">Ош</option>
  <option value="karakol">Каракол</option>
</select>
```

**Радиокнопки — выбор строго одного варианта.** Секрет в том, что группу образует **одинаковый
`name`**: браузер понимает «это один вопрос анкеты» и, выбирая один кружок, снимает другой:

```html
<fieldset>
  <legend>Способ доставки</legend>
  <label><input type="radio" name="delivery" value="courier" checked /> Курьер по Бишкеку — 200 сом</label>
  <label><input type="radio" name="delivery" value="pickup" /> Самовывоз — бесплатно</label>
</fieldset>
```

Если по ошибке дать радиокнопкам разные `name`, они перестанут «знать друг о друге» — пользователь
сможет выбрать и курьера, и самовывоз одновременно. А `checkbox`, наоборот, независимы: галочек
можно поставить сколько угодно.

<Callout title="fieldset и legend: рамка-раздел анкеты">
`<fieldset>` объединяет связанные поля в группу, а `<legend>` даёт группе заголовок — как рамка
с названием раздела в бумажной анкете. Это особенно важно для радиокнопок: скринридер сначала
прочитает `legend` («Способ доставки»), потом варианты — незрячий пользователь поймёт контекст.
Большие формы (доставка / оплата / получатель) принято резать на такие секции.
</Callout>

## Обязательные поля и встроенная валидация

**Валидация** — проверка, что введённые данные похожи на правду, до того как их принять. Первая
линия — сам браузер, ему достаточно атрибутов:

| Атрибут | Что проверяет | Пример |
| --- | --- | --- |
| `required` | поле не пустое | нельзя отправить без телефона |
| `minlength` / `maxlength` | длина текста | пароль не короче 8 символов |
| `min` / `max` | диапазон числа | количество товара от 1 до 99 |
| `pattern` | текст совпадает с шаблоном | телефон в формате +996… |

Самый мощный из них — **`pattern`**: он принимает **регулярное выражение** (шаблон, описывающий,
как должен выглядеть текст). Проверим кыргызстанский номер телефона — «+996 и ровно 9 цифр»:

```html
<label for="phone">Телефон</label>
<input
  type="tel"
  id="phone"
  name="phone"
  required
  pattern="\+996[0-9]{9}"
  title="Формат: +996 и 9 цифр, без пробелов"
/>
```

Читается шаблон так: `\+996` — буквально символы «+996», `[0-9]{9}` — любая цифра, повторённая
ровно 9 раз. Текст из атрибута `title` браузер подставит в сообщение об ошибке — напишите там
подсказку человеку, а не «данные некорректны».

А ещё браузер сам помечает поля CSS-псевдоклассами: `:invalid` — поле сейчас не проходит проверку,
`:valid` — проходит. На этом строится живая подсветка. Потрогайте: введите номер с ошибкой и без —
рамка сменит цвет сама, без единой строчки JavaScript:

И три уточнения к базовым атрибутам:

- **`placeholder`** — бледная подсказка внутри поля. Это **НЕ замена метки**: как только человек
  начал печатать, подсказка исчезает — и посреди длинной формы он уже не помнит, что это за поле.
- **`type="email"` + `required`** — браузер сам проверит, что введён текст, похожий на почту.
- Браузерная проверка — только первая линия. **Данные всегда дублируют проверкой на сервере**:
  форму легко отправить в обход браузера (это умеет любая программа), и слепо доверять ей нельзя.

## Мобильные мелочи, которые решают: клавиатура и автозаполнение

До 70% посетителей заполняют формы с телефона, где каждое нажатие — усилие. Два атрибута экономят
эти усилия:

- **`inputmode`** — какую экранную клавиатуру показать. `inputmode="numeric"` у поля «код из SMS»
  сразу откроет крупные цифры вместо буквенной клавиатуры.
- **`autocomplete`** — разрешает браузеру подставить сохранённые данные: `autocomplete="name"`,
  `autocomplete="tel"`, `autocomplete="email"`, `autocomplete="street-address"`. Форма из пяти полей
  заполняется в два касания вместо минуты ручного набора — по замерам Google, автозаполнение
  ускоряет заполнение форм примерно на 30%.

<BusinessNote>
Типичная форма оформления заказа в интернет-магазинах содержит 11–12 полей, хотя для доставки
хватает 6–8. Каждое лишнее поле на мобильном — это дополнительные секунды набора и лишний повод
бросить корзину (в мире бросают около 70% корзин). Если заявка стоит бизнесу 400–500 сом рекламного
бюджета, то поле «Отчество», которое никто не использует, буквально сжигает деньги. Аудит формы —
самая дешёвая оптимизация конверсии из существующих.
</BusinessNote>

## UX ошибок: как ругаться, не теряя клиента

Ошибка валидации — момент истины: человек уже потратил силы на заполнение, и грубое «Ошибка!»
отправит его к конкуренту. Четыре правила:

1. **Ошибка — рядом с полем**, а не общим сообщением наверху страницы: на экране телефона верх
   формы давно ускользнул из вида.
2. **Текстом, а не только цветом.** Красная рамка без слов не объясняет, что чинить, а около 8%
   мужчин различают красный и зелёный с трудом.
3. **Говорить, что исправить**, а не констатировать факт ошибки.
4. **Никогда не очищать заполненное.** Форма, стёршая 10 полей из-за одной ошибки, — верный способ
   потерять заявку навсегда.

| Плохо | Хорошо |
| --- | --- |
| «Ошибка в поле» | «В номере не хватает цифры: после +996 должно быть 9 цифр» |
| «Неверный формат» | «Похоже, в адресе почты нет символа @ — проверьте опечатку» |
| Красная рамка без текста | Рамка + короткая подсказка под полем |
| Очистить форму после ошибки | Сохранить всё введённое, подсветить только проблемное поле |

И момент показа: не ругайтесь на первой же букве. Пока человек только печатает адрес почты, он
*ещё* невалиден — честно проверять поле, когда пользователь закончил ввод и перешёл к следующему.

## Практика: сделай руками и проверь себя

**Упражнение 1 — увидеть GET своими глазами.** Откройте google.com, наберите в поиске «курс доллара
НБКР» и нажмите Enter. Теперь посмотрите в адресную строку. *Ожидаемый результат:* после знака `?`
вы найдёте параметр `q=` с вашим запросом (слова будут соединены знаками `+` или кодами вида `%20`).
Поиск Google — это обычная форма с `method="get"`, а вы только что прочитали её строку запроса.

**Упражнение 2 — найти name у настоящего поля.** Не уходя из Google, нажмите F12 (или ПКМ по полю
поиска → «Просмотреть код»). *Ожидаемый результат:* в подсвеченном теге вы увидите атрибут

## Граничные случаи: где всё ломается

- **Пробел вместо пустой строки.** Поле с `required` пропускает ввод из одних пробелов — визуально
  пусто, но браузер считает его заполненным, потому что символ там есть. Причина: `required`
  проверяет только длину строки, а не её смысл. Как правильно: пустоту от пробелов отсекает уже
  сервер — там текст обрезают (`trim`) перед проверкой.
- **Радиокнопки без единого выбранного варианта.** Если ни у одного `input type="radio"` в группе
  нет `checked`, форма отправится с этим полем вообще без значения — как будто вопрос никто не
  задавал. Причина: браузер не выбирает вариант «по умолчанию» сам. Как правильно: либо ставить
  `checked` на самый частый вариант, либо на сервере отдельно проверять, что значение вообще
  пришло.
- **Число в поле `type="number"` за пределами `min`/`max`.** Пользователь вписывает `9999` в
  количество товара при `max="99"` — но, вставив значение через клавиатуру (а не стрелочки), можно
  ввести что угодно, и `:invalid` подсветит поле только при попытке отправки, не раньше. Причина:
  `min`/`max` — это подсказка для проверки при сабмите, а не запрет набора цифр. Как правильно:
  дублировать диапазон проверкой на сервере, иначе через API можно отправить и отрицательное
  количество.
- **`pattern` совпал с частью строки, а не со всей.** Регулярное выражение без явных границ иногда
  пропускает мусор до или после нужного текста, если сам шаблон это допускает. Причина: пример из
  лекции — `\+996[0-9]{9}` — работает, только если ничего лишнего не окружает всю строку поля;
  доверять шаблону как единственной защите нельзя. Как правильно: браузерный `pattern` всегда
  проверяют этим же (или более строгим) регулярным выражением ещё раз на сервере.
