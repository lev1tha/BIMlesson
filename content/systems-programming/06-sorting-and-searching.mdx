Отсортировать каталог магазина по цене, найти клиента по номеру телефона в базе на 200 тысяч
строк, показать десять самых прибыльных товаров — всё это **алгоритмы**: пошаговые рецепты решения
задачи. Один и тот же результат можно получить разными способами, и разница огромна: на миллионе
записей неудачный алгоритм работает часами, а удачный — доли секунды. Разберём две базовые задачи —
сортировку и поиск — и научимся оценивать скорость алгоритма до того, как он положит ваш отчёт.

<BusinessNote>
«Отчёт строится 40 минут» — чаще всего это не слабый сервер, а неудачный алгоритм внутри. Посчитаем:
аналитик с зарплатой 60 000 сом в месяц обходится компании примерно в 340 сом за рабочий час. Если

«это квадратичный алгоритм? на наших объёмах он взорвётся» — и вернуть эти деньги в работу.
</BusinessNote>

## Сортировка пузырьком

Самый простой (и наглядный) алгоритм сортировки — **пузырёк**: идём по массиву, сравниваем соседей
и меняем местами, если они «не по порядку». Большие числа постепенно «всплывают» в конец, как
пузырьки воздуха в воде. За несколько проходов массив отсортирован.

Прогоните визуализатор по шагам — жёлтым подсвечены сравниваемые столбики, зелёным — уже
отсортированный «хвост»:

Обратите внимание на счётчик сравнений: для 7 элементов пузырёк в худшем случае делает 21 сравнение —
по формуле n × (n − 1) / 2, потому что каждый элемент так или иначе сравнивается с каждым. А сколько
это будет для миллиона строк выгрузки? Держите вопрос в голове — ниже дойдём до точной цифры.

## Big-O: как оценивают скорость алгоритма

**Big-O** («о большое») — способ описать, как растёт время работы при росте объёма данных `n`. Нас
интересует не точное время в секундах (оно зависит от компьютера), а **характер роста**:

| Обозначение | Название | Пример | На больших n |
| --- | --- | --- | --- |
| `O(1)` | константа | взять элемент по индексу | мгновенно |
| `O(log n)` | логарифм | бинарный поиск | очень быстро |
| `O(n)` | линейно | пройти массив один раз | терпимо |
| `O(n log n)` | «почти линейно» | быстрые сортировки, встроенный `sort` | хорошо |
| `O(n²)` | квадратично | пузырёк, вложенные циклы | больно на больших данных |

<Callout title="Почему O(n²) — это боль">
Точное число сравнений пузырька — n × (n − 1) / 2. Для 7 элементов это 21 (как в визуализаторе),
для 10 — 45, для 1000 — почти 500 тысяч, для миллиона — около 500 миллиардов. Рост «в квадрате»
означает: данных стало в 10 раз больше — работы в 100 раз больше. Поэтому в реальных программах
используют алгоритмы класса `O(n log n)`, а пузырёк остаётся учебным экспонатом.
</Callout>

## Встроенный sort и его главная ловушка

В реальном коде пузырёк руками никто не пишет — в JavaScript есть встроенный метод `arr.sort()`.
Но у него есть подвох, на который попадаются даже опытные разработчики:

```js
[10, 9, 1].sort();    // [1, 10, 9]  — что?!
[100, 25, 3].sort();  // [100, 25, 3] — «отсортировано», но без изменений
```

Без параметров `sort()` превращает элементы в **строки** и сортирует их по алфавиту — это называется
**лексикографический порядок**, то есть «как слова в словаре». Строка «10» начинается с символа «1»,
поэтому идёт раньше строки «9» — так же, как «арбуз» стоит в словаре раньше «банана», хотя букв в нём
больше. Для цен, сумм и количеств это катастрофа: 100 сом окажутся «дешевле» 25.

Чтобы сортировать числа как числа, методу передают **компаратор** — функцию из двух аргументов,
которая решает, кто из пары встанет раньше:

```js
const prices = [1200, 90, 450];

prices.sort((a, b) => a - b); // [90, 450, 1200] — по возрастанию
prices.sort((a, b) => b - a); // [1200, 450, 90] — по убыванию
```

Правило простое: вернул отрицательное число — `a` встанет раньше `b`; положительное — позже; ноль —
порядок пары не важен. Выражение `a - b` отрицательно ровно тогда, когда `a` меньше, — вот и весь
секрет возрастания. Для **убывания** аргументы просто меняют местами: `b - a`. Никаких флагов
«desc» — только направление вычитания.

<Callout title="sort меняет исходный массив">
`sort()` — **мутирующий** метод: он перестраивает сам массив, а не возвращает копию. Если исходный
порядок ещё нужен (например, «в порядке добавления в корзину»), сортируйте копию:
`[...arr].sort(...)`. В современных браузерах есть немутирующий вариант — `arr.toSorted(...)`:
он возвращает новый массив, не трогая старый.
</Callout>

Строки с кириллицей надёжнее сравнивать через `localeCompare` — он понимает алфавиты и регистр:

```js
const cities = ['Ош', 'Бишкек', 'Каракол'];
cities.sort((a, b) => a.localeCompare(b, 'ru'));
// ['Бишкек', 'Каракол', 'Ош']
```

## Сортировка объектов: то, что аналитику нужно каждый день

Реальные данные — это не массив чисел, а массив объектов: товары, заказы, транзакции. Компаратор
сравнивает не сами объекты, а их **поля**:

```js
const products = [
  { name: 'Кофе зерновой', price: 1450 },
  { name: 'Чай каркаде', price: 320 },
  { name: 'Мёд горный', price: 890 },
];

// «Сначала недорогие» — для витрины
products.sort((a, b) => a.price - b.price);

// «Сначала дорогие» — для отчёта по выручке
products.sort((a, b) => b.price - a.price);
```

С датами тот же приём. Если дата хранится строкой в формате `ГГГГ-ММ-ДД` (например, `2026-08-17`),
её можно сортировать как строку — формат специально придуман так, чтобы алфавитный порядок совпадал
с хронологическим. А метка времени (число миллисекунд) сортируется как обычное число:

```js
orders.sort((a, b) => a.date.localeCompare(b.date)); // старые сверху
orders.sort((a, b) => b.createdAt - a.createdAt);    // новые сверху
```

<BusinessNote>
Каждая кнопка «Сортировать по…» в интернет-магазине — это ровно одна строка с компаратором. И она
двигает выручку напрямую: товар на первом экране выдачи покупают в разы чаще, чем на пятом. Если
магазин на shop.kg делает 300 заказов в день со средним чеком 1 800 сом, то порядок выдачи «управляет»
оборотом в 540 000 сом ежедневно. Понимать, по какому полю и в какую сторону отсортирована витрина, —
это не техническая мелочь, а вопрос денег.
</BusinessNote>

## O(n log n): что работает внутри настоящего sort

Внутри движка V8 (это Chrome и Node.js) метод `sort()` — не пузырёк, а **Timsort**: гибрид сортировки
слиянием и сортировки вставками, придуманный для языка Python и перекочевавший в JavaScript и Java.
Его сложность — `O(n log n)`, «эн-лог-эн»: почти линейный рост.

Что это значит в цифрах. `log₂ n` — сколько раз нужно поделить n пополам, чтобы дойти до единицы:
для миллиона это всего 20. Сравним объём работы на миллионе записей:

| Алгоритм | Формула | Сравнений на 1 000 000 записей | Время при 100 млн сравнений/сек |
| --- | --- | --- | --- |
| Пузырёк | n × (n − 1) / 2 | ≈ 500 миллиардов | ≈ 1,4 часа |
| Timsort (встроенный `sort`) | n × log₂ n | ≈ 20 миллионов | ≈ 0,2 секунды |

Разница — в 25 000 раз. Железо одинаковое, вся разница — в формуле.

<Callout title="Зачем тогда учить пузырёк">
Не чтобы писать его в продакшене, а чтобы, во-первых, узнавать O(n²) в чужом коде: вложенный цикл
«каждый с каждым» по одной и той же коллекции — главный красный флаг на код-ревью. Во-вторых, чтобы
понимать: «медленно» — это почти всегда про алгоритм, а не про компьютер. Новый сервер ускорит отчёт
в 2 раза, замена O(n²) на O(n log n) — в тысячи.
</Callout>

## Поиск: линейный против бинарного

**Линейный поиск** — идём по массиву с начала и сравниваем каждый элемент. Просто, работает на любых
данных, но это `O(n)`: в худшем случае обойдём всё. Для базы в 200 000 клиентов — до 200 000 сравнений
на каждый запрос.

**Бинарный поиск** работает только по **отсортированным** данным, зато молниеносно. Идея — как в игре
«угадай число от 1 до 100»: смотрим в середину, и если искомое меньше — отбрасываем всю правую
половину, если больше — левую. Каждый шаг **вдвое** сокращает область поиска. Это `O(log n)`.

<Mermaid
  title="Бинарный поиск: сужение границ"
  chart={`flowchart TD
    A["lo = 0, hi = длина − 1"] --> B{"lo больше hi?"}
    B -->|"да"| C["Не найдено: вернуть −1"]
    B -->|"нет"| D["mid = середина между lo и hi"]
    D --> E{"arr[mid] сравнить с target"}
    E -->|"равно"| F["Найдено: вернуть mid"]
    E -->|"arr[mid] меньше target"| G["lo = mid + 1"]
    E -->|"arr[mid] больше target"| H["hi = mid − 1"]
    G --> B
    H --> B`}
/>

<Callout title="Сила логарифма">
В базе на миллион записей линейный поиск — до миллиона сравнений, бинарный — всего около 20
(2²⁰ ≈ миллион). Удвоили базу до двух миллионов? Линейному вдвое больше работы, бинарному — плюс
одно сравнение. Именно так вы сами ищете слово в бумажном словаре: открываете примерно посередине,
а не листаете с первой страницы. Плата за скорость одна: данные должны быть отсортированы.
</Callout>

<BusinessNote>
Эта идея окружает аналитика со всех сторон. Функция ВПР (VLOOKUP) в Excel в режиме приблизительного
совпадения использует именно бинарный поиск — поэтому требует отсортированный столбец и поэтому на
таблице в 100 000 строк работает в сотни раз быстрее точного перебора. Индексы в базах данных — та же
логика: «найти клиента по номеру телефона за миллисекунды» возможно потому, что индекс хранит ключи
упорядоченными.
</BusinessNote>

## Граничные случаи: где всё ломается

Алгоритмы, которые красиво работают на учебных примерах, спотыкаются на реальных данных. Вот
типичные ловушки именно для сортировки и поиска.

**Пустой массив.** `[].sort((a, b) => a - b)` не падает и не ругается — просто возвращает `[]`.
Почему: цикл сравнений просто не запускается, сравнивать нечего. Как правильно: не нужно отдельно
проверять пустой массив перед вызовом `sort` или `linearSearch` — они уже безопасны для `[]`, это
проверяют и тест-кейсы выше.

**Отсортированный по убыванию массив для бинарного поиска.** Если передать в `binarySearch` массив
вроде `[11, 9, 7, 5, 3, 1]` (по убыванию, а не по возрастанию), алгоритм тихо вернёт неверный
результат или `-1` даже для существующего элемента. Почему: логика «если `arr[mid]` меньше `target`
— двигаем `lo` вправо» верна только при возрастающем порядке, при убывающем она отбрасывает не ту
половину. Как правильно: перед бинарным поиском убедитесь, что массив отсортирован именно по
возрастанию — например, самим же `sort((a, b) => a - b)`.

**NaN в массиве чисел.** `[5, NaN, 1].sort((a, b) => a - b)` даёт непредсказуемый порядок: `NaN - 5`
и `5 - NaN` оба равны `NaN`, а компаратор ожидает число, а не `NaN`. Почему: движок трактует `NaN`
как «пара равна», и в зависимости от алгоритма сортировки элемент может оказаться где угодно. Как
правильно: перед сортировкой отфильтровать некорректные значения — `arr.filter(x => !Number.isNaN(x))`
— или явно решить, куда девать «плохие» строки (например, цену без числа).

**Дубликаты и стабильность сортировки.** Если два товара стоят одинаково (`{ price: 40 }` и
`{ price: 40 }`), какой из них окажется первым после `sort`? Правильный ответ — тот, что шёл первым
в исходном массиве: современный `Array.prototype.sort` в JavaScript **стабилен** по спецификации.
Почему это важно: если сортировать список сначала по имени, а потом (отдельным вызовом) по цене,
стабильность гарантирует, что товары с одинаковой ценой останутся в алфавитном порядке между собой —
это тест-кейс с «Вода» и «Айран» в задаче `sortByPrice` выше.
