## Введение

Бакыт — разработчик в бишкекской компании, которая развозит заказы по Кыргызстану. Полгода назад он написал
функцию, которой гордился: короткая, ни одного лишнего символа. Сегодня руководитель просит: «Считай заказы
от 5000 сом включительно, а не строго больше 5000. Сделай за час». Бакыт открывает файл и видит вот что:

```js
function f(a, b) {
  var c = 0;
  for (var i = 0; i < a.length; i++) {
    if (a[i].paid && a[i].amount > b) c = c + a[i].amount;
  }
  return c;
}
```

Что лежит в `a`, `b` и `c`? Какой из знаков сравнения — тот самый порог? Автор — сам Бакыт, но за полгода
контекст выветрился, и свой код он читает как чужой. Час превращается в рабочий день. Компьютеру всё равно — он
одинаково выполнит и `f(a, b)`, и `sumOfLargePaidOrders(orders, minAmount)`; людям разница огромная. **Чистый код** —
код, который понятен без автора рядом: читается почти как текст, а менять его не страшно. **Рефакторинг** —
наведение порядка в таком коде без изменения того, что он делает.

<BusinessNote>
Сколько стоит непонятный код. Допустим, разработчик в Бишкеке получает 90 000 сом в месяц; в месяце около 176
рабочих часов, значит, час стоит примерно 500 сом. Правка, которая в чистом коде занимает час, а в запутанном —
рабочий день (8 часов), съедает лишние 7 часов, то есть 3 500 сом. Если в команде из пяти человек каждый делает две
такие правки в неделю, потери — 10 × 3 500 = 35 000 сом в неделю и около 140 000 сом в месяц: полторы зарплаты
разработчика, потраченные на расшифровку старого кода вместо новых функций. И это без ошибок, рождённых непониманием.
</BusinessNote>

**Что вы узнаете:**

- почему код читают в десять раз чаще, чем пишут, и сколько сомов стоит запутанный код
- как называть переменные и функции, чтобы код читался как текст
- как упрощать код: маленькие функции, константы вместо магических чисел, ранний выход вместо пирамиды if
- как делать рефакторинг, не ломая работающее: только под тестами и маленькими шагами
- когда повторы стоит убирать (DRY), а когда это ловушка, и что писать в комментариях
- как договориться о стиле через Prettier, провести код-ревью без обид и почему технический долг — кредит с процентами

Пригодится из прошлых лекций: «Тестирование» (тесты как страховочная сетка), «Отладка и ошибки», «TypeScript», «Git и совместная работа» (pull request и откат), «Объекты и JSON».

## Код читают чаще, чем пишут

Роберт Мартин в книге «Чистый код» оценивает соотношение так: на каждую написанную строку приходится больше
десяти прочтений. Вы читаете код, когда ищете причину бага, добавляете функцию, готовите правку к ревью,
вводите в проект новичка. Точная цифра условна, а порядок верный: программист большую часть дня читает, а не
печатает. Поэтому экономить надо не секунды набора, а минуты чтения: удлинить имя на десять букв дешевле, чем
заставить десять человек десять раз его расшифровывать. Вот функция Бакыта, написанная для людей. Поведение
прежнее, изменились только имена и оформление:

```js
function sumOfLargePaidOrders(orders, minAmount) {
  let total = 0;
  for (const order of orders) {
    if (order.paid && order.amount > minAmount) {
      total += order.amount;
    }
  }
  return total;
}
```

Теперь просьба «от 5000 включительно» — это замена одного знака `>` на `>=` в строке, которую видно с первого
взгляда. Запутанный код обходится команде в три вида потерь:

- **время** — минуты и часы уходят на то, чтобы просто понять, что происходит;
- **страх** — код боятся трогать, поэтому правят «рядом», а не «где нужно», и беспорядок растёт;
- **ошибки** — поняли неправильно, значит, и поменяли неправильно.

## Имена: переменная говорит, что в ней

Имя — ярлык на коробке на складе. Ярлык «Картофель, 25 кг, Ош» позволяет взять нужную коробку, не вскрывая;
ярлык «Коробка 2» заставит вскрыть все. Хорошее имя отвечает без заглядывания внутрь: для переменной — «что здесь
лежит?», для функции — «что она делает?». Правила собраны в таблице:

| Что называем | Правило | Плохо | Хорошо |
| --- | --- | --- | --- |
| Переменная | существительное: что внутри | `d`, `data2`, `tmp`, `x` | `daysUntilDelivery` |
| Функция | глагол: какое действие | `delivery(o)`, `data(u)` | `calculateDeliveryCost(order)` |
| Да или нет | вопрос: is, has, can | `flag`, `paid` | `isPaid`, `hasDiscount` |
| Список | множественное число | `order`, `list` | `orders` |
| Величина | единица в имени | `timeout`, `price` | `timeoutMs`, `priceTyiyn` |

```js
// было
function check(o) {
  const t = Date.now();
  const d = Math.ceil((o.time - t) / 86400000);
  return d > 3;
}
```

```js
// стало
function isSlowDelivery(order) {
  const now = Date.now();
  const daysUntilDelivery = Math.ceil((order.time - now) / 86400000);
  return daysUntilDelivery > 3;
}
```

Числа `86400000` и `3` пока остались — ими займёмся в разделе про магические числа. Ещё три тонкости:

- **Длина имени растёт с областью видимости.** `i` в цикле на три строки — нормально; константа на весь проект из одной буквы — нет.
- **Одно слово — одно понятие.** Не смешивайте `get`, `fetch` и `load` для одного и того же.
- **Не врите именем.** Переменная `orderCount` со списком заказов хуже, чем `x`: `x` хотя бы не обманывает.

<Callout title="Один язык для имён">
JavaScript разрешает кириллицу в именах, и в учебных лекциях мы местами ею пользовались. В рабочих проектах команда
договаривается об одном языке — чаще английском. Хуже всего русские слова латиницей вроде `summaZakaza`: ни русский, ни английский.
</Callout>

## Маленькие функции: одна функция — одно дело

Функция на 80 строк — как рецепт, где «купить продукты», «приготовить» и «помыть посуду» слиты в один абзац.
**Принцип единственной ответственности** гласит: у функции должна быть одна причина измениться. Проверка
простая — опишите функцию одной фразой. Если в ней появилось «и» («проверяет заказ И считает сумму И шлёт
SMS»), функций внутри на самом деле несколько.

```js
// было: одна функция делает четыре дела
function processOrder(order) {
  // проверяем
  if (order.items.length === 0) throw new Error('Пустой заказ');
  // считаем
  let total = 0;
  for (const item of order.items) total += item.price * item.qty;
  // сохраняем и сообщаем
  db.save(order, total);
  sendSms(order.phone, 'Заказ принят на ' + total + ' сом');
  return total;
}
```

```js
// стало: главная функция читается как оглавление
function processOrder(order) {
  validateOrder(order);
  const total = calculateTotal(order);
  saveOrder(order, total);
  notifyCustomer(order.phone, total);
  return total;
}

function validateOrder(order) {
  if (order.items.length === 0) throw new Error('Пустой заказ');
}

function calculateTotal(order) {
  let subtotal = 0;
  for (const item of order.items) subtotal += item.price * item.qty;
  return subtotal;
}
```

За пять секунд виден весь сценарий, а детали лежат там, где их ищут. Заметьте: комментарии «проверяем» и
«считаем» исчезли — они стали именами. Если внутри функции понадобился комментарий-заголовок, это название
будущей функции. Признаки того, что функция делает слишком много:

- в описании есть «и»;
- внутри комментарии-заголовки;
- не помещается на экран (ориентир — до 20 строк, но это ориентир, а не закон);
- больше трёх параметров — передайте один объект с понятными полями;
- её нельзя проверить тестом без базы и SMS: значит, расчёт перемешан с побочными действиями.

## Рефакторинг: меняем структуру, поведение не трогаем

**Рефакторинг** — изменение внутреннего устройства кода без изменения того, что он делает снаружи. Это уборка на
кухне работающего ресторана: переставили кастрюли, подписали банки, а меню прежнее — гость ничего не заметил. Всё,
что меняет результат (починка бага, новая функция), рефакторингом не считается. Отсюда правило «двух шляп»: в
каждый момент вы либо наводите порядок, либо меняете поведение, но не оба дела сразу — иначе при поломке не
понять, кто виноват.

Как узнать, что поведение осталось прежним? Глазами ненадёжно: в запутанной функции десяток ветвей, а вы проверите
две-три. Страховочная сетка — **тесты** из лекции «Тестирование». Помните цикл «красный → зелёный → чистый»? Тест
падает (красный), код заставляет его пройти (зелёный), и только потом вы наводите порядок (чистый) — а тесты рядом
мгновенно подскажут, если уборка что-то испортила. Рефакторинг без тестов — ремонт проводки при включённом рубильнике.

<Mermaid
  title="Безопасный рефакторинг: маленький шаг, проверка, следующий шаг"
  chart={`flowchart TD
    A["Хочу навести порядок в коде"] --> B{"Есть тесты на это<br/>поведение?"}
    B -->|"нет"| C["Сначала напиши тесты на то,<br/>как код работает сейчас"]
    C --> D["Один маленький шаг:<br/>переименовать, вынести, упростить"]
    B -->|"да"| D

    F --> D
    E -->|"да"| G["Сохрани шаг коммитом"]
    G --> H{"Код достаточно чистый?"}
    H -->|"ещё нет"| D
    H -->|"да"| I["Готово: поведение прежнее,<br/>структура лучше"]`}
/>

Три правила из схемы:

- **Шаги маленькие:** одно переименование, одно выделение функции, один ранний выход; после каждого — тесты (`npx vitest`, секунды).
- **Красный — откат:** не чините поверх. Верните код к последнему зелёному состоянию (`git restore` для ещё не закоммиченного шага — см. «Git и совместная работа») и сделайте шаг меньше.
- **Тестов нет — сначала они:** зафиксируйте тестами, как код работает сейчас, даже если поведение странное. Странности исправите потом, в другой «шляпе».

Вот тесты для `calculateTotal`, выделенной в прошлом разделе: они пишутся до выделения и после него не меняются.

```js
import { describe, it, expect } from 'vitest';
import { calculateTotal } from './order.js';

describe('calculateTotal', () => {
  it('2 × 300 + 1 × 700 = 1300', () => {
    const order = { items: [{ price: 300, qty: 2 }, { price: 700, qty: 1 }] };
    expect(calculateTotal(order)).toBe(1300);
  });

  it('пустой заказ стоит 0', () => {
    expect(calculateTotal({ items: [] })).toBe(0);
  });
});
```

| Шаг | Что сделали | Тесты | Решение |
| --- | --- | --- | --- |
| 1 | переименовали `t` в `total` | зелёные | коммит |
| 2 | цикл на `reduce` без начального значения (пустой заказ даст `TypeError`) | красные | откат шага |
| 3 | то же, но с начальным значением 0 | зелёные | коммит |

## Магические числа: смысл должен быть в имени

**Магическое число** — число (или строка) прямо посреди кода, смысл которого без пояснений непонятен: `0.12`,
`86400000`, `2000`. Проблем две: читатель не понимает, что это; а если число повторяется, то при смене правил его
придётся искать по всему проекту — и обязательно пропустить одно место. Лечится **именованной константой**: имя
заглавными буквами через подчёркивание, значение — в одном месте.

```js
// было
function vatAmount(price) {
  return price * 0.12;
}

function priceWithoutVat(total) {
  return total / 1.12;
}
```

```js
// стало
// Ставка НДС в Кыргызстане — 12%. Закон изменится — правим одну строку.
const VAT_RATE = 0.12;

function vatAmount(price) {
  return price * VAT_RATE;
}

function priceWithoutVat(total) {
  return total / (1 + VAT_RATE);
}
```

Обратите внимание на `1.12`: это скрытая копия той же ставки (1 + 0.12). Сменят НДС, поправят `0.12`, забудут
`1.12` — и цены без НДС тихо поедут. (Деньги в боевом коде считают в тыйынах и округляют — см. «Числа, деньги и
даты»; здесь мы смотрим только на имена.) Не каждое число магическое:

| В коде | Магия? | Что делать |
| --- | --- | --- |
| `price * 0.12` | да | константа `VAT_RATE` |
| `sum >= 2000` | да | константа `FREE_DELIVERY_FROM` |
| `ms / 86400000` | да | константа `MS_PER_DAY` |
| `items.length - 1`, `i + 1` | нет | смысл очевиден из контекста |
| `status === 'paid'` в тридцати местах | да, это строка | `ORDER_STATUS.PAID`: опечатка `'payed'` без константы не даст ошибки |

Правило: если читатель может спросить «а это что за число?» — дайте ему имя.

## Ранний выход: плоско лучше, чем вложенно

Когда условие сидит в условии в условии, код растёт вправо ступеньками — «пирамида». Читатель вынужден держать в
голове все открытые условия сразу, а в голове человека умещается всего несколько вещей. **Ранний выход** (guard
clause, «охранное условие») переворачивает логику: особые случаи отсекаются сразу, наверху, а основной сценарий
идёт ровно, без отступов — как охранник на входе: лишних отсёк у двери, остальные спокойно проходят.

```js
// было: пирамида
function discountPercent(customer) {
  let percent = 0;
  if (customer) {
    if (customer.isActive) {
      if (customer.ordersCount >= 10) {
        percent = 10;
      } else if (customer.ordersCount > 0) {
        percent = 5;
      }
    }
  }
  return percent;
}
```

```js
// стало: ранний выход
function discountPercent(customer) {
  if (!customer) return 0;
  if (!customer.isActive) return 0;
  if (customer.ordersCount >= 10) return 10;
  if (customer.ordersCount > 0) return 5;
  return 0;
}
```

Условия те же и в том же порядке, поэтому результат для любого входа тот же — это и есть рефакторинг. Три-пять
охранных условий — норма; если их десять, функция делает слишком много, вернитесь к предыдущим разделам. А когда
вместо цепочки условий у вас просто соответствие «город → тариф», не нужны ни пирамида, ни цепочка: хватит
таблицы данных, которая стоит рядом с кодом. Этим приёмом вы воспользуетесь в тренажёре.

## Тренажёр: отрефактори и почини

Ниже — запутанная версия функции `deliveryCost`: вложенные `if`, `var`, безымянная переменная `x`. Перепишите её
чисто: тарифы — в объекте, логика — в паре строк. В коде спрятан баг, о котором вам не сказали: заметят его только
тесты. Работайте как профессионал: сначала нажмите «Проверить» на старом коде и посмотрите, какой случай красный,
затем меняйте код маленькими шагами, проверяя после каждого.

Решили? Сверьтесь. Не решили — нажмите «Подсказку» и только потом читайте дальше. Один из вариантов:

```js
const TARIFFS = {
  'Бишкек': { freeFrom: 2000, price: 150 },
  'Ош': { freeFrom: 3000, price: 250 },
};
const OTHER_CITY_PRICE = 400;

function deliveryCost(sum, city) {
  const tariff = TARIFFS[city];
  if (!tariff) return OTHER_CITY_PRICE;
  return sum >= tariff.freeFrom ? 0 : tariff.price;
}
```

**Что поймали тесты.** В запутанной версии для Оша стояло `sum > 3000`: заказ ровно на 3000 сом платил 250 вместо
бесплатной доставки. Пять уровней вложенности прятали ошибку — глаз «съедает» знак. После рефакторинга порог
живёт в данных рядом с ценой, а проверка одна на все города — второй такой баг негде спрятать. Бонус: если город
приходит из формы, пользователь может вписать `toString`; обычный объект вернёт унаследованную функцию вместо «не
найдено», и наша функция вернёт `undefined`. Надёжнее `Object.hasOwn(TARIFFS, city)` или `Map`.

## DRY и его ловушка: не всё похожее — одно и то же

**DRY** (Don't Repeat Yourself — «не повторяйся») — одно знание должно жить в одном месте. Прайс-лист в магазине
один; если на каждой витрине свой ценник, при смене цены один обязательно забудут. В коде так же: проверку
телефона скопировали в три формы, ошибку поправили в одной — в двух остались старые.

```js
// было: копия проверки в каждой форме
if (!/^\+996\d{9}$/.test(phone)) showError('Неверный номер'); // заказ
if (!/^\+996\d{9}$/.test(phone)) showError('Неверный номер'); // регистрация

// стало: одно знание — одна функция
function isValidKgPhone(phone) {
  return /^\+996\d{9}$/.test(phone);
}
if (!isValidKgPhone(phone)) showError('Неверный номер');
```

Обратная сторона — **преждевременная абстракция**: общая функция, придуманная раньше, чем стало ясно, что это
действительно одно и то же. Сходство вида ещё не сходство смысла. Скидки для студентов и пенсионеров сегодня
обе по 10% — но это два разных решения бизнеса, и «улучшение» их свяжет:

```js
// было: два решения, случайно совпавшие по числу
const STUDENT_DISCOUNT = 0.1;
const PENSIONER_DISCOUNT = 0.1;

// ловушка: «одна скидка». Через месяц маркетинг захочет 15% студентам,
// и общую константу придётся разматывать в десяти местах
const SOCIAL_DISCOUNT = 0.1;
```

<Callout title="Правило трёх и вопрос про причину">
Первый раз пишете — пишите. Второй раз повторяете — поморщитесь, но можно скопировать. На третий остановитесь
и спросите: изменятся ли эти куски по одной и той же причине? Если да — выносите в функцию. Если нет — оставьте
дубль: дублирование обходится дешевле, чем неверная абстракция.
</Callout>

| Повтор | Одна причина изменений? | Решение |
| --- | --- | --- |
| Проверка телефона в трёх формах | да, формат номера один | вынести: `isValidKgPhone` |
| Ставка `0.12` в десяти местах | да, закон один | константа `VAT_RATE` |
| Скидки студентам и пенсионерам | нет, решает маркетинг, по каждой отдельно | оставить две константы |

## Комментарии: объясняют «почему», а не «что»

Комментарий — записка на щитке: «Не трогать — греется». Что делает строка, читатель увидит сам, если имена
хорошие. А вот почему она такая — этого в коде не видно: бизнес-решение, требование банка, обход чужой ошибки.
Для этого комментарии и нужны.

```js
// было: комментарии пересказывают код
// увеличиваем i на 1
i++;
// если сумма не меньше порога, доставка бесплатная
if (sum >= FREE_DELIVERY_FROM) return 0;
// старый вариант:
// if (sum > 2000) return 0;
```

```js
// стало: имена говорят «что», комментарий — «почему»
i++;

// Порог включительный: заказ ровно на 2000 сом доставляем бесплатно —
// условие акции маркетинга от 12 марта (задача #218).
if (sum >= FREE_DELIVERY_FROM) return 0;
```

Три правила. Если хочется написать комментарий «что» — сначала переименуйте или выделите функцию. Пишите причину,
источник и срок: кто решил, когда, в какой задаче; даже `TODO` должен иметь срок: `TODO до 1 ноября: убрать после
акции`. Закомментированный код удалите: у вас есть Git («Git и совместная работа»), он помнит все старые версии.

## Форматирование: спор о пробелах решает машина

Табы или пробелы, одинарные или двойные кавычки, точка с запятой или без — команды тратят часы на споры, которые
ни на что не влияют, кроме нервов. Решение — отдать это машине. **Форматтер** (самый популярный — Prettier) сам
перепишет файл в единый стиль при сохранении. **Линтер** (ESLint) — «проверка правописания» для кода: ловит не
стиль, а подозрительные места: неиспользуемую переменную, `==` вместо `===`, `var` вместо `let`.

```js
// было
function total(items){var s=0
for(var i=0;i<items.length;i++){s+=items[i].price*items[i].qty}
return s}
```

```js
// стало: после запуска Prettier
function total(items) {
  var s = 0;
  for (var i = 0; i < items.length; i++) {
    s += items[i].price * items[i].qty;
  }
  return s;
}
```

```bash
npx prettier --write .
npx eslint .
```

```text
delivery.js
  2:3  error  Unexpected var, use let or const instead  no-var
  3:9  error  Expected '===' and instead saw '=='       eqeqeq

2 problems (2 errors, 0 warnings)
```

<Callout title="Стиль мы не обсуждаем">
Настройки Prettier и ESLint лежат в репозитории, у всех команды работают одинаково. В код-ревью не пишут
«поставь пробел»: за это отвечает машина (в VS Code включите Format On Save). Для бизнеса это часы внимания
ревьюера, потраченные на логику, границы и имена, а не на вкусовщину.
</Callout>

## Код-ревью: второй взгляд до слияния

**Код-ревью** — коллега читает ваши изменения до того, как они попадут в основную ветку. В Git это делается через
**pull request**: вы предлагаете влить ветку, коллеги комментируют строки и нажимают «Одобрить» или «Вернуть на
доработку» (см. «Git и совместная работа»). Ревью ловит ошибки, которых автор не видит, разносит знания по команде и
держит планку качества. Чек-лист ревьюера:

| Вопрос ревьюера | Что ищем |
| --- | --- |
| Работает ли? | задача решена; границы: пустой ввод, ноль, ровно порог, NaN |
| Есть ли тесты? | тест на новое поведение и на границы; тесты зелёные |
| Понятно ли без автора? | имена, размер функций, вложенность, комментарии «почему» |
| Нет ли магии и дублей? | числа без имён, копипаст; и наоборот — лишняя абстракция |
| Безопасно ли? | ключи и пароли в коде, слепое доверие к вводу пользователя |
| Не слишком ли большая правка? | от нескольких сотен строк — просите разбить |
| Не врёт ли комментарий? | текст рядом с кодом совпадает с тем, что код делает сейчас |
| Стиль? | не обсуждаем: это работа Prettier и линтера |

Замечания пишут так, чтобы их хотелось исполнить:

- **о коде, а не о человеке:** «эта функция делает три дела», а не «ты написал мусор»;
- **вопрос вместо приказа:** «что вернёт функция для пустого города?»;
- **причина и предложение:** не «плохо», а «вынесем 2000 в константу — маркетинг поменяет порог, и придётся искать по файлу»;
- **пометка важности:** блокер (нельзя вливать), совет, вопрос, мелочь;
- **похвала:** «удачно выделил функцию» — сигнал, что здесь ничего менять не надо.

| Так не надо | Так лучше |
| --- | --- |
| «Тут всё неправильно, переделай» | «Блокер: в строке 14 условие `sum > 3000`, а для Бишкека порог включительный. При сумме ровно 3000 в Оше доставка станет платной. Добавим тест на 3000?» |

Принимать замечания — тоже навык. Критикуют код, а не вас; ревью — бесплатный урок. Не оправдывайтесь, а
выясняйте: если ревьюер спросил «почему так?», значит, из кода это не видно, и ответ должен оказаться в самом коде
(комментарий «почему» или лучшее имя), а не только в чате. Отвечайте на каждый комментарий: «исправил» или «не
согласен, потому что…». Не сошлись — позовите третьего; споры о стиле оставьте линтеру.

## Технический долг: кредит, проценты по которому платит каждая задача

Иногда сделать грязно — осознанное решение: завтра выставка, и функция нужна любой ценой. Это нормально, если помнить,
что вы взяли **технический долг** — кредит: время получили сейчас, а платить будете позже и с процентами. Тело долга —
сэкономленное время; проценты — замедление каждой следующей задачи в этом месте: костыль приходится обходить,
объяснять новичкам, бояться трогать. Пока долг не погашен, проценты капают с каждой задачи.

    A["Быстрый костыль<br/>к дедлайну"] --> B["Каждая следующая<br/>задача дольше"]

<BusinessNote>
Посчитаем при ставке 500 сом в час. Костыль сэкономил рабочий день: 8 часов, или 4 000 сом. Но теперь каждая
следующая задача в модуле длиннее на 2 часа — это 1 000 сом процентов. За год в модуле делают около 12 задач:
12 000 сом процентов за кредит в 4 000 сом, и счёт растёт. Плановое погашение — два дня на рефакторинг модуля —
стоит 8 000 сом и окупается после восьмой задачи (8 000 ÷ 1 000); дальше команда экономит те же 1 000 сом на каждой задаче.
</BusinessNote>

Управлять долгом можно, как кредитом:

- **Различайте виды.** Осознанный долг — вы о нём знаете, записали задачу «убрать костыль до 1 ноября»: кредит на оборудование с графиком возврата. Неосознанный — никто не помнит, откуда костыль: микрозайм до зарплаты, удобный сегодня и разорительный через месяц.
- **Записывайте.** Задача в трекере или `TODO` со сроком и автором: о долге, которого не видно, не вспоминают.
- **Платите регулярно.** Многие команды закладывают в каждую итерацию долю времени на уборку (ориентир — 10–20%) и действуют по правилу скаута: оставь код чуть чище, чем нашёл.
- **Не доводите до банкротства.** Когда команда только платит проценты, возникает соблазн «переписать всё с нуля» — об этой ловушке ниже.

## Практика: сделай руками и проверь себя

Три задания — от простого к самостоятельному. Первые два проверяйте в консоли браузера (F12, вкладка Console)
или в Node. Если консоль ругается на повторное объявление `const`, обновите страницу.

### Задание 1. Верните коду имена

Функция получает строки корзины `l` (количество `q` и цена `pr` — имена полей диктует сервер, у себя их менять
нельзя) и порог крупного заказа `p`. Если сумма больше порога, вычитается скидка 500 сом. Переименуйте функцию,
параметры и переменные, дайте имя числу 500, а поля `q` и `pr` переведите в понятные имена на входе.

```js
function calc(l, p) {
  let t = 0;
  for (let i = 0; i < l.length; i++) {
    const d = l[i].q * l[i].pr;
    t = t + d;
  }
  const x = t > p ? t - 500 : t;
  return x;
}
```

Образец ответа:

```js
const BIG_ORDER_DISCOUNT = 500; // сом

function calculateTotal(cartLines, bigOrderThreshold) {
  let subtotal = 0;
  for (const line of cartLines) {
    const quantity = line.q; // q и pr диктует сервер,
    const price = line.pr; // переводим их здесь, на входе
    subtotal += quantity * price;
  }
  return subtotal > bigOrderThreshold ? subtotal - BIG_ORDER_DISCOUNT : subtotal;
}
```

**Ожидаемо:** три вызова дают те же числа, что и старая `calc`, — поведение не изменилось. Ваши имена могут
отличаться; критерии: по имени понятно, что внутри; функция названа глаголом; односимвольных имён нет; числа 500
в теле функции нет.

```js
calculateTotal([], 1000); // 0: пустая корзина
calculateTotal([{ q: 1, pr: 1000 }], 1000); // 1000: ровно порог, сравнение строгое
calculateTotal([{ q: 2, pr: 300 }, { q: 1, pr: 700 }], 1000); // 800: 1300 минус 500
```

### Задание 2. Найдите запахи кода

**Запах кода** (code smell) — признак, что здесь, возможно, прячется проблема: код работает, но «пахнет». Перед вами
расчёт зарплаты (ставки условные): `e` — сотрудник, `t` — тип (1 — штатный), `y` — стаж в годах, `s` — оклад,
`b` — премия, `m` — месяц. Найдите не меньше пяти запахов:

```js
function calc(e, m) {
  var r = 0;
  if (e.t == 1) {
    if (e.y > 5) {
      r = e.s * 1.2;
    } else {
      r = e.s * 1.1;
    }
  } else {
    r = e.s;
  }
  // прибавляем премию
  r = r + e.b;
  // вычитаем налог
  r = r - r * 0.1;
  db.save(e.id, m, r);
  sendEmail(e.email, 'Зарплата за ' + m + ': ' + r + ' сом');
  return r;
}
```

**Ожидаемо:** пять и больше из семи — задание выполнено.

| № | Запах | Чем лечить |
| --- | --- | --- |
| 1 | Непонятные имена: `calc`, `e`, `r`, `t`, `y` | осмысленные имена |
| 2 | Магические числа: `1`, `5`, `1.2`, `1.1`, `0.1` | константы `FULL_TIME`, `INCOME_TAX_RATE` |
| 3 | Пирамида вложенных if | ранний выход или таблица ставок |
| 4 | Много дел в одной функции: считает, пишет в базу, шлёт письмо | расчёт отдельно, побочные действия отдельно |
| 5 | Комментарии «что»: «прибавляем премию» | именованные шаги вместо комментариев |
| 6 | Переменная-хамелеон: `r` — то оклад, то с премией, то «на руки» | по переменной на каждый смысл |
| 7 | `var` и `==` | `const`, `let`, `===`: найдёт линтер |

Пункт 4 особенно коварен: функция зовётся `calc`, а письма рассылает — первый же тест отправит их настоящим
сотрудникам. И граничный вопрос: что со стажем ровно 5 лет? Условие `e.y > 5` даёт повышенную ставку только с
шестого года. Спросите у бизнеса, так ли задумано, и зафиксируйте ответ тестом.

### Задание 3. Код-ревью по чек-листу

Обменяйтесь с одногруппником кодом — подойдёт решение тренажёра `deliveryCost`. Нет напарника — возьмите свой код

**Ожидаемо:** на руках письменное ревью без оценок личности, блокеры отделены от мелочей, автор по каждому пункту

## Граничные случаи: где всё ломается

- **1. Рефакторинг «чуть-чуть поправил» — без тестов.** Ситуация: запутанную `deliveryCost` «только подчистили» и склеили ветки; руками проверили Бишкек и Ош — верно. Что происходит: заказ из Каракола возвращает `undefined`, и страница оплаты пишет «Итого: NaN сом»; заметили через три дня — редкая ветка жила без присмотра. Почему: глаз проверяет две-три дороги из десятка. Как правильно: сначала тесты на каждую ветку и границы (включая «любой другой город»), потом маленькие шаги; отчёт о покрытии из лекции «Тестирование» покажет непроверенные ветки.
- **2. Переименовали поле у себя, а сервер присылает старое.** Ситуация: «найти и заменить» поменяло `pr` на `price` по всему проекту, тесты зелёные, а на сайте цена `NaN`. Что происходит: сервер по-прежнему отдаёт JSON с полем `pr`, поэтому `item.price` — `undefined`, а `undefined * 2` — `NaN`. Почему: имя поля — договорённость двух программ, замена меняет лишь вашу сторону, а тестовые данные поправили вместе с кодом. Как правильно: переименовывать на границе — функция-**адаптер** («переводчик») превращает сырой ответ в удобные объекты; в тестах держите образец настоящего ответа; типы из лекции «TypeScript» помогут описать его форму.

```js
// граница между сервером и вашим кодом: имена переводим в одном месте
function fromServer(raw) {
  return { id: raw.id, price: raw.pr, quantity: raw.q };
}
```

- **3. «Общая» функция обросла флагами.** Ситуация: расчёт премии менеджера и курьера выглядел одинаково, и его вынесли в `calcBonus(person, sum)`; через месяц она стала `calcBonus(person, sum, isCourier, isNight, useCap)`. Что происходит: правка для одних ломает других (после «починки» ночного коэффициента просели премии менеджеров). Почему: случаи только выглядели одинаково, а менялись по разным причинам — это два знания, а не одно. Как правильно: первый флаг-переключатель — тревожный сигнал; под тестами верните две функции, а общим оставьте лишь действительно общее, например `percentOf(sum, percent)`.
- **4. Комментарий устарел и врёт.** Ситуация: над условием написано «бесплатная доставка от 2000 сом», а константа `FREE_DELIVERY_FROM` давно равна 2500. Что происходит: новый разработчик верит комментарию и «чинит» код под него — магазин раздаёт доставку на заказы от 2000 до 2500 сом. Почему: комментарии не проверяют ни тесты, ни компилятор. Как правильно: не дублируйте в комментарии то, что уже сказано именем и значением; пишите причину и дату решения — то, что не устаревает; меняете код — меняйте комментарий в том же коммите.
- **5. «Перепишем всё с нуля».** Ситуация: четыре разработчика решили переписать запутанный модуль заказов «за два месяца». Что происходит: старая версия живёт и получает новые требования, а новую нужно довести до тех же возможностей, включая сотни незаписанных исправлений; через полгода она не готова, а новых функций не вышло ни одной: 4 × 90 000 × 6 = 2 160 000 сом зарплат без результата для клиентов. Почему: в старом коде осело знание, которого нет ни у кого в голове; без тестов не узнать, что потеряно. Как правильно: обложить старый код тестами и заменять по кусочку, выкладывая рабочую версию каждую неделю — тот же рефакторинг, только крупнее.
