## Введение

Ни один реальный проект не пишут «с нуля». Дата-пикер, работа с Excel, отправка писем, графики —
всё это уже написано и лежит в открытом доступе. Современная разработка — это на 80% сборка из чужих
деталей. В реестре npm — больше 3 миллионов пакетов, и каждую неделю их скачивают миллиарды раз.
Разберёмся, как эти детали подключаются, как ими управлять и где спрятаны грабли, из-за которых
компании теряют деньги.

<BusinessNote>
Зависимости — это цепочка поставок вашего продукта, только цифровая. Как в закупках: чем больше
поставщиков, тем быстрее вы соберёте товар, но тем больше риск, что один из них подведёт.
Посчитаем на сомах: библиотека для чтения Excel-файлов — это месяц-два работы разработчика. При
зарплате мидла в Бишкеке порядка 120 000 сом в месяц своё решение обойдётся в 150 000–250 000 сом
плюс вечная поддержка. Готовый пакет подключается за 30 секунд и 0 сом. Аналитик, который понимает,
что такое `package.json` и lock-файл, способен оценить техдолг проекта и юридические риски по
лицензиям — а это уже разговор уровня руководителя, а не джуниора.
</BusinessNote>

**Что вы узнаете:**

- зачем делить код на модули и как работают export и import
- что лежит в package.json и зачем он проекту
- что значат знаки `^` и `~` в версии пакета и как читаются семантические версии
- что такое node_modules и lock-файл и почему у всей команды должна получаться одна и та же сборка
- чем платят за чужой код: размер бандла, уязвимости и лицензии
- как пощупать экосистему npm руками и не попасться на граничные случаи

Пригодится из прошлых лекций: «Объекты и JSON».

## Зачем вообще модули

Пока в файле 30 строк, всё хорошо. Когда их 3 000 — файл невозможно читать, два человека не могут
править его одновременно, а любое имя переменной рискует конфликтовать с другим. **Модуль** — это
отдельный файл, который сам решает, что показать наружу, а что оставить внутри.

Работает это через две команды: `export` («забирайте это») и `import` («дайте мне вон то»).

```js
// файл tax.js — маленький модуль расчёта налога
const RATE = 0.12;             // ставка НДС в Кыргызстане — 12%; наружу не видна

export function withVat(price) {
  return price * (1 + RATE);
}

export function vatOnly(price) {
  return price * RATE;
}
```

```js
// файл invoice.js — тот, кто пользуется модулем
import { withVat, vatOnly } from './tax.js';

console.log(withVat(1000)); // 1120 — цена в сомах с НДС
console.log(vatOnly(1000)); // 120 — сколько уйдёт в ГНС
```

Обратите внимание: `RATE` наружу не экспортирован, поэтому файл `invoice.js` его просто не видит.
Это и есть главная ценность модуля — **инкапсуляция**: наружу торчит короткий понятный интерфейс, а
внутренности можно переписать, не сломав чужой код. Если ГНС завтра поменяет ставку, вы исправите
одну константу в одном файле — и все счета по всему проекту пересчитаются правильно.

<Callout title="Именованный экспорт и export default">
`export function withVat(...)` — **именованный** экспорт: импортируется строго по имени, в фигурных
скобках. `export default something` — «главная вещь модуля», её при импорте можно назвать как угодно:
`import calc from './tax.js'`. Правило простое: если модуль отдаёт одну сущность — `default`, если
несколько — именованные. Смешивать без нужды не стоит, это путает читателя.
</Callout>

Один нюанс истории: раньше в Node.js писали `const fs = require('fs')` — это старый формат
**CommonJS**. Сейчас стандарт — **ESM** (`import`/`export`), он же работает в браузере. В старых
проектах вы встретите оба; для нового кода выбирайте `import`.

## package.json — паспорт проекта

В корне любого JS-проекта лежит файл `package.json`. Это одновременно паспорт, список закупок и
пульт управления:

```json
{
  "name": "shop-analytics",
  "version": "1.4.0",
  "type": "module",
  "scripts": {
    "dev": "next dev",
    "test": "vitest run",
    "build": "next build"
  },
  "dependencies": {
    "date-fns": "^3.6.0",
    "zod": "^3.23.8"
  },
  "devDependencies": {
    "vitest": "^2.0.5",
    "typescript": "^5.5.4"
  }
}
```

Что здесь важно понимать:

- **`scripts`** — короткие имена для длинных команд. Вместо того чтобы помнить точную команду сборки,
  вся команда пишет `pnpm build`. Новый разработчик открывает этот раздел и сразу видит, что вообще
  умеет проект.
- **`dependencies`** — пакеты, нужные приложению *в работе* (например, библиотека дат, которая
  форматирует «14 августа 2026» на странице).
- **`devDependencies`** — нужны только *при разработке*: тесты, линтеры, компилятор TypeScript.
  У пользователя в браузере их нет, в итоговую сборку они не попадают.

<Callout title="Почему разделение dev/prod — это не формальность">
Всё, что попало в `dependencies`, едет на сервер и часто в браузер пользователю. Затащили туда
тестовый фреймворк — раздули сборку на мегабайты, замедлили сайт и увеличили площадь для атаки.
Лишний мегабайт JavaScript — это лишние секунды загрузки на мобильном интернете где-нибудь по дороге
в Каракол, а для интернет-магазина каждая секунда загрузки — минус несколько процентов конверсии.
Правило: «нужно, чтобы продукт *работал*» → `dependencies`; «нужно, чтобы продукт *разрабатывался*»
→ `devDependencies`.
</Callout>

## Семантические версии: что значат `^3.6.0` и `~3.6.0`

Номер версии в npm — это не просто число, а обещание. Формат называется **semver** (semantic
versioning) и состоит из трёх частей:

```text
   3   .   6   .   0
MAJOR   MINOR   PATCH
```

| Часть | Когда увеличивают | Что это значит для вас |
| --- | --- | --- |
| **PATCH** (0 → 1) | починили баг | можно обновляться смело |
| **MINOR** (6 → 7) | добавили возможность, старое работает | можно обновляться смело |
| **MAJOR** (3 → 4) | **сломали совместимость** | старый код может перестать работать, читайте инструкцию по миграции |

Значок перед номером говорит, какие обновления вы разрешаете ставить автоматически:

- `^3.6.0` («карет») — разрешены любые версии до 4.0.0: 3.6.1, 3.7.0, 3.19.2. Запрещена 4.0.0.
- `~3.6.0` («тильда») — разрешены только патчи: 3.6.1, 3.6.9. Запрещена 3.7.0.
- `3.6.0` — точно эта версия, ничего другого.

Проверьте, что правило усвоилось: напишите функцию, которая решает, можно ли автоматически поставить
новую версию по правилу карета.

<Callout title="Ловушка версии 0.x">
Для версий, начинающихся с нуля (`0.7.3`), правила semver фактически не действуют: авторы считают
такую библиотеку незрелой и могут ломать совместимость в любом релизе. Если в проекте много
зависимостей вида `0.x` — это сигнал нестабильности, о котором стоит сказать вслух на планировании.
</Callout>

## node_modules и lock-файл

Когда вы пишете `pnpm add date-fns`, происходит следующее:

1. Пакетный менеджер идёт в реестр npm (это гигантский общий склад пакетов).
2. Скачивает `date-fns`, а вместе с ним — **все пакеты, от которых зависит сам `date-fns`**. Те тянут
   свои, и так далее. Это **транзитивные зависимости**.
3. Складывает всё в папку `node_modules` — ту самую, которая весит сотни мегабайт и стала мемом.
4. Записывает **точные** версии всего дерева в **lock-файл** (`package-lock.json`, `pnpm-lock.yaml`).

<Mermaid
  title="Что происходит при pnpm add date-fns"
  chart={`flowchart TD
    A["pnpm add date-fns"] --> B["Идём в реестр npm"]
    B --> C["Читаем package.json пакета date-fns"]
    C --> D{"Есть свои зависимости?"}
    D -->|"да"| E["Скачиваем каждую транзитивную зависимость"]
    E --> D
    D -->|"нет, дерево построено"| F["Складываем всё в node_modules"]
    F --> G["Записываем точные версии в lock-файл"]`}
/>

Масштаб бедствия оцените в числах: свежесозданный проект на Next.js — это уже порядка 300 пакетов
и 400–500 МБ в `node_modules`, хотя вы сами написали 10 строк. Вы попросили одну библиотеку — она
привела с собой всю свою «родню».

Зачем нужен lock-файл: в `package.json` написано `^3.6.0` — это диапазон. Без фиксации вы поставите
проект сегодня и получите 3.6.0, а коллега поставит завтра и получит 3.7.1. Отсюда классическое
«на моей машине работает». Lock-файл прибивает всё дерево гвоздями: у всех — до последней цифры
одинаковые версии.

<Callout title="Три практических правила">
1. **Lock-файл коммитят в репозиторий.** Всегда. Это часть проекта, а не мусор.
2. **`node_modules` не коммитят.** Эта папка полностью восстанавливается из lock-файла командой
   установки и попадает в `.gitignore`.
3. На сервере сборки ставят зависимости строго **по lock-файлу** (`npm ci`, `pnpm install --frozen-lockfile`),
   чтобы сборка была воспроизводимой и никакое случайное обновление не приехало в продакшен.
</Callout>

## Риски: чем платят за чужой код

Экономия времени реальна, но у неё есть цена. Четыре риска, которые нужно уметь называть.

**1. Уязвимости.** В зависимости находят дыру — уязвимым автоматически становится ваш продукт.
Команда `npm audit` (или `pnpm audit`) сверяет ваше дерево зависимостей с базой известных уязвимостей
и показывает, что именно дырявое и насколько это серьёзно. Проверять стоит регулярно, а не раз в год.

**2. Атака на цепочку поставок.** Злоумышленник получает доступ к популярному пакету и подкладывает
в него вредоносный код — и тот автоматически приезжает всем, кто обновился. Это не страшилка, а
регулярная практика, у которой есть даты и суммы:

- **left-pad, март 2016.** Автор удалил из реестра свой пакет из 11 строк кода. Через транзитивные
  зависимости от него зависели тысячи проектов — сборки сломались по всему миру, включая
  инфраструктуру крупнейших компаний. Одиннадцать строк остановили заметную часть индустрии на часы.
- **event-stream, 2018.** Пакет с примерно 2 миллионами скачиваний в неделю передали «помощнику»,
  который вшил в него код для кражи биткоин-кошельков. Вредонос месяц ехал в тысячи продуктов
  вместе с обычным `install`.
- **Тайпсквоттинг.** Злоумышленники публикуют пакеты с именами-опечатками (`reqests` вместо
  `requests`, `lodahs` вместо `lodash`) и ждут, когда кто-то промахнётся клавишей. Внутри — код,
  ворующий переменные окружения с ключами и паролями.

Защита: lock-файл, осторожность с автообновлениями, внимательность к именам при установке и отказ
от пакетов на три строчки кода.

**3. Лицензии.** У каждого пакета есть лицензия — юридическое разрешение на использование. MIT,
Apache-2.0, BSD — либеральные, для бизнеса безопасные. А вот копилефт-лицензии семейства GPL могут
требовать открыть исходники вашего продукта. Для коммерческого проекта это не мелочь, а вопрос
к юристам — и хорошо, если он всплывёт до релиза, а не после.

**4. Заброшенность.** Пакет, у которого последний релиз три года назад и полторы сотни открытых
issues, однажды перестанет работать с новой версией платформы — чинить придётся вам.

<BusinessNote>
Мини-чеклист выбора пакета — годится и как аргумент на код-ревью: сколько установок в неделю; когда
был последний релиз; закрываются ли issues; какая лицензия; сколько своих зависимостей он тянет;
сколько килобайт добавит в сборку. Если пакет заменяется десятью строками своего кода — напишите
свои десять строк. Час разработчика стоит порядка 700–1000 сом; разбирательство с одним взломанным
или брошенным пакетом легко съедает неделю — 30 000–40 000 сом прямых затрат, не считая простоя.
</BusinessNote>

## Как это выглядит в жизни

Типичный набор команд, который вы будете видеть в README проектов:

```bash
pnpm install          # поставить всё по lock-файлу
pnpm add date-fns     # добавить пакет в dependencies
pnpm add -D vitest    # добавить в devDependencies (только для разработки)
pnpm remove lodash    # удалить пакет
pnpm outdated         # показать, где вышли новые версии
pnpm audit            # проверить известные уязвимости
```

Отдельно про менеджеры: `npm` идёт в комплекте с Node.js, `pnpm` и `yarn` — альтернативы. `pnpm`
хранит все пакеты в одном общем хранилище на диске и раскладывает по проектам ссылки, поэтому ставит
быстрее и занимает в разы меньше места. Формат `package.json` у всех одинаковый — меняется только
имя команды в терминале.

## Практика: пощупайте экосистему руками

### Упражнение 1. Аудит пакета за пять минут

Пройдите чеклист выбора пакета на реальном примере — без установки чего-либо, только браузер.

1. Откройте сайт `npmjs.com` и найдите через поиск пакет `dayjs` (маленькая библиотека дат).
2. На странице пакета найдите в правой колонке блок статистики. Вы должны увидеть: **Weekly
   Downloads** — больше 10 миллионов, **License** — MIT, **Last publish** — не старше года.
3. Найдите строку **Dependencies**. Ожидаемый результат: **0** — dayjs не тянет за собой никого,
   это одна из причин его популярности.
4. Теперь найдите пакет `moment` (старая библиотека дат) и прочитайте первый абзац его описания.
   Вы должны увидеть честное предупреждение авторов, что проект в режиме поддержки и для новых
   проектов его брать не советуют — при миллионах скачиваний в неделю!

Самопроверка: если вы нашли все четыре пункта, вы только что сделали то, что делает техлид перед
добавлением зависимости. Вывод из упражнения: популярность (скачивания) и живость (свежие релизы) —
разные вещи, смотреть нужно на обе.

### Упражнение 2. Найдите четыре проблемы в чужом package.json

Представьте: вам передали проект службы доставки. В репозитории лежит папка `node_modules`,
lock-файла нет, а `package.json` выглядит так:

```json
{
  "name": "bishkek-delivery",
  "version": "1.0.0",
  "dependencies": {
    "vitest": "^2.0.5",
    "left-pad": "^1.3.0",
    "pdf-magic": "^0.2.7"
  }
}
```

Найдите минимум четыре проблемы, запишите их — потом сверьтесь.

<Callout title="Самопроверка к упражнению 2">
1. `vitest` — тестовый фреймворк, ему место в `devDependencies`, иначе он поедет в продакшен-сборку.
2. `left-pad` — пакет на 11 строк (тот самый!): дешевле написать свои строки, чем нести риск.
3. `pdf-magic` версии `0.2.7` — зависимость `0.x`: semver не действует, любой релиз может всё сломать.
4. Всё наоборот с файлами: `node_modules` закоммичен (сотни мегабайт мусора в истории), а lock-файла
   нет — установка у каждого разработчика даст разные версии. Должно быть ровно наоборот.
</Callout>

## Граничные случаи: где всё ломается

**Версия `0.0.1` при первой публикации.** Ситуация: автор выложил новый пакет с номером `0.1.0`.
Что происходит: правило carret (`^`) для версий `0.x.y` разрешает обновляться только внутри того же
минора (например, `^0.1.0` пускает `0.1.9`, но не `0.2.0`) — semver здесь работает иначе, чем для
`1.x` и выше. Почему: спецификация semver считает всё, что ниже `1.0.0`, черновиком без гарантий
совместимости. Как правильно: относиться к `0.x`-зависимости как к потенциально ломающейся в любом
обновлении и явно фиксировать версию, а не полагаться на `^`.

**Циклический импорт.** Ситуация: `a.js` делает `import` из `b.js`, а `b.js` — из `a.js`. Что
происходит: один из модулей на момент своей загрузки получает от другого не готовый экспорт, а
`undefined` или неполный объект — код падает в рантайме на ровном месте. Почему: ESM грузит модули
по цепочке, и второй модуль в цикле физически не может дождаться, пока первый доисполнится. Как
правильно: вынести общую часть в третий, независимый модуль, от которого зависят оба.

**Два пакета в дереве требуют разные мажорные версии одной библиотеки.** Ситуация: пакет A просит
`react@^17`, пакет B — `react@^18`. Что происходит: пакетный менеджер не может подставить одну общую
версию, которая устроит обоих, и либо ставит несколько копий библиотеки рядом (раздувает сборку и
может задвоить состояние), либо падает с ошибкой конфликта версий. Почему: semver-диапазоны с разными
мажорами по определению несовместимы. Как правильно: смотреть `pnpm outdated` / сообщение об ошибке
и обновлять либо A, либо B до версии, поддерживающей общий мажор.

**Пустой или битый `package.json`.** Ситуация: файл случайно сохранили без содержимого или с
незакрытой скобкой. Что происходит: любая команда пакетного менеджера (`install`, `add`, `build`)
падает с ошибкой парсинга JSON ещё до того, как что-либо скачается. Почему: `package.json` — не
документация, а конфиг, который парсится буквально; JSON не прощает висячих запятых и незакрытых
скобок. Как правильно: держать файл под контролем версий и проверять валидность (`node -e
"require('./package.json')"`) перед коммитом.
