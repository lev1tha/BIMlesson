## Введение

Когда программа просит данные из сети — например, свежий курс доллара к сому, — ответ приходит не
мгновенно. Для процессора, который складывает числа за наносекунды, ожидание сети — целая вечность.
Если тупо стоять и ждать, интерфейс «замёрзнет»: кнопки не нажимаются, страница не листается.
Поэтому в JavaScript все сетевые операции **асинхронны** (от греческого «а-» — «не» и «синхронос» —
«одновременный»): код не стоит на месте, а продолжает работать и обрабатывает ответ, когда тот придёт.

<BusinessNote>
Каждый обмен данными между системами — это запрос к **API** (application programming interface,
«интерфейс для программ»: договорённость о том, как одна программа запрашивает данные у другой).
Курс валют, статус платежа, остатки на складе в 1С, заказы в CRM — всё это асинхронные запросы.
Для бизнеса их скорость — деньги: по оценкам Google и Amazon, лишние 100 миллисекунд задержки
отнимают порядка 1% продаж. Для интернет-магазина в Бишкеке с оборотом 3 млн сом в месяц это минус
30 000 сом — просто из-за медленного API. Аналитик, который понимает, как устроены эти запросы,
читает интеграции, находит «узкое место» и объясняет, почему «данные подтягиваются с задержкой».
</BusinessNote>

**Что вы узнаете:**

- почему для процессора сеть — целая вечность и зачем вообще нужна асинхронность
- как событийный цикл успевает всё, хотя JavaScript делает только одно дело за раз
- как промисы и async/await спасают от «ада колбэков»
- как запросить данные через fetch и почему статус 404 для него не считается ошибкой
- как отправить данные методом POST и ускорить загрузку через Promise.all
- как показать пользователю три состояния: загрузка, ошибка и повтор

Пригодится из прошлых лекций: «Объекты и JSON», «Условия и логика».

## Насколько сеть медленная: почувствуйте масштаб

Главная причина, по которой асинхронность вообще существует, — чудовищная разница скоростей между
процессором и сетью:

| Операция | Время | Медленнее сложения |
| --- | --- | --- |
| Сложение двух чисел в процессоре | ~1 наносекунда | — |
| Чтение из оперативной памяти | ~100 наносекунд | в 100 раз |
| Чтение файла с SSD | ~0,1 миллисекунды | в 100 000 раз |
| Запрос к серверу в Бишкеке (зона .kg) | ~10–30 мс | в десятки миллионов раз |
| Запрос к серверу в Европе | ~120–150 мс | в 150 миллионов раз |
| Запрос по мобильному 3G из маршрутки | ~300–800 мс | почти в миллиард раз |

Переведём в человеческий масштаб: если бы сложение занимало 1 секунду, то запрос из Бишкека к серверу
во Франкфурте длился бы почти **5 лет** (150 миллионов секунд). Представьте сотрудника, который 5 лет
сидит без дела, ожидая один ответ по почте, — вот что такое синхронное ожидание сети для процессора.

## Синхронно против асинхронно

**Синхронный** код выполняется строго по очереди: строка за строкой, каждая ждёт предыдущую.
**Асинхронный** — умеет «отложить» долгую операцию и не блокировать остальное.

<Callout title="Аналогия: кофейня">
Синхронно — вы стоите у кассы и ждёте, пока сварят ваш кофе, никого больше не обслуживают. Асинхронно
— вам дают пейджер, вы отходите, касса обслуживает других, а когда кофе готов — пейджер пищит. Второй
способ куда эффективнее, и именно так работает сеть в коде.
</Callout>

## setTimeout: простейшая асинхронность

`setTimeout` откладывает выполнение на потом. Обратите внимание на порядок вывода:

<Sandbox code={`console.log('1. старт');

setTimeout(() => {
  console.log('3. прошло 2 секунды');
}, 2000);

console.log('2. эта строка не ждёт таймер');
`} />

Строка «2» выведется **раньше** «3», хотя написана до неё: программа не стала ждать таймер, а пошла
дальше. Функция внутри `setTimeout` — это **колбэк** (callback, «перезвони мне»): «вызови меня, когда
придёт время». Колбэки — исторически первый способ работы с асинхронностью, но у него есть болезнь:
когда после первого ответа нужен второй запрос, а после второго — третий, колбэки вкладываются друг
в друга «лесенкой». Этот антипаттерн так и называют — **ад колбэков** (callback hell). Именно от него
спасают промисы, о которых чуть ниже.

## Событийный цикл: как JavaScript всё успевает

Как программа «не ждёт», если JavaScript выполняет только одну вещь за раз? Внутри движка работает
**событийный цикл** (event loop) — диспетчер, который распределяет задачи:

```text
        ┌────────────────────────────────┐
        │  Стек вызовов: код, который    │  ← выполняется прямо сейчас
        │  выполняется в данный момент   │
        └───────────────┬────────────────┘
                        │ стек пуст? берём следующую задачу
        ┌───────────────▼────────────────┐
        │  Событийный цикл (диспетчер)   │
        └───────────────▲────────────────┘
                        │
        ┌───────────────┴────────────────┐
        │  Очередь задач: сработавшие    │  ← сюда падают колбэки таймеров,
        │  таймеры, ответы сети, клики   │     ответы fetch, клики мыши
        └────────────────────────────────┘
```

Правило одно: колбэк из очереди попадёт в работу **только когда текущий код полностью закончится**.

  title="Событийный цикл: путь колбэка от таймера до консоли"
  chart={`flowchart TD
    A["Код вызывает setTimeout(fn, 0)"] --> B["Таймер стартует в фоне браузера"]

/>

Это как регистратура в поликлинике: даже если ваша очередь подошла (таймер сработал), вы зайдёте в
кабинет только после того, как врач закончит с текущим пациентом (стек вызовов опустеет).

Проверьте на опыте: таймер на 0 миллисекунд всё равно ждёт, пока доработает весь скрипт — даже цикл
на миллион шагов:

<Sandbox code={`console.log('А: начало скрипта');

setTimeout(function () {
  console.log('Г: таймер на 0 мс — а вывелся последним!');
}, 0);

console.log('Б: скрипт продолжается');

let сумма = 0;
for (let i = 1; i <= 1000000; i++) {
  сумма += i;
}
console.log('В: цикл на миллион шагов закончен, сумма = ' + сумма);
`} />

<Callout title="Практический вывод">
`setTimeout(..., 0)` означает не «выполни сейчас», а «выполни, как только освободишься». И наоборот:
тяжёлый синхронный цикл в коде страницы блокирует ВСЁ — клики, анимации, ответы сети. Если сайт
«подвисает» при нажатии кнопки, чаще всего кто-то занял стек вызовов долгой синхронной работой.
</Callout>

## Промисы: обещание результата

**Промис** (Promise) — это объект-«обещание»: «результата ещё нет, но он будет позже — или будет
ошибка». Как номерок в химчистке: сам костюм вам не отдали, но по номерку вы его получите, когда
будет готов. У промиса три состояния:

- **pending** («ожидание») — операция ещё идёт;
- **fulfilled** («исполнен») — результат готов;
- **rejected** («отклонён») — случилась ошибка.

Реакцию вешают через `.then()` (на успех) и `.catch()` (на ошибку), а `.finally()` сработает в любом
случае — удобно, например, спрятать спиннер загрузки:

```js
получитьКурс()
  .then(курс => console.log('Курс:', курс))
  .catch(ошибка => console.log('Не удалось:', ошибка))
  .finally(() => console.log('Запрос завершён — прячем спиннер'));
```

## async / await: промисы, но читаемо

`async/await` — современный синтаксис, который делает асинхронный код похожим на обычный,
последовательный:

```js
async function показатьКурс() {
  try {
    const курс = await получитьКурс(); // ждём результат промиса
    console.log('Курс:', курс);
  } catch (ошибка) {
    console.log('Не удалось:', ошибка);
  }
}
```

`await` «ждёт» промис, не блокируя всю программу: пока функция стоит на `await`, событийный цикл
спокойно обрабатывает клики и другие задачи. Два правила: `await` работает только внутри функции со
словом `async`, а ошибки ловят обычным `try/catch` — тем же, что и в синхронном коде.

## HTTP за две минуты: методы и статусы

Прежде чем делать запросы, разберёмся, на каком языке программы разговаривают с серверами. **HTTP**
(HyperText Transfer Protocol) — протокол, то есть свод правил разговора: клиент отправляет **запрос**
(адрес + метод + иногда данные), сервер возвращает **ответ** (статус-код + данные). Методы — это
«глаголы» запроса:

| Метод | Смысл | Пример из жизни магазина |
| --- | --- | --- |
| **GET** | «дай данные» | открыть страницу товара, запросить курс валют |
| **POST** | «прими данные» | оформить заказ, отправить заполненную форму |
| **PUT / PATCH** | «обнови данные» | изменить количество товара в корзине |
| **DELETE** | «удали» | убрать товар из корзины |

Как запрос физически долетает до сервера через DNS и маршрутизаторы — тема курса «Вычислительные
системы». Здесь нам хватит главного: каждый запрос имеет метод, а каждый ответ — числовой статус.

## fetch: запрос к API

Реальные данные берут функцией `fetch` — она делает HTTP-запрос и возвращает промис с ответом.
Ответ обычно в **JSON** (текстовый формат данных из лекции про объекты), который разбирают в объект:

```js
async function загрузить() {
  const ответ = await fetch('https://api.shop.kg/rates'); // GET по умолчанию
  const данные = await ответ.json(); // разобрали JSON в объект
  console.log('Доллар:', данные.usd, 'сом'); // например: Доллар: 87.45 сом
}
```

Обратите внимание: `await` здесь два. Первый ждёт заголовки ответа от сервера, второй — дочитывает
и разбирает тело ответа (оно тоже приезжает не мгновенно).

## Капкан: для fetch статус 404 — не ошибка

Самая коварная особенность `fetch`, на которой ловятся даже опытные разработчики: **промис fetch
отклоняется только при сетевой ошибке**. Если сервер ответил — пусть даже статусом 404 или 500 —
промис считается успешным, и `catch` не сработает. С точки зрения `fetch` всё честно: запрос дошёл,
ответ пришёл. А что в ответе написано «такой страницы нет» — это уже ваша забота. Поэтому статус
проверяют руками через `response.ok` — оно равно `true` для статусов от 200 до 299:

```js
async function загрузитьТовар(id) {
  const ответ = await fetch('https://api.shop.kg/products/' + id);
  if (!ответ.ok) {
    throw new Error('Сервер ответил со статусом ' + ответ.status);
  }
  return await ответ.json();
}
```

Частые статусы, которые аналитик встречает в работе с API:

| Код | Название | Что означает на практике |
| --- | --- | --- |
| **200** | OK | всё хорошо, данные в теле ответа |
| **201** | Created | сервер принял POST и создал запись (заказ, платёж) |
| **301 / 302** | Redirect | адрес переехал навсегда / временно |
| **404** | Not Found | опечатка в адресе или запись удалена |
| **429** | Too Many Requests | вы запрашиваете слишком часто — API просит притормозить |
| **500** | Internal Server Error | баг на стороне сервера |
| **503** | Service Unavailable | сервер перегружен или на техработах |

<Callout title="Сетевая ошибка и ошибка сервера — разные вещи">
**Сетевая ошибка** — ответ вообще не пришёл: нет интернета, домен не найден, соединение оборвалось.
Только в этом случае промис `fetch` отклоняется и срабатывает `catch`. **Ошибка сервера** — ответ
пришёл, но со статусом 4xx/5xx: промис успешен, `catch` молчит, ловить нужно проверкой `response.ok`.
Надёжный код обрабатывает оба случая — и говорит пользователю разные вещи: «проверьте интернет»
против «на сервере неполадки, попробуйте позже».
</Callout>

## POST: отправляем данные на сервер

До сих пор мы только забирали данные. Чтобы отправить — оформить заказ, сохранить форму — используют
метод POST и передают `fetch` второй аргумент с настройками:

```js
async function отправитьЗаказ() {
  const ответ = await fetch('https://api.shop.kg/orders', {
    method: 'POST', // метод: принимаем данные
    headers: { 'Content-Type': 'application/json' }, // заголовок: «в теле — JSON»
    body: JSON.stringify({ товар: 'ноутбук', количество: 1, суммаСом: 64990 }),
  });
  if (!ответ.ok) {
    throw new Error('Заказ не принят, статус ' + ответ.status);
  }
  const созданный = await ответ.json();
  console.log('Номер заказа:', созданный.id); // сервер обычно отвечает статусом 201
}
```

Три обязательных ингредиента: `method` («глагол» запроса), `headers` (**заголовки** —
сопроводительная записка к посылке: здесь мы предупреждаем сервер, что внутри JSON) и `body` — сами
данные. Объект нельзя отправить «как есть»: его превращают в строку через `JSON.stringify` — тот
самый метод из лекции про объекты и JSON.

## Promise.all: параллельная загрузка

Представьте дашборд руководителя: курс валют (запрос занимает 280 мс), остатки на складе (350 мс)
и свежие заказы (400 мс). Если ждать по очереди — набегает 280 + 350 + 400 = **1030 мс**. Но эти
запросы не зависят друг от друга, значит их можно запустить одновременно и ждать только самый
медленный — **400 мс**, в два с половиной раза быстрее:

```js
// Медленно: каждый await ждёт предыдущий (1030 мс суммарно)
const курс = await загрузитьКурс();       // 280 мс
const остатки = await загрузитьОстатки(); // ещё 350 мс
const заказы = await загрузитьЗаказы();   // ещё 400 мс

// Быстро: все три стартуют сразу, ждём самый медленный (400 мс)
const [курс2, остатки2, заказы2] = await Promise.all([
  загрузитьКурс(),
  загрузитьОстатки(),
  загрузитьЗаказы(),
]);
```

`Promise.all` принимает массив промисов и возвращает один промис с массивом результатов — в том же
порядке, что и запросы.

<Callout title="Ложка дёгтя">
`Promise.all` отклоняется целиком, если упал хотя бы один промис: три запроса удались, четвёртый
вернул сетевую ошибку — вы не получите ничего. Когда нужны «все результаты, какие есть», используют
`Promise.allSettled`: он дожидается всех и для каждого сообщает, успех это или ошибка. Для дашборда
это правильнее: пусть виджет курса валют покажет ошибку, но остатки и заказы отобразятся.
</Callout>

## Загрузка, ошибка, повтор: три состояния интерфейса

Раз ответ приходит с задержкой, у любого экрана с данными есть минимум три состояния — и все три
надо нарисовать:

| Состояние | Что видит пользователь | Типовая ошибка разработчика |
| --- | --- | --- |
| Загрузка | спиннер или «скелетон» (серые плашки) | пустой белый экран |
| Успех | данные | — |
| Пусто | «Заказов пока нет» + подсказка, что делать | показать ошибку вместо честной пустоты |
| Ошибка | понятный текст + кнопка «Повторить» | вечный спиннер, который крутится навсегда |

<BusinessNote>
Это напрямую про конверсию. По данным Google, 53% мобильных пользователей закрывают страницу, если
она грузится дольше 3 секунд, — а у нас до 70% трафика с телефонов, часто на мобильном интернете.
Если магазин с выручкой 100 000 сом в день с мобильных теряет хотя бы каждого десятого посетителя
на «вечном спиннере» без кнопки «Повторить», это минус 10 000 сом в день — 300 000 сом в месяц.
Кнопка «Повторить» и понятное сообщение об ошибке — самые дешёвые «фичи» с прямым влиянием на выручку.
</BusinessNote>

### Задача 4: подглядите за реальными запросами

Инструмент разработчика показывает все запросы любой страницы — попробуйте на живом сайте:

1. Откройте любой новостной сайт или интернет-магазин.
2. Нажмите F12 и перейдите на вкладку **Network** (Сеть).
3. Обновите страницу клавишей F5 — таблица заполнится десятками строк. Каждая строка — один
   HTTP-запрос: страница, стили, картинки, данные.
4. Посмотрите колонку **Status**: у большинства строк должно стоять 200. Кликните на любую строку —
   справа откроется панель, где видно Request Method (обычно GET) и Status Code.
5. Включите фильтр **Fetch/XHR** — останутся только запросы к API, которые страница делает из
   JavaScript тем самым `fetch`. Вы должны увидеть, что сайт продолжает дёргать API даже после
   загрузки — подтягивает данные асинхронно.
6. Найдите выпадающий список **Throttling** (обычно написано No throttling), выберите Slow 3G и
   обновите страницу. Время запросов вырастет в разы — именно так ваш сайт видит студент в маршрутке
   по мобильному интернету. Ожидаемый вывод: страница, что грузилась за секунду, будет собираться
   10–20 секунд.

## Граничные случаи: где всё ломается

**Забыли await перед fetch.** Функция вернёт не данные, а сам объект-промис (Promise pending) —
и следующая строка попытается прочитать поле из промиса, а не из ответа сервера. Программа не
упадёт сразу, но выведет `undefined` или ошибку «cannot read property of undefined» чуть ниже по
коду, что сбивает с толку при отладке. Правильно: каждый вызов асинхронной функции внутри
async-функции сопровождать `await`, либо явно обрабатывать через `.then()`.

**Тело ответа пустое (204 No Content) или не JSON.** Если сервер вернул статус 204 («принято, но
возвращать нечего») или обычный текст вместо JSON, вызов `response.json()` упадёт с ошибкой парсинга
— промис `fetch` был успешен, а вот разбор тела ломается уже после проверки `response.ok`. Правильно:
проверять статус 204 отдельно и не звать `.json()`, либо оборачивать разбор в свой `try/catch`.

**Promise.all с одним провалившимся запросом.** Курс валют и остатки склада загрузились за 200 мс,
а заказы упали с сетевой ошибкой на 190-й миллисекунде — `Promise.all` отклонится целиком, и уже
готовые курс с остатками тоже пропадут для интерфейса. Почему: `Promise.all` устроен «всё или
ничего». Правильно: для дашборда с независимыми виджетами использовать `Promise.allSettled`, чтобы
получить и успехи, и ошибки по каждому запросу отдельно.

**Двойной клик по кнопке «Отправить заказ».** Пока первый `fetch('POST', ...)` ещё летит (200–400 мс),
пользователь на медленном 3G нажимает кнопку второй раз — уходит два одинаковых POST-запроса, и
магазин рискует создать два заказа на один товар. Почему: асинхронный код не блокирует интерфейс, а
кнопка по умолчанию остаётся кликабельной, пока ответ не пришёл. Правильно: сразу после первого клика
отключать кнопку (`disabled`) до получения ответа или ошибки.
