## Введение

Код, который «вроде работает», — это бомба замедленного действия. Настоящие команды сопровождают код
**автотестами**: программами, которые проверяют программу. Бытовая аналогия — чек-лист пилота перед
вылетом: пилот не «вроде помнит», что закрылки выпущены, — он проходит список пунктов, и каждый пункт
либо зелёный, либо красный. Автотесты — такой же чек-лист, только проходит его компьютер за секунды
и перед каждым «вылетом» кода. Кстати, автопроверка в наших задачах — это ровно они и есть.

<BusinessNote>
Тесты — это страховка бизнеса от дорогих ошибок. В индустрии есть правило «1–10–100»: баг, пойманный
при написании кода, стоит условные 100 сом времени разработчика; найденный тестировщиком перед
релизом — уже 1 000 сом (переоткрыть задачу, пересобрать, перепроверить); а доехавший до живых
клиентов — 10 000 сом и больше. Реальный масштаб: интернет-магазин в Бишкеке с 1 500 заказами в день
ошибся в округлении стоимости доставки на 7 сом в пользу клиента. Мелочь? За три недели — примерно
31 500 заказов и минус 220 000 сом, которых никто не заметил, потому что «код вроде работал».
Один юнит-тест на функцию доставки стоил бы 15 минут работы.
</BusinessNote>

**Что вы узнаете:**

- зачем нужны автотесты, если код можно проверить руками, и как они ловят регрессии
- как выглядит юнит-тест и настоящий тест-файл с describe, it и expect
- почему toBe не подходит для сравнения объектов и какой матчер выбрать
- какие граничные случаи чаще всего ломают код и как их проверить
- что такое пирамида тестирования и как читать покрытие кода, например «покрыто на 80%»
- как моки позволяют тестировать код, который зависит от сети и времени

Пригодится из прошлых лекций: «Отладка и ошибки», «Асинхронность и API».

## Зачем автотесты, если можно проверить руками

Проверить руками один раз — можно. Но программу меняют постоянно: новая фича, правка бага, обновление
библиотеки. После каждого изменения нужно убедиться, что не сломалось всё остальное, — а вручную
перепроверять 200 сценариев после каждой правки не будет ни один человек. **Автотест** делает это
за секунды и не устаёт:

- **Ловит регрессии.** **Регрессия** — это когда правка в одном месте случайно ломает другое.
  Как в старой квартире: починил кран на кухне — потекло в ванной. Тесты замечают «протечку» сразу.
- **Документирует.** По тестам видно, что функция должна делать в каждой ситуации, — это спецификация,
  которая не устаревает: устаревший тест сразу падает.
- **Даёт смелость.** Можно переписывать и ускорять код без страха: если тесты зелёные — поведение
  не изменилось.

Цифры для понимания масштаба: в средней команде прогон всех юнит-тестов занимает 10–60 секунд
и запускается автоматически при каждой попытке влить код. Если хотя бы один тест красный —
изменение просто не попадает в основную ветку. Ручная проверка того же объёма заняла бы у человека
несколько дней.

## Юнит-тест: проверяем одну функцию

**Юнит-тест** (unit test) проверяет один «кирпичик» — обычно функцию: даём вход, сверяем выход
с ожидаемым. Аналогия: прежде чем класть стену, каменщик проверяет каждый кирпич — целый ли.
Сердце теста — **утверждение** (assertion, произносится «ассёршн»): фраза «ожидаю, что результат
равен такому-то»:

```js
// функция
function sum(a, b) {
  return a + b;
}

// тест
expect(sum(2, 3)).toBe(5);   // ожидаю 5
expect(sum(-1, 1)).toBe(0);  // и для отрицательных
```

Если реальность разойдётся с ожиданием — тест «падает» красным и показывает, где именно.

## Как выглядит настоящий тест-файл: describe, it, expect

В реальных проектах тесты пишут с помощью специальных библиотек — **тест-раннеров** (test runner,
«запускальщик тестов»). Самые популярные в мире JavaScript — **Vitest** и **Jest**: синтаксис у них
практически одинаковый. Наш портал, кстати, тоже проверяет свои тренажёры тестами на Vitest —
это не учебная абстракция, а рабочий инструмент.

Тест-файл кладут рядом с кодом и называют по шаблону `имя.test.js`. Внутри — три кита:

| Слово | Что делает | Бытовая аналогия |
| --- | --- | --- |
| `describe` | группирует тесты одной функции или темы | папка-скоросшиватель с названием |
| `it` (или `test`) | один конкретный сценарий проверки | один пункт чек-листа |
| `expect` | утверждение «ожидаю, что…» | галочка или крестик напротив пункта |

Вот полноценный тест-файл для функции скидки из магазина на `shop.kg`:

```js
// discount.test.js — тесты для discount.js
import { describe, it, expect } from 'vitest';
import { applyDiscount } from './discount.js';

describe('applyDiscount — цена со скидкой', () => {
  it('считает скидку 10% от 2000 сом', () => {
    expect(applyDiscount(2000, 10)).toBe(1800);
  });

  it('скидка 0% не меняет цену', () => {
    expect(applyDiscount(2000, 0)).toBe(2000);
  });

  it('скидка 100% даёт 0 сом', () => {
    expect(applyDiscount(2000, 100)).toBe(0);
  });
});
```

Запускается это одной командой `npx vitest`, и через пару секунд в терминале появляется отчёт:

```text
 ✓ discount.test.js (3 tests) 6ms

 Test Files  1 passed (1)
      Tests  3 passed (3)
```

А если разработчик случайно сломает формулу (например, посчитает скидку от скидки), вывод станет
таким — с точным указанием, что ожидали и что получили:

```text
 ✗ applyDiscount — цена со скидкой › считает скидку 10% от 2000 сом
   AssertionError: expected 1620 to be 1800

   - Expected: 1800
   + Received: 1620
```

<Callout title="Читаем имена тестов как документацию">
Обратите внимание: имена в `it` — это человеческие фразы «скидка 100% даёт 0 сом». Прочитав только
названия тестов, менеджер без единой строки кода понимает, как ведёт себя функция. Поэтому имена
тестов пишут содержательно, а не «тест 1», «тест 2».
</Callout>

## Матчеры: почему toBe не работает для объектов

Методы после `expect(...)` называются **матчерами** (matcher — «сопоставитель»): они сравнивают
реальность с ожиданием. Два главных надо не путать:

- **`toBe`** — строгое сравнение через `===`. Идеально для чисел, строк, булевых значений.
- **`toEqual`** — сравнение **по содержимому**, поле за полем. Нужен для объектов и массивов.

Почему так? Вспомните лекцию про объекты: переменная хранит не сам объект, а **ссылку** на него.
Два одинаковых с виду объекта — это два разных «дома» по разным адресам:

```js
const a = { город: 'Бишкек' };
const b = { город: 'Бишкек' };

expect(a).toBe(b);    // УПАДЁТ: ссылки разные (два разных объекта)
expect(a).toEqual(b); // пройдёт: содержимое одинаковое
```

Типичная ошибка новичка: тест на функцию, возвращающую массив или объект, написан через `toBe` —
и падает, хотя функция работает верно. Если сравниваете структуру — берите `toEqual`.

## Граничные случаи — где ломается код

Хороший тест проверяет не только «обычный» ввод, но и **края** — граничные случаи, на которых код
чаще всего спотыкается:

- пустой массив `[]`, пустая строка `''`;
- ноль, отрицательные числа;
- деление на ноль;
- `NaN` и строка там, где ждали число;
- очень большое число (переполнение);
- особые даты: 29 февраля, 31 декабря, переход через полночь.

<Callout title="Правило: тестируй край, а не серединку">
`sum(2, 3)` пройдёт почти у всех. Баги живут на границах: что вернёт функция для пустого массива?
Для нуля? Для деления на ноль? Именно эти случаи стоит проверять в первую очередь — и именно их
обычно забывают обработать. Практическое упражнение: прежде чем писать тесты, выпишите на бумаге
5 самых «злых» входов для своей функции.
</Callout>

## Пирамида тестирования: юнит, интеграционные, e2e

Юнит-тесты — не единственный вид проверок. В зрелых командах тесты выстраивают **пирамидой** —
как медосмотр: дешёвых экспресс-анализов много, дорогое полное обследование — редко.

| Уровень | Что проверяет | Скорость одного теста | Сколько их обычно |
| --- | --- | --- | --- |
| **Юнит** | одну функцию изолированно | миллисекунды | сотни и тысячи, ~70% |
| **Интеграционный** | связку модулей: функция + база + API вместе | секунды | десятки, ~20% |
| **E2E** (end-to-end, «от края до края») | весь сценарий глазами пользователя: робот открывает браузер, кладёт товар в корзину, оплачивает | минуты | единицы, ~10% |

Почему пирамида, а не наоборот? Экономика. Прогон 1 000 юнит-тестов — 30 секунд; прогон 50
e2e-тестов — легко 40 минут, и падают они часто не из-за бага, а из-за медленной сети или
всплывшего баннера. Юнит-тест, поймавший ошибку, показывает точную строку; упавший e2e-тест
говорит лишь «оплата не прошла» — и дальше час раскопок.

<BusinessNote>
Для аналитика пирамида — аргумент на планировании. Когда подрядчик предлагает «покроем всё
e2e-тестами через кликер», это означает: прогон перед каждым релизом — час машинного времени,
постоянные ложные падения и дорогая поддержка. Правильный вопрос подрядчику: «какая доля логики
покрыта быстрыми юнит-тестами?» Ориентир здоровья проекта — прогон всех тестов быстрее 10 минут:
иначе разработчики начинают релизить, не дожидаясь проверок, и страховка перестаёт работать.
</BusinessNote>

## Покрытие кода: что значит «покрыто на 80%»

**Покрытие** (coverage) — доля строк кода, которые выполнились хотя бы раз во время прогона тестов.
Команда `npx vitest --coverage` печатает такую табличку:

```text
File           | % Lines | Uncovered Line #s
---------------|---------|------------------
discount.js    |   100   |
delivery.js    |    62   | 14-19, 27
```

Читается так: в `delivery.js` строки 14–19 и 27 не выполнялись ни в одном тесте — что бы в них
ни было написано, тесты об этом ничего не знают. Обычно это как раз ветки «если что-то пошло
не так», то есть самые аварийные места.

Но вот главная ловушка, и её любят спрашивать на собеседованиях: **100% покрытия не гарантируют
отсутствие багов**. Покрытие говорит, что строка *выполнялась*, а не что она *проверена на всех
входах*. Аналогия: сторож обошёл все комнаты — покрытие 100%, — но ни в одной не подёргал окна.

```js
function pricePerUnit(total, count) {
  return total / count; // строка «покрыта» тестом ниже
}

// тест даёт 100% покрытия — и пропускает баг деления на ноль:
expect(pricePerUnit(1000, 4)).toBe(250);
// pricePerUnit(1000, 0) вернёт Infinity — и ни один тест этого не видел
```

Разумный ориентир в командах — покрытие 70–90% плюс обязательные тесты на граничные случаи.
Гнаться за круглой цифрой 100% ради отчёта — дорого и бессмысленно: последние проценты обычно
покрывают тривиальные строки, а не реальные риски.

## Моки: как тестировать код, зависящий от сети и времени

Есть код, который нельзя тестировать «в лоб». Функция ниже ходит в интернет за курсом доллара —
например, чтобы магазин на `shop.kg` показывал цены импортных товаров в сомах:

```js
async function priceInSom(usd) {
  const res = await fetch('https://api.rates.kg/usd'); // реальный запрос в сеть!
  const data = await res.json();
  return usd * data.rate;
}
```

Тестировать её напрямую — плохая идея по трём причинам: тест станет **медленным** (сотни миллисекунд
на запрос вместо миллисекунд), **нестабильным** (упадёт без интернета или при сбое сервера) и
**непредсказуемым** (курс НБКР меняется каждый день — какое число писать в `expect`?).

Решение — **мок** (mock, «имитация»): подменная версия зависимости, которая возвращает заранее
известный ответ. Аналогия: краш-тест автомобиля проводят с манекеном, а не с живым водителем, —
манекен ведёт себя предсказуемо, и испытание можно повторять сколько угодно раз:

```js
import { vi, it, expect } from 'vitest';

it('переводит доллары в сомы по курсу', async () => {
  // Подменяем fetch: вместо похода в сеть — мгновенный ответ с курсом 89.5
  vi.stubGlobal('fetch', () =>
    Promise.resolve({ json: () => Promise.resolve({ rate: 89.5 }) })
  );

  expect(await priceInSom(100)).toBe(8950); // 100 × 89.5 — всегда, в любой день
});
```

То же самое делают со временем. Как проверить, что отчёт «за сегодня» правильно работает
29 февраля, не дожидаясь високосного года? Подменить часы:

```js
vi.setSystemTime(new Date('2024-02-29T10:00:00+06:00')); // Бишкек, 29 февраля
// теперь new Date() внутри тестируемого кода вернёт эту дату
```

<Callout title="Что мокать, а что нет">
Мокают **внешнее и непредсказуемое**: сеть, базу данных, текущее время, генератор случайных чисел.
Свою собственную логику не мокают — иначе тест проверяет имитацию, а не код. Если функцию невозможно
протестировать без пяти моков — это сигнал, что она делает слишком много и её стоит разбить.
</Callout>

## Практика 4: соберите expect своими руками

Чтобы снять с тестов последний налёт магии, соберите мини-версию `expect` прямо в браузере —
без установки чего-либо.

1. Откройте консоль браузера: F12 → вкладка Console (на macOS: Cmd+Option+J).
2. Вставьте и выполните этот код:

```js
function expect(actual) {
  return {
    toBe(expected) {
      if (actual === expected) {
        console.log('зелёный: получили ' + actual);
      } else {
        console.error('красный: ожидали ' + expected + ', получили ' + actual);
      }
    }
  };
}

expect(2 + 2).toBe(4);
expect('сом'.toUpperCase()).toBe('СОМ');
expect(0.1 + 0.2).toBe(0.3);
```

3. Проверьте себя: первые две строки должны напечататься зелёным логом, а третья — упасть красным
   с текстом «ожидали 0.3, получили 0.30000000000000004».

Поздравляем: вы только что своими глазами увидели, (а) что тест-библиотека — это обычный JavaScript,
никакого волшебства, и (б) знаменитую проблему дробных чисел, из-за которой деньги в коде считают
в тыйынах, а не в сомах, — про это будет отдельная лекция о числах и деньгах.

<Callout title="TDD: тест сначала">
Есть подход **TDD** (test-driven development, «разработка через тестирование»): сначала пишут тест
(что функция должна делать), запускают — он красный, ведь кода ещё нет, — и только потом пишут код,
пока тест не позеленеет. Звучит непривычно, но заставляет продумать поведение и края до первой
строчки реализации. По сути, в тренажёрах этой лекции вы уже практикуете TDD: тесты заданы заранее,
вы пишете код под них.
</Callout>

## Граничные случаи: где всё ломается

- **Пустой массив в reduce без начального значения.** `[].reduce((a, b) => a + b)` бросает
  `TypeError: Reduce of empty array with no initial value` — тест на пустой список заказов упадёт
  не с неверным числом, а с обрывом программы. Почему: reduce без стартового значения берёт первый
  элемент массива как накопитель, а брать нечего. Как правильно: всегда передавать начальное
  значение — `reduce((a, b) => a + b, 0)` — и отдельно проверять этот случай тестом.

- **`toBe` на NaN.** `expect(NaN).toBe(NaN)` падает, хотя интуитивно кажется, что NaN равен NaN.
  Почему: `toBe` использует `===`-подобную логику, а по стандарту JavaScript `NaN === NaN` — всегда
  `false` (единственное значение, не равное самому себе). Как правильно: использовать матчер
  `toBeNaN()`, специально созданный для этого случая.

- **Мок времени, который забыли выключить.** Тест вызвал `vi.setSystemTime(...)`, но не вызвал
  `vi.useRealTimers()` после себя. Почему это ломает всё: подмена глобальная — следующий тест-файл
  в этом же прогоне тоже увидит поддельную дату 29 февраля 2024 года, хотя ничего про неё не писал.
  Как правильно: сбрасывать моки в `afterEach(() => vi.useRealTimers())`, чтобы тесты не «заражали»
  друг друга.

- **Асинхронный тест без `await`.** `it('получает курс', () => { priceInSom(100).then(r => expect(r).toBe(8950)) })`
  — тест-раннер завершит `it` раньше, чем промис успеет разрешиться, и покажет зелёную галочку
  независимо от результата. Почему: JS не дожидается промисов сам по себе. Как правильно: пометить
  колбэк `async` и поставить `await` перед вызовом — `it('...', async () => { expect(await priceInSom(100)).toBe(8950) })`.
