Код почти никогда не работает с первого раза — и это нормально. Программирование во многом состоит
из **отладки** (debugging): поиска и починки ошибок. Хорошая новость — это навык, а не талант, и ему
можно научиться. У профессионального разработчика на отладку уходит до половины рабочего времени,
и отличает его от новичка не отсутствие багов, а скорость их поиска.

Кстати, слово **баг** (bug — «жук») буквально пришло из железа: в 1947 году инженеры выловили из
реле компьютера Mark II настоящую моль и вклеили её в журнал с подписью «первый реальный случай
обнаружения жука». С тех пор ошибки — «жуки», а их ловля — отладка.

<BusinessNote>
Ошибка в расчёте зарплаты или в отчёте для ГНС КР — это не «баг разработчика», это деньги и
репутация. Живой пример: интернет-магазин в Бишкеке из-за опечатки в условии стал считать доставку
бесплатной для всех. Доставка стоит 150 сом, заказов 300 в день — минус 45 000 сом ежедневно,
и за неделю до обнаружения набежало 315 000 сом. Аналитик, который умеет внятно описать проблему
(«вот входные данные, вот что ожидалось, вот что получилось»), сокращает время починки с дней до
часов — потому что разработчик не тратит день на воспроизведение бага.
</BusinessNote>

## Три вида ошибок

| Вид | Что случилось | Пример | Кто ловит |
| --- | --- | --- | --- |
| **Синтаксическая** | нарушены правила языка | забыта скобка, `=` вместо `===` | интерпретатор, ещё до запуска |
| **Времени выполнения (runtime)** | код запустился, но упал на середине | обратились к свойству у `undefined` | программа падает с сообщением |
| **Логическая** | код работает, ошибок нет, результат неверный | скидка 10% посчитана как ×0.1 вместо ×0.9 | только тесты и внимательность |

Первые два вида — «честные»: программа сама кричит, где болит. Логические — самые коварные и самые
дорогие, потому что молчат. Разберём на числах: товар стоит 2 500 сом, скидка 10%. Правильно —
`2500 * 0.9 = 2250` сом. Программист перепутал и написал `2500 * 0.1` — клиент платит 250 сом.
Сорок таких заказов в день — и магазин недосчитался 80 000 сом, а в консоли при этом ни одной
красной строчки.

Ещё один типичный логический баг — часовые пояса: ночной отчёт собирается «за сутки по UTC»,
а не по Asia/Bishkek (UTC+6). Итог: все продажи после 18:00 уезжают в «завтра», и утренние цифры
не бьются с кассой, хотя код «работает без ошибок».

<Callout title="Читайте сообщение об ошибке — оно помогает">
Новички пугаются красного текста и закрывают его. А зря: в сообщении обычно есть **тип** ошибки
(`TypeError`, `ReferenceError`, `SyntaxError`), **что** случилось и **где** (файл и номер строки).
`ReferenceError: x is not defined` буквально говорит: «переменной x не существует, посмотри строку N».
Это не ругань, а подсказка — и читать её быстрее, чем гадать.
</Callout>

## Stack trace: лесенка под сообщением

Под красной строкой обычно идёт «лесенка» строк — это **stack trace** (стек вызовов): список
функций, через которые программа дошла до места падения. Читается как маршрут посылки в накладной:
кто кому передал, прежде чем она разбилась.

```text
TypeError: Cannot read properties of undefined (reading 'city')
    at printAddress (app.js:12:25)   ← здесь упало
    at processOrder (app.js:31:9)    ← её вызвала эта функция
    at main (app.js:47:3)            ← а её — эта
```

Правила чтения простые:

- **Сверху — место падения**, ниже — цепочка «кто кого вызвал» до самого начала программы.
- Идите сверху вниз и найдите **первую строку с вашим файлом** — чужие строки из библиотек
  (`node_modules`, `react-dom.js`) обычно можно пропустить: библиотека, скорее всего, не виновата,
  ей просто передали плохие данные.
- `app.js:12:25` означает: файл `app.js`, строка 12, символ 25. В DevTools по этой записи можно
  кликнуть — откроется точное место в коде.

## Самая частая ошибка новичка: Cannot read properties of undefined

`TypeError: Cannot read properties of undefined (reading 'city')` — абсолютный чемпион по частоте.
Расшифровка: код попытался прочитать свойство `city` у значения `undefined`. То есть сломалось
**не** `city`, а звено **перед** ним:

```js
const order = { id: 8821 }; // а поля client нет!
console.log(order.client.city);
// order.client === undefined
// undefined.city → TypeError
```

Цепочка `order.client.city` — как три звена: если среднее звено пусто, попытка взять у пустоты
свойство роняет программу. Типичные причины:

- **опечатка** в имени свойства (`order.clint` вместо `order.client`);
- **данные ещё не пришли** из сети, а код уже их читает;
- сервер вернул **пустой или другой по форме ответ**;
- индекс **за границей массива**: `arr[99]` в массиве из трёх элементов — это `undefined`.

Как искать: печатайте цепочку по звеньям — `console.log(order)`, потом `console.log(order.client)` —
и смотрите, где впервые появляется `undefined`. Как защищаться: проверка `if (order.client)` либо
**опциональная цепочка** `order.client?.city` — оператор `?.` вместо падения тихо вернёт
`undefined`, а запасное значение подставит `??` (например, `order.client?.city ?? 'неизвестно'`).

## console.log и его семья

Самый простой и мощный инструмент — **`console.log`**. Не понимаете, почему функция врёт? Выведите
промежуточные значения и посмотрите, где реальность разошлась с ожиданием:

```js
function average(arr) {
  let sum = 0;
  for (let i = 0; i < arr.length; i++) {
    sum += arr[i];
    console.log('шаг', i, 'сумма пока', sum); // подглядываем внутрь
  }
  return sum / arr.length;
}
```

Увидели, что на каком-то шаге сумма «не та» — значит, баг рядом. Это как расставить контрольные
точки по маршруту, чтобы понять, где свернули не туда. Но у `console` есть и менее известные
родственники, которые экономят массу времени:

| Метод | Что делает | Когда полезен |
| --- | --- | --- |
| `console.log(x)` | печатает значение | универсальная «контрольная точка» |
| `console.table(arr)` | массив объектов — аккуратной таблицей | выгрузка заказов: битая строка видна сразу |
| `console.error(x)` | печатает красным | пометить настоящую проблему среди сотни логов |
| `console.warn(x)` | печатает жёлтым | «подозрительно, но не смертельно» |
| `console.time('метка')` / `console.timeEnd('метка')` | секундомер между двумя точками | «почему отчёт строится 40 секунд?» |

Попробуйте прямо здесь — заодно поймайте классический баг с `NaN`:

<Sandbox code={`const orders = [
  { id: 101, city: 'Бишкек', total: 2500 },
  { id: 102, city: 'Ош', total: 1800 },
  { id: 103, city: 'Каракол' }, // у этого заказа нет total!
];

// console.table показывает массив таблицей — пустая ячейка видна сразу
console.table(orders);

let sum = 0;
for (let i = 0; i < orders.length; i++) {
  sum += orders[i].total;
  console.log('после заказа', orders[i].id, 'сумма:', sum);
}
console.error('Итог:', sum, '— а должен быть числом!');`} />

Запустите и посмотрите: на третьем шаге `sum` превращается в `NaN` (Not a Number — «не число»),
потому что `2500 + 1800 + undefined` числом быть не может. **`NaN` заразен**: один раз появившись,
он портит все дальнейшие вычисления. Если в итоге отчёта `NaN` — ищите первый шаг, где он возник,
именно так, как мы сейчас: логом на каждой итерации.

## Отладчик DevTools: стоп-кадр для программы

`console.log` хорош, но требует «стрелять вслепую»: добавил вывод, перезапустил, посмотрел, добавил
ещё. У браузера есть инструмент мощнее — **отладчик** (debugger) во вкладке **Sources** DevTools.
Его главная идея — **точка останова** (breakpoint): вы помечаете строку, и программа, дойдя до неё,
замирает как стоп-кадр на видео. В этот момент можно рассмотреть значения **всех** переменных —
не печатая ни одной строчки.

Как это выглядит на практике:

1. Откройте DevTools клавишей **F12** (или Cmd+Option+I на macOS) → вкладка **Sources**.
2. Найдите свой файл, кликните по **номеру строки** — появится синяя метка. Это и есть breakpoint.
3. Обновите страницу или вызовите функцию — выполнение замрёт на помеченной строке.
4. Наведите курсор на любую переменную — увидите её текущее значение. Справа панель **Scope**
  показывает вообще все переменные в этот момент.
5. Кнопки управления: **Resume** (продолжить до следующей точки), **Step over** (F10 — выполнить
  строку и шагнуть на следующую), **Step into** (F11 — зайти внутрь вызываемой функции).

Есть и способ из кода: строка `debugger;` посреди функции работает как breakpoint — браузер
остановится на ней сам (если DevTools открыты). Только не забудьте убрать её перед сдачей кода.

<Callout title="Когда что выбирать">
`console.log` — быстрые проверки «что тут лежит» и отладка на телефоне или на чужой машине.
Отладчик — запутанные случаи: длинный цикл, десяток переменных, «падает где-то на 73-й итерации».
Поставить **условный** breakpoint (правый клик по метке → условие, например `i === 73`) быстрее,
чем читать простыню из тысячи логов.
</Callout>

## throw: когда код должен упасть сам

До сих пор мы ловили чужие падения. Но иногда правильно — **упасть намеренно**. Оператор `throw`
бросает **исключение** (exception — сигнал «работать дальше нельзя»), обычно объект `new Error`
с текстом причины:

```js
function applyDiscount(price, percent) {
  if (typeof price !== 'number' || Number.isNaN(price)) {
    throw new Error('Цена должна быть числом, получено: ' + price);
  }
  if (percent < 0 || percent > 100) {
    throw new Error('Скидка ' + percent + '% вне диапазона 0–100');
  }
  return price * (1 - percent / 100);
}
```

Зачем падать, если можно «как-нибудь посчитать»? Затем же, зачем пожарная сигнализация: лучше
громко сейчас, чем тихо сгореть. Если функция молча вернёт ерунду, ошибка всплывёт через неделю
в отчёте для руководства — и искать её будут по всей программе. А `throw` останавливает работу
**в момент и в месте** появления плохих данных, с внятным текстом. Правило зрелых команд:
**лучше упасть громко, чем соврать тихо**.

## try / catch / finally: страховочная сетка

Иногда ошибка ожидаема (данные из сети могут прийти битыми). Чтобы программа не рухнула целиком,
опасный код оборачивают в **`try/catch`**:

```js
try {
  const data = JSON.parse(rawText); // вдруг это не JSON
  console.log(data.name);
} catch (err) {
  console.error('Не удалось разобрать данные:', err.message);
} finally {
  console.log('Проверка завершена'); // выполнится в любом случае
}
```

`try` — «попробуй», `catch` — «если упало, вот что делать вместо паники». У пойманной ошибки есть
`err.message` (текст), `err.name` (тип) и `err.stack` (тот самый stack trace). А блок **`finally`**
выполняется **всегда** — и после успеха, и после ошибки. Это «в любом случае выключи свет, когда
уходишь»: убрать спиннер загрузки, закрыть соединение, разблокировать кнопку «Оплатить» — то, что
обязано случиться при любом исходе.

<Callout title="try/catch — не ковёр для мусора">
Оборачивать в `try/catch` весь код подряд и оставлять `catch` пустым — худшая практика: ошибки
не исчезают, они просто перестают быть видимыми (тот самый «тихий соврал»). Ловите только там, где
знаете, **что** может упасть и **что делать** в ответ: показать пользователю сообщение, повторить
запрос, подставить запасное значение.
</Callout>

## Чек-лист: как искать любой баг

1. **Воспроизведите.** Найдите минимальные входные данные, на которых ломается. «Иногда неправильно
  считает» — не баг-репорт; «на заказе с пустой корзиной возвращает NaN» — баг-репорт.
2. **Прочитайте сообщение и stack trace.** Тип ошибки, строка, первая строка вашего файла.
3. **Локализуйте.** `console.log` по звеньям или breakpoint — сузьте место до одной-двух строк.
  Работает «бинарный поиск»: проверьте середину цепочки вычислений — до неё всё хорошо? Значит,
  баг во второй половине.
4. **Проверьте данные, не только код.** Половина «багов» — это сюрпризы во входных данных: пустая
  строка, `null`, число в виде строки `"2500"`.
5. **Почините и проверьте на краях.** Пустой массив, ноль, отрицательное число, один элемент.
6. **Закрепите тестом**, чтобы баг не вернулся (об этом — следующая лекция).

### Упражнение: первый breakpoint своими руками

Виджета для DevTools нет — поэтому руками, это займёт три минуты:

1. Откройте любую страницу, нажмите **F12** → вкладка **Console**.
2. Вставьте туда код (он объявляет функцию с намеренной паузой) и нажмите Enter:

```js
function demo() {
  let sum = 0;
  for (let i = 1; i <= 3; i++) {
    debugger; // стоп-кадр на каждой итерации
    sum += i * 100;
  }
  return sum;
}
demo();
```

3. Браузер сам переключится на вкладку **Sources** и замрёт на строке `debugger;`. Вы должны
  увидеть подсвеченную строку, а справа — панель **Scope** со значениями `sum` и `i`.
4. Нажмите **F10** (Step over) два раза и наведите курсор на `sum` — значение изменилось с 0 на 100.
5. Нажмите **Resume** (синий треугольник) — программа добежит до следующей итерации и снова замрёт,
  теперь `i` равно 2. Ещё два Resume — и в консоли появится результат `600`.

Если всё так — поздравляем, вы только что посмотрели программе «под кожу» без единого
`console.log`. Это и есть основной рабочий инструмент отладки в индустрии.
