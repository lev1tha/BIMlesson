## Введение

Откройте консоль браузера и наберите `0.1 + 0.2`. Ответ будет `0.30000000000000004`. Это не баг
вашего компьютера — так считает **любой** компьютер в мире, на любом языке программирования. Для
кода «про картинки» эта странность безобидна. Для кода «про деньги» — это расхождение в отчётности,
злой бухгалтер и неприятные вопросы от ГНС при проверке. Сегодня разберёмся, откуда берутся такие
сюрпризы и как писать код, которому можно доверять расчёты.

<BusinessNote>
Ошибки округления — классика финансовых катастроф в софте. Известный сюжет: система считает НДС
(в Кыргызстане — 12%) от каждой строки заказа и от итога — и эти суммы расходятся на тыйын;
на миллионе заказов это уже десятки тысяч сомов расхождений, которые бухгалтерия ищет вручную.
Аналитик, который понимает природу таких ошибок, находит их причину за час, а не за неделю — и
именно его зовут, когда «в 1С одна цифра, а в отчёте банка другая».
</BusinessNote>

**Что вы узнаете:**

- почему 0.1 + 0.2 не равно 0.3 и как правильно сравнивать дробные числа
- почему деньги хранят в целых тыйынах и где у чисел предел точности
- как считать по дробному курсу валют и округлять один раз, явно и в самом конце
- как превратить ввод пользователя с запятыми и пробелами в число и не получить NaN
- как не потерять часы и сутки на датах и часовых поясах, включая Asia/Bishkek
- какие грабли прячутся в процентах и больших числах

Пригодится из прошлых лекций: «Первая программа».

## Почему 0.1 + 0.2 ≠ 0.3

Компьютер хранит числа в двоичной системе — только нули и единицы. Целые числа перекладываются в
двоичную запись точно: 5 — это `101`, 12 — это `1100`. А вот с дробями беда: **0.1 в двоичной системе —
бесконечная периодическая дробь**, как 1/3 = 0.3333… в десятичной. Записать её точно нельзя — только
обрезать где-то.

JavaScript хранит все числа в формате **double** (64-битное число с плавающей точкой): примерно
15–17 значащих десятичных цифр. Поэтому в памяти лежит не 0.1, а ближайшее представимое число —
чуть-чуть другое. Складываем два «чуть-чуть неточных» числа — получаем 0.30000000000000004.

```js
console.log(0.1 + 0.2);            // 0.30000000000000004
console.log(0.1 + 0.2 === 0.3);    // false — сюрприз в if!
console.log(0.3 - 0.2);            // 0.09999999999999998
console.log(19.99 * 100);          // 1998.9999999999998 — цена «поплыла»
```

Последняя строка — самая коварная: вы просто перевели цену в тыйыны, а она уже не целая.

<Callout title="Как сравнивать дробные числа">
Никогда не сравнивайте дробные числа через `===`. Правильный способ — проверять, что разница
меньше крошечного допуска (его называют «эпсилон»; в JS даже есть константа `Number.EPSILON` —
минимальный «зазор» между соседними дробными числами около единицы):

```js
function nearlyEqual(a, b) {
  return Math.abs(a - b) < 1e-9; // разница меньше одной миллиардной
}
nearlyEqual(0.1 + 0.2, 0.3); // true
```
</Callout>

## Деньги: только целые тыйыны

Из первого раздела следует железное правило всей финансовой разработки: **деньги никогда не хранят
в дробных числах**. Их хранят **целым числом минимальных единиц** — тыйынов, центов, копеек:

```js
// ПЛОХО: сомы с дробной частью
let price = 19.99;
let total = price * 3;        // 59.96999999999999

// ХОРОШО: целые тыйыны
let priceTyiyn = 1999;
let totalTyiyn = priceTyiyn * 3;  // 5997 — точно
```

Целые числа double хранит точно вплоть до `Number.MAX_SAFE_INTEGER` = 9 007 199 254 740 991.
В тыйынах это около 90 триллионов сомов — примерно 180 годовых госбюджетов Кыргызстана (бюджет КР —
порядка 500 млрд сом), так что любой бухгалтерии страны запаса хватит. Но дальше этой границы
начинаются потери:

```js
console.log(9007199254740992 === 9007199254740993); // true (!!)
```

Для сумм за пределами безопасной зоны (криптовалюты с 18 знаками после запятой, микросекунды
процентных начислений) существует тип **BigInt** — целые числа неограниченной длины:
`12345678901234567890n` (обратите внимание на `n` в конце). А правила округления в финансах задаёт
не программист, а бухгалтерия и закон — поэтому округление в коде должно быть **явным и в одном
месте**, а не «как получится» после каждой операции.

Потренируемся: напишите функцию, которая красиво печатает сумму в тыйынах.

## Курсы валют: дробный курс, целые тыйыны

Магазин на shop.kg продаёт подписку на зарубежный сервис за 12.99 доллара. НБКР публикует
официальный курс каждый рабочий день на nbkr.kg — допустим, сегодня 87.45 сома за доллар. Как
посчитать цену в сомах и не потерять точность?

Хитрость в единицах: цент × (сом/доллар) = тыйын. Поэтому умножаем **центы** на курс и округляем
**один раз, явно**:

```js
const rate = 87.45;               // курс НБКР: сомов за 1 доллар
const priceCents = 1299;          // 12.99 $ в центах

const raw = priceCents * rate;    // 113597.55 — дробные тыйыны, промежуточный результат
const tyiyn = Math.round(raw);    // 113598 тыйынов = 1135.98 сома — итог
```

Курс — единственное место, где дробное число допустимо: мы умножаем на него один раз и тут же
округляем.

<BusinessNote>
Почему это важно в деньгах: платёжный агрегатор проводит 200 000 валютных операций в месяц. Если
каждая операция теряет или приобретает случайные пол-тыйына из-за неявных округлений, расхождение
с банковской выпиской — до 1 000 сомов в месяц. Сумма смешная, но **сверка не сходится**, и
бухгалтер тратит два рабочих дня (его день стоит дороже 3 000 сомов) на поиск «пропавших» тыйынов.
Явное округление в одном месте кода делает сверку сходящейся всегда — ноль потраченных дней.
</BusinessNote>

## Округление: одно, явное, в конце

Даже привычный `toFixed` подводит — он работает с теми же неточными double:

```js
(1.005).toFixed(2); // "1.00", а не "1.01" — в памяти лежит 1.00499999…
```

А теперь классика офисной жизни: трое коллег обедали на Киевской в Бишкеке, счёт — 1 000 сомов
(100 000 тыйынов). Поделить поровну — 33 333.33… тыйына. Дробный тыйын заплатить нельзя. Правило
финансового кода: части округляем вниз, а оставшиеся тыйыны раздаём по одному первым участникам —
тогда **сумма частей всегда равна исходной сумме**. Так делят платежи по рассрочке, комиссию между
партнёрами и НДС между строками заказа.

## Ввод пользователя: запятые, пробелы и NaN

Менеджер вставляет в вашу форму сумму из выгрузки Excel: `1 234,56`. Что увидит код?

```js
parseFloat('1 234,56');  // 1 — остановился на первом пробеле!
Number('1 234,56');      // NaN — «не смог»

// Правильно: сначала нормализуем строку
const raw = '1 234,56';
const num = Number(raw.replace(/\s/g, '').replace(',', '.')); // 1234.56
Number.isNaN(num);       // false — можно считать
```

**NaN** (Not a Number, «не число») — специальное значение, которое JavaScript возвращает, когда
вычисление не имеет числового смысла. Коварство в том, что NaN не бросает ошибку — он **тихо
расползается** по расчётам: `NaN * 100` — снова NaN, и в отчёте вместо итога красуется «NaN сом».
Поэтому любой ввод пользователя проверяем через `Number.isNaN` сразу после разбора. И ещё нюанс из
жизни: Excel часто разделяет тысячи **неразрывным пробелом** — на глаз он обычный, но
`replace(' ', '')` его не поймает, а вот `\s` в регулярном выражении ловит оба вида.

## Даты: минное поле номер два

Дата и время выглядят простыми ровно до первого бага «акция включилась не в полночь». В JavaScript
за даты отвечает объект `Date`, и у него есть исторические странности, о которых нужно знать заранее.

```js
const d = new Date(2026, 0, 15); // 15 ЯНВАРЯ 2026 — месяцы считаются С НУЛЯ!
d.getFullYear(); // 2026
d.getMonth();    // 0  — январь
d.getDate();     // 15 — день месяца
d.getDay();      // 4  — день недели (0 = воскресенье!)
```

Два классических капкана в одной пачке: **месяцы нумеруются с 0** (декабрь — это 11), а `getDay()`
возвращает день недели, где 0 — воскресенье. Перепутать `getDate` и `getDay` — дежурный баг
новичка.

Внутри `Date` хранит одно число — **timestamp**: количество миллисекунд, прошедших с полуночи
1 января 1970 года по Гринвичу (эту точку называют «эпохой Unix»). Это гениально простое решение:
момент времени — просто число, а значит даты можно сравнивать и вычитать как числа.

```js
const start = new Date('2026-08-01T00:00:00Z').getTime(); // 1785542400000
const end = new Date('2026-08-15T00:00:00Z').getTime();
const days = (end - start) / (1000 * 60 * 60 * 24); // 14 дней
```

## Часовые пояса: где теряются часы и сутки

Момент времени один, а показаний часов — много: когда в Бишкеке 18:00, в Стамбуле 15:00, а по
Гринвичу — ровно полдень. Отсюда главное правило распределённых систем: **храним и передаём время
в UTC** (всемирное координированное время, «нулевой пояс»), а **показываем пользователю в его
местном**. Кыргызстан живёт в поясе **Asia/Bishkek — UTC+6 круглый год**, стрелки на летнее время
не переводятся с 2005 года.

Стандарт записи даты-времени называется **ISO 8601** — его понимают все языки и базы данных:

```text
2026-08-15T14:30:00Z        ← Z = UTC («зулу»)
2026-08-15T20:30:00+06:00   ← тот же момент по бишкекским часам
2026-08-15                  ← просто дата
```

Обратите внимание: обе первые строки — **один и тот же момент времени**, записанный для разных
поясов. Сравнивать строки нельзя, сравнивать нужно timestamp.

<Callout title="Три классических бага с датами">
1. **«Акция началась в 6 утра».** Магазин shop.kg хранит дату старта как `2026-08-15` без времени.
   Парсер считает это полуночью **UTC**, а полночь UTC в Бишкеке — это 06:00 утра. Клиенты ждали
   скидку в полночь, а она включилась к завтраку. Лечится хранением полного момента с поясом:
   `2026-08-14T18:00:00Z`.
2. **Сезонное время партнёров.** Кыргызстан часы не переводит, а Европа — переводит. Созвон
   «каждый понедельник в 15:00 по Бишкеку» для партнёра в Берлине дважды в год съезжает на час.
   Календарную арифметику ведут библиотеки дат, а не ручное прибавление 86 400 000 миллисекунд:
   в ночь перевода сутки в Европе длятся 23 или 25 часов.
3. **День рождения в феврале.** Прибавили год к 29 февраля — получили 1 марта. Граничные случаи
   календаря (високосные годы, конец месяца) обязаны быть в тестах.
</Callout>

## Проценты и большие числа: последние грабли

Ещё две ситуации, где числа подводят аналитика.

**Копящаяся ошибка.** Тысяча операций по 0.1% от суммы, посчитанных с округлением на каждом шаге,
дают заметное расхождение с расчётом «от итога»: каждое промежуточное округление добавляет в
среднем до половины тыйына ошибки. Миллион строк заказов в месяц — до 5 000 сомов расхождения на
пустом месте. Правило: округлять **один раз в конце**, а промежуточные значения держать точными
(в тыйынах).

**ID из базы данных.** Идентификаторы в больших системах давно перевалили за `MAX_SAFE_INTEGER`.
Если API вернул `{"id": 9007199254740993}`, то после `JSON.parse` в JavaScript это число тихо
превратится в `...992` — на единицу меньше! Поэтому большие ID передают **строками**: `"id":
"9007199254740993"`. Встретите в API строковые ID — теперь вы знаете, что это не лень разработчика,
а защита от потери точности.

```js
JSON.parse('{"id": 9007199254740993}').id === 9007199254740992; // true — id «уехал»
```

## Практика: пять минут в консоли

Всё из этой лекции проверяется руками прямо сейчас. Откройте консоль браузера (F12 → вкладка
Console; на ноутбуке без F-клавиш — Ctrl+Shift+J, на Mac — Cmd+Option+J) и выполните по шагам.
Сверяйте каждый результат с ожидаемым — если совпало, тема закреплена.

1. Наберите `0.1 + 0.2` — вы должны увидеть `0.30000000000000004`.
2. Наберите `(1.005).toFixed(2)` — вы должны увидеть `"1.00"`, хотя «по-школьному» ждали 1.01.
3. Наберите `Number.MAX_SAFE_INTEGER` — вы должны увидеть `9007199254740991`.
4. Наберите `9007199254740992 === 9007199254740993` — вы должны увидеть `true`: за границей
   безопасной зоны соседние целые неразличимы.
5. Наберите `new Date().getTimezoneOffset()` — в Бишкеке вы должны увидеть `-360`: это смещение
   от UTC в минутах, минус означает «восточнее Гринвича», 360 минут = 6 часов.
6. Сравните `new Date().toString()` и `new Date().toISOString()` — второе время должно отставать
   ровно на 6 часов: это тот же момент, но в UTC.
7. Наберите `new Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'KGS' }).format(1234.56)` —
   вы должны увидеть сумму с пробелом-разделителем тысяч и запятой: `"1 234,56 KGS"`.

Если что-то не сошлось в шаге 5 — проверьте часовой пояс своей системы: возможно, компьютер
настроен не на Asia/Bishkek.

## Шпаргалка на выход

| Ситуация | Правило |
| --- | --- |
| Деньги | целые тыйыны; округление — явно и один раз |
| Сравнение дробных | `Math.abs(a - b) < eps`, никогда `===` |
| Вывод сумм | `Intl.NumberFormat` с валютой KGS, считать — отдельно |
| Курс валют | умножили на курс → округлили один раз |
| Делёж суммы | части целые, остаток раздать по одному тыйыну |
| Ввод пользователя | нормализовать пробелы и запятую, проверить `Number.isNaN` |
| Хранение времени | UTC + ISO 8601, показывать в поясе пользователя |
| Часовой пояс КР | Asia/Bishkek, UTC+6 круглый год, перевода стрелок нет |
| Арифметика дат | timestamp для интервалов, библиотека для календаря |
| Большие ID | передавать строками |
| Месяцы в Date | считаются с нуля: январь = 0 |

## Граничные случаи: где всё ломается

**Пустая строка в поле суммы.** Пользователь стёр значение и нажал «Сохранить» — форма отправляет
`''`. `Number('')` возвращает `0`, а не ошибку, потому что пустая строка считается «нулём» по
правилам приведения типов. Итог: заказ на 0 сомов тихо проходит вместо предупреждения. Правильно —
проверять пустой ввод отдельной веркой до вызова `Number()`, ещё до попытки распознать число.

**29 февраля плюс год.** `new Date(2024, 1, 29)` — последний день февраля високосного года. Если
прибавить год «наивно» (`setFullYear(year + 1)`), получится 1 марта 2025 — объект `Date`
перескакивает несуществующий день без единой ошибки. Для годовщин и подписок с датой продления
29 февраля решение выбирают явно: либо 28 февраля, либо 1 марта — но не отдаётся на волю движка дат.

**Курс НБКР равен нулю или не пришёл.** Если API курсов недоступен и переменная `rate` осталась
`undefined`, `priceCents * rate` даёт `NaN`, а `Math.round(NaN)` — тоже `NaN`. Заказ проведётся с
ценой «NaN тыйынов», если не поставить проверку `Number.isFinite(rate)` перед расчётом с падением на
последний известный курс или явной ошибкой пользователю.

**Отрицательная сумма в splitBill.** Возврат денег клиенту описывают отрицательным `total`, например
`-100000`. `Math.floor(-100000 / 3)` округляет **в меньшую сторону**, то есть от нуля, а не к нулю
(результат `-33334`, а не `-33333`), и остаток тоже меняет знак — наивная копипаста логики деления
положительных сумм на возвраты даёт неверную раздачу тыйынов. Отрицательные суммы обрабатывают
отдельной веткой или считают через модуль числа с последующей сменой знака у результата.
